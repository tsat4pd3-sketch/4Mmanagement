DevTools — 3 แท็บที่ต้องใช้เป็น (กด F12)

🔴 Console

  • อ่าน error สีแดง
  • ดูค่าที่เรา console.log() ออกมา
  • ตัวหนังสือแดง = บอกทั้งไฟล์และบรรทัด
  • เปิดค้างไว้ตลอดเวลาเขียนโค้ด

🌐 Network

  • ดูว่ายิงไปถามฐานข้อมูลจริงมั้ย
  • ได้ข้อมูลกลับมากี่แถว
  • สีแดง = โดนปฏิเสธ (มักเป็นเรื่องสิทธิ์)
  • เช็คตรงนี้ก่อนโทษโค้ดตัวเอง

🧱 Elements

  • ดูโครงหน้าเว็บที่วาดออกมาจริง
  • ลองแก้สี/ขนาดสดๆ ได้
  • แก้ตรงนี้ไม่ได้แก้ไฟล์ — refresh แล้วหาย
  • ใช้ลองก่อนแล้วค่อยไปแก้ในโค้ด
ทักษะที่ทำให้คุณต่างจากคนอื่น: คนที่ไปต่อได้ = คนที่อ่าน error แล้วเดาทางออกได้ ไม่ใช่คนที่จำโค้ดได้เยอะ · error ไม่ใช่ศัตรู มันคือใบแจ้งซ่อมที่บอกตำแหน่งให้แล้ว

3 ภาษา 3 หน้าที่ — เทียบกับคน

HTML = โครงกระดูก

  • บอกว่ามีอะไรอยู่ในหน้า
  • หัวข้อ · ย่อหน้า · ปุ่ม · ตาราง · ช่องกรอก
  • ไม่มี HTML = หน้าว่างเปล่า

CSS = เสื้อผ้า

  • บอกว่าหน้าตาเป็นยังไง
  • สี · ขนาด · ระยะห่าง · การจัดวาง
  • ไม่มี CSS = หน้าตายังใช้ได้ แค่ดูโบราณ

JavaScript = สมอง

  • บอกว่ากดแล้วเกิดอะไร
  • คำนวณ · เรียกข้อมูล · เปลี่ยนหน้าจอ
  • ไม่มี JS = หน้านิ่ง กดอะไรไม่ได้
<h2>ยอดผลิตวันนี้</h2> ← HTML: มีหัวข้อ <style> h2 { color: green; } </style> ← CSS: ให้มันเขียว <script> document.querySelector('h2').textContent = 'ยอด 1,240 ชิ้น' </script> ← JS: เปลี่ยนข้อความ

/* 1) เลือกของที่จะแต่ง */ h2 { color: #0D3D14; } /* ทุก h2 ในหน้า */ .card { padding: 16px; } /* ทุกอันที่ class="card" */ #total { font-weight: bold; } /* อันที่ id="total" */ /* 2) กล่องทุกใบมี 4 ชั้น — เรียงจากในออกนอก */ .card { padding: 16px; /* ระยะจากขอบถึงข้อความ */ border: 1px solid #ddd; /* เส้นขอบ */ margin: 12px; } /* ระยะห่างจากกล่องอื่น */ /* 3) จัดวางหลายกล่อง — ใช้ 2 ตัวนี้พอ */ .row { display: flex; gap: 12px; } /* เรียงแถวเดียว */ .grid { display: grid; grid-template-columns: repeat(3,1fr); } /* ตาราง 3 คอลัมน์ */

JavaScript — จัดการรายการ (ใช้ทุกหน้าจริงๆ)

const logs = [ { line: 'ASSY 060', ok: 1240, ng: 6 }, { line: 'ASSY 061', ok: 980, ng: 0 }, { line: 'HDF 1', ok: 450, ng: 12 }, ] // filter = คัดเฉพาะที่ต้องการ → เหลือ 2 แถว const hasNg = logs.filter(r => r.ng > 0) // map = แปลงทุกตัวเป็นอย่างอื่น → ['ASSY 060','ASSY 061','HDF 1'] const names = logs.map(r => r.line) // reduce = ยุบทั้งหมดเหลือค่าเดียว → 2670 const totalOk = logs.reduce((sum, r) => sum + r.ok, 0) // find = หาตัวแรกที่ตรงเงื่อนไข → { line:'HDF 1', ... } const worst = logs.find(r => r.ng > 10)
อ่านว่า: r => r.ng > 0 แปลว่า "เอาแต่ละแถวมาเรียกว่า r แล้วตอบว่า ng ของมันมากกว่า 0 มั้ย" · เครื่องหมาย => เรียกว่า arrow function — 4 ตัวนี้ (filter/map/reduce/find) ครอบคลุมงานสรุปข้อมูลเกือบทั้งหมดในระบบ ESM

JavaScript — ฟังก์ชัน และการ "รอ"

// ฟังก์ชัน = ชุดคำสั่งที่ตั้งชื่อไว้ เรียกใช้ซ้ำได้ function calcOee(a, p, q) { return a * p * q / 10000 } calcOee(90, 88, 99) // → 78.4 // เขียนแบบสั้น (arrow) — เจอบ่อยกว่าในโค้ดจริง const calcOee = (a, p, q) => a * p * q / 10000 // ───────────────────────────────────────────────────── // งานที่ "ต้องรอ" เช่น ถามฐานข้อมูล ต้องใส่ async/await async function loadLogs() { const { data, error } = await supabase.from('daily_logs').select('*') // ↑ await = รอตรงนี้จนกว่าข้อมูลจะมาถึง if (error) { console.error(error); return [] } return data }
⚠️ ลืม await = ได้ "ใบสัญญาว่าจะส่งของ" มาแทนตัวข้อมูล → หน้าจอว่างเปล่าโดยไม่มี error · เป็นบั๊กที่มือใหม่เจอบ่อยที่สุดอันดับ 1

⚠️ 4 กับดัก JavaScript ที่กัดทุกคน

= กับ === ไม่เหมือนกัน
= คือ "ตั้งค่าให้" · === คือ "เท่ากันมั้ย" — เขียนผิดที่ในเงื่อนไข if แล้วโปรแกรมจะทำงานตลอดเวลาโดยไม่แจ้งอะไร
ค่าที่ยังมาไม่ถึง = undefined
ข้อมูลยังโหลดไม่เสร็จแล้วสั่ง rows.length → error "Cannot read properties of undefined" · ป้องกันด้วย rows?.length หรือตั้งค่าเริ่มต้นเป็น [] เสมอ
ตัวเลขจากช่องกรอก = ข้อความ
'10' + 5 ได้ '105' ไม่ใช่ 15 · แปลงก่อนคำนวณเสมอ: Number(qty)
วันที่ = กับดักที่แพงที่สุด
ระบบเราเคยลงวันที่ผิดไป 1 วันทั้งระบบ เพราะใช้ toISOString() ที่คืนเวลาสากล (ช้ากว่าไทย 7 ชม.) — รายละเอียดเต็มอยู่ในหัวข้อบทเรียนช่วงบ่าย

ถ้าเขียน JavaScript เปล่าๆ

  • หน้าใหญ่ขึ้น = ลืมมากขึ้น
  • เลขบนจอไม่ตรงกัน คือบั๊กคลาสสิก

ถ้าใช้ React

setQty(qty + 1) // จบ. // ทุกที่ที่ใช้ qty อัปเดตเองหมด // ตัวเลข · ยอดรวม · แถบความคืบหน้า
  • เราบอกแค่ "ข้อมูลตอนนี้คืออะไร"
  • React ไปวาดหน้าจอให้ตรงเอง
  • เลขบนจอตรงกันเสมอโดยอัตโนมัติ
ประโยคเดียวที่ต้องจำจากทั้งช่วงนี้: ในโลก React เราไม่สั่งแก้หน้าจอ — เราแก้ข้อมูล แล้วหน้าจอตามเอง

props — ส่งค่าเข้าไปในชิ้นส่วน

// รับค่าเข้ามาทาง { } ในวงเล็บ แล้วเอาไปใช้ด้วย { } export default function LineCard({ name, qty, target }) { const pct = Math.round(qty / target * 100) return ( <div className="card"> <h3>{name}</h3> <p>{qty.toLocaleString()} / {target.toLocaleString()} ชิ้น ({pct}%)</p> </div> ) } // เรียกใช้ — ส่งค่าเหมือนใส่คุณสมบัติของแท็ก HTML <LineCard name="ASSY 060" qty={1240} target={1500} /> <LineCard name="ASSY 061" qty={980} target={1000} />
ข้อความใส่ใน "..." · ตัวเลข/ตัวแปร/ค่าจริง-เท็จ ใส่ใน {...} · props ส่งลงล่างอย่างเดียว — ลูกแก้ค่าของแม่ไม่ได้ (เหมือนใบสั่งงานที่แนบมากับกล่อง จะแก้ใบเองไม่ได้)

state — ค่าที่เปลี่ยนได้ระหว่างใช้งาน

import { useState } from 'react' export default function Counter() { // ค่าปัจจุบัน ตัวสั่งเปลี่ยนค่า ค่าเริ่มต้น const [qty, setQty] = useState(0) return ( <div> <p>นับได้ {qty} ชิ้น</p> <button onClick={() => setQty(qty + 1)}>+1</button> <button onClick={() => setQty(0)}>เริ่มใหม่</button> </div> ) }

เกิดอะไรขึ้นตอนกดปุ่ม

  • เรียก setQty → React รู้ว่าข้อมูลเปลี่ยน
  • React รันฟังก์ชันนี้ใหม่ทั้งอัน
  • วาดเฉพาะส่วนที่ต่างจากเดิม

⚠️ ห้ามทำ

  • qty = qty + 1 ← หน้าจอไม่ขยับ
  • ต้องผ่าน setQty เท่านั้น
  • ของที่เปลี่ยนแล้วต้องเห็นบนจอ = ต้องเป็น state

⚠️ กฎเหล็กของ Hooks

useState / useEffect ต้องอยู่บนสุดเสมอ
  • ห้ามวางไว้หลัง if (loading) return ...
  • ห้ามวางใน if · ใน for · ในฟังก์ชันย่อย

ออกแบบตารางแรก

-- รันในหน้า SQL Editor ของ Supabase create table daily_logs ( id bigserial primary key, -- เลขประจำแถว ระบบแจกให้เอง work_date date not null, -- วันงาน '2026-09-08' shift text not null default 'day', -- กะ day / night line_name text not null, -- ชื่อไลน์ qty_ok int not null default 0, -- จำนวนดี qty_ng int not null default 0, -- จำนวนเสีย note text, -- หมายเหตุ (ว่างได้) created_at timestamptz default now() -- เวลาที่บันทึก );

ชนิดข้อมูลที่ใช้จริง 5 ตัว

  • text — ข้อความทุกแบบ
  • int / numeric — จำนวนเต็ม / มีทศนิยม
  • date — วันที่ล้วน
  • timestamptz — วันที่+เวลา
  • boolean — จริง/เท็จ

3 ข้อที่ต้องคิดตั้งแต่ตอนสร้าง

  • อะไรห้ามว่าง → ใส่ not null
  • ค่าตั้งต้นคืออะไร → ใส่ default
  • ใครบันทึก เมื่อไหร่ → เก็บไว้เสมอ ไม่งั้นสอบกลับไม่ได้

// อ่าน — เลือกคอลัมน์ที่ใช้จริง ไม่ต้อง * ทั้งหมด const { data, error } = await supabase .from('daily_logs') .select('id, work_date, line_name, qty_ok, qty_ng') .eq('work_date', '2026-09-08') // เท่ากับ .gt('qty_ng', 0) // มากกว่า .order('line_name') // เรียง .limit(200) // เอาเท่าที่ใช้ // เพิ่มแถวใหม่ await supabase.from('daily_logs').insert({ work_date, line_name, qty_ok: 1240 }) // แก้แถวเดิม — ★ ต้องมี .eq() เสมอ ไม่งั้นแก้ทั้งตาราง await supabase.from('daily_logs').update({ qty_ng: 6 }).eq('id', 12) // ลบ — ★ ต้องมี .eq() เสมอ await supabase.from('daily_logs').delete().eq('id', 12)
⚠️ ลืม .eq() ใน update/delete = แก้/ลบทั้งตาราง และมันจะรายงานว่า "สำเร็จ" ด้วย · ทดสอบกับข้อมูลจริงเมื่อไหร่ เจ็บเมื่อนั้น — เขียน .eq() ก่อนเขียนอย่างอื่นเสมอ

⚠️ กฎเหล็กข้อ 1 ของระบบเรา

คำสั่งฐานข้อมูล "ไม่โวยวาย" เวลาล้มเหลว

⚠️ อีก 2 กับดักที่ทำข้อมูลหายเงียบ

1. ดึงข้อมูลได้สูงสุด 1,000 แถวต่อครั้ง
เกินจากนั้นหายไปเฉยๆ ไม่มี error · ตารางสิทธิ์ของเราโตเกิน 1,000 แถวแล้วครั้งหนึ่ง → แถวที่เพิ่มทีหลังหายจากระบบ = ตั้งสิทธิ์ถูกแล้วแต่ปุ่มไม่โผล่ หาสาเหตุอยู่หลายวัน
ทางแก้: แบ่งดึงทีละหน้า และ ต้องสั่งเรียงลำดับ (order) ให้ครบทุกครั้ง ไม่งั้นหน้า 1 กับหน้า 2 ไม่ต่อกัน
2. สิทธิ์ปฏิเสธการแก้/ลบ = "สำเร็จ 0 แถว ไม่มี error"
มีแต่การ เพิ่มแถว เท่านั้นที่ฟ้องกลับมา · การแก้และลบที่ถูกปฏิเสธจะเงียบสนิท
ทางแก้: ปุ่มที่ผลลัพธ์สำคัญ ให้ต่อท้ายด้วย .select('id') แล้วนับแถวที่ได้กลับมา — ได้ 0 แถว = ยังไม่สำเร็จ ห้ามขึ้นข้อความสีเขียว
หลักการเดียวที่ครอบทั้ง 3 ข้อ: ห้ามล้มเหลวเงียบ — ระบบที่บอกว่า "สำเร็จ" ทั้งที่ล้มเหลว อันตรายกว่าระบบที่พังดังๆ เพราะไม่มีใครไปตามแก้

RLS — ด่านความปลอดภัยของตาราง

-- เปิดด่านให้ตาราง (ค่าเริ่มต้นของ Supabase คือ "เปิดแล้ว") alter table daily_logs enable row level security; -- ★ เปิดด่านแล้วยังไม่เขียนกฎ = ไม่มีใครเห็นอะไรเลย แม้แต่ตัวเอง -- กฎที่ 1: คนที่ล็อกอินแล้ว อ่านได้ทุกแถว create policy "read for logged-in" on daily_logs for select to authenticated using (true); -- กฎที่ 2: คนที่ล็อกอินแล้ว เพิ่มแถวได้ create policy "insert for logged-in" on daily_logs for insert to authenticated with check (true);
⚠️ อาการที่มือใหม่เจอ 100%: "โค้ดถูกทุกอย่าง แต่ตารางว่างเปล่า" → เกือบทุกครั้งคือลืมเขียนกฎ RLS · เช็คได้ที่แท็บ Network ใน DevTools — ถ้าได้ข้อมูลกลับมาเป็นลิสต์ว่าง ทั้งที่ในตารางมีข้อมูล = ใช่เลย
⚠️ บทเรียนราคาแพงของเรา: เคยไล่เปลี่ยนกฎหลายตารางพร้อมกันให้ "ปลอดภัยขึ้น" โดยไม่ดูว่าฝั่งไหนเรียกใช้ — ผลคือข้อมูลหายทั้งระบบ ต้องย้อนคืนฉุกเฉิน · แก้กฎสิทธิ์ทีละตาราง แล้วทดสอบทีละตัวเสมอ

ต้องทำได้

  • เลือกวันงาน + กะ
  • กรอก ไลน์ / จำนวนดี / จำนวนเสีย / หมายเหตุ

  • ยังไม่กรอกไลน์ = กดบันทึกไม่ได้
  • บันทึกล้มเหลว = ขึ้นข้อความสีแดง ห้ามเงียบ
  • ลบ = ถามยืนยันก่อน

7 กับดักที่ทำระบบพัง เรียงตามความเจ็บ

กับดักอาการที่เห็นวิธีกัน
ใช้เวลาสากลหาวันที่ข้อมูลลงผิดวันช่วงตี 0–7ใช้ฟังก์ชันวันงานกลางตัวเดียวทั้งระบบ
ไม่เช็ค error ตอนเขียนข้อมูลขึ้น "สำเร็จ" แต่ไม่มีอะไรถูกบันทึกครอบทุกจุดเขียนด้วยตัวเช็คกลาง
ดึงข้อมูลเกิน 1,000 แถวข้อมูลหายเงียบ ไม่มี errorแบ่งดึงเป็นหน้า + สั่งเรียงลำดับให้ครบ
สิทธิ์ในฐานข้อมูลไม่ตรงกับปุ่มบนจอกดปุ่มได้ แต่ข้อมูลไม่เปลี่ยนกฎในฐานข้อมูลอ้างคีย์สิทธิ์เดียวกับปุ่ม
คำตอบเก่ามาทับจอใหม่สลับกะเร็วๆ แล้วเห็นข้อมูลผิดกะใส่ตัวยกเลิกก่อนเขียนค่าลงจอ
วาง hook ผิดที่จอแดงทั้งหน้าตัวตรวจในขั้นตอน build จับให้ตั้งแต่ในเครื่อง
สูตรเดียวกันอยู่หลายที่สองหน้าโชว์ตัวเลขไม่ตรงกันย้ายเข้าไฟล์กลาง ใช้ที่เดียว
สังเกตว่า 5 ใน 7 ข้อ "ไม่มี error" — ระบบยังทำงานอยู่ ดูปกติทุกอย่าง แต่ข้อมูลผิด · นี่คือบั๊กประเภทที่แพงที่สุด เพราะกว่าจะรู้ตัวก็ตัดสินใจผิดไปหลายรอบแล้ว

4 หลักคิดที่ใช้ตัดสินใจได้ทุกครั้ง

1. ของอย่างเดียวกัน ต้องมีที่อยู่ที่เดียว
สูตรคำนวณ · รายชื่อไลน์ · เลขฟอร์ม · นิยาม "วันงาน" — ก๊อปไปวางที่สองเมื่อไหร่ วันหนึ่งมันจะไม่ตรงกัน แล้วไม่มีใครรู้ว่าอันไหนถูก
2. เก็บเป็นข้อมูล ดีกว่าฝังในโค้ด
ถามตัวเองว่า "ผู้ใช้อยากเปลี่ยนเองมั้ย" — ถ้าใช่ ทำเป็นตารางให้เขาแก้เอง · ทุกอย่างที่ฝังในโค้ด = ทุกการเปลี่ยนต้องรอโปรแกรมเมอร์
3. ห้ามล้มเหลวเงียบ
พังแล้วบอกดังๆ ดีกว่าพังแล้วเงียบ · ผู้ใช้ที่เห็นข้อความแดงจะโทรมาถาม — ผู้ใช้ที่เห็นข้อความเขียวปลอมๆ จะเชื่อไปอีก 3 เดือน
4. คิดเผื่อวันที่ต้องถอยกลับ
ก่อนแก้อะไรใหญ่ ถามว่า "ถ้าพังจะถอยยังไง" · เพิ่มคอลัมน์ใหม่ให้มีค่าตั้งต้น · แก้ทีละอย่าง ไม่แก้ 5 อย่างในครั้งเดียว — ไม่งั้นพังแล้วไม่รู้ว่าตัวไหนทำ

ใช้ AI ช่วยเขียนโค้ด — 5 กฎ

1. บอกบริบทให้ครบ ก่อนสั่งงาน
"เขียนหน้าบันทึกยอดผลิต" → ได้ของมั่ว · "เขียนหน้าบันทึกยอดผลิต ใช้ React + Supabase ตาราง daily_logs มีคอลัมน์… วันงานตัดที่ 08:00" → ได้ของที่ใช้ได้จริง
2. ขอทีละชิ้น อย่าขอทั้งระบบ
ขอทีเดียว 500 บรรทัด = อ่านไม่ไหว ตรวจไม่ได้ พังแล้วหาไม่เจอ · ขอทีละฟังก์ชัน แล้วรันดูทุกครั้ง
3. โค้ดที่ AI เขียน ยังเป็นความรับผิดชอบของคุณ
มันแต่งชื่อฟังก์ชันที่ไม่มีอยู่จริงได้ · เดาชื่อคอลัมน์ผิดได้ · รันจริงทุกครั้งก่อนเชื่อ — ไม่มีทางลัดตรงนี้
4. ระวังจุดที่มันชอบพลาดเป็นพิเศษ
เรื่องวันที่/เขตเวลา · การเช็ค error · สิทธิ์การเข้าถึง — 3 เรื่องนี้ต้องอ่านเองทุกบรรทัด เพราะเป็นเรื่องเฉพาะของแต่ละที่ ที่ AI ไม่มีทางรู้
5. ให้มันอธิบาย จนคุณเข้าใจ
ถามว่า "บรรทัดนี้ทำอะไร ทำไมต้องมี" · ถ้ายังอธิบายให้คุณเข้าใจไม่ได้ อย่าเพิ่งเอาโค้ดนั้นไปใช้ — โค้ดที่ไม่มีใครเข้าใจ คือหนี้ที่ต้องจ่ายวันหน้า

  • เป้า: คล่องเรื่องกรอก-เก็บ-แสดง

  • เป้า: ทำระบบที่คนอื่นใช้จริงได้ 1 ระบบ

  • เป้า: ดูแลระบบที่คนอื่นก็แก้ต่อได้
