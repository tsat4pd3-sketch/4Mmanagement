## 1. โจทย์

วันนี้เอกสาร PE (PFMEA/PFC/CP) กับปัญหาที่เกิดจริง **เดินคนละทาง**:

```
ปัญหาเกิด → NCR → 8D → ปิด → จบ           ← ไม่มีอะไรย้อนกลับไปที่เอกสาร
PFMEA/PFC/CP → ตั้งไว้ตอนออกแบบ → นิ่ง      ← ไม่รู้ว่าที่คาดไว้ตรงกับของจริงไหม
```

ผลคือตอบคำถามที่สำคัญที่สุด 2 ข้อไม่ได้:
1. **"อาการนี้เคยคาดไว้ใน PFMEA มั้ย"** — ถ้าเคย = รู้แล้วแต่คุมไม่อยู่ (แก้ที่การควบคุม)
   ถ้าไม่เคย = ตอนออกแบบมองไม่เห็น (แก้ที่วิธีทำ FMEA)
2. **"แก้แล้วเอกสารตามไปแก้หรือยัง"** — IATF 16949 §10.2.3/10.2.4 บังคับว่าต้องตาม
   และ auditor ถามข้อนี้ทุกครั้ง

**สิ่งที่อยากได้:** ปิด 8D แล้ว **ระบบย้อนกลับไปชี้เองว่าต้องแก้เอกสารตัวไหน บรรทัดไหน**
รวมถึง **พาร์ทอื่นที่มีอาการเดียวกันแต่ยังไม่เกิด** (yokoten / horizontal deployment)

## 2. ของที่มีอยู่แล้ว — ต่อวงจรได้เลย ไม่ต้องสร้างใหม่

| มีแล้ว | ใช้ทำอะไรในลูปนี้ |
|---|---|
| `qa_ncr` (part_no · line_name · defect_desc · root_cause · severity) | ต้นทางอาการ + กุญแจหาชุดเอกสาร |
| `qa_capa` (D1–D8 + effectiveness + status open→in_progress→verify→closed) | ตัวจุดลูป — ปิดเมื่อไหร่ = เวลาที่ต้องแก้เอกสาร |
| `pe_doc_sets.part_no` / `line_name` | จับคู่กับ NCR ได้ตรงๆ |
| `pe_fmea_items` (failure_mode · causes · prevention · detection_ctrl · S/O/D) | ปลายทางที่ต้องแก้ |
| `pe_cp_items` (product_char · method · frequency · control_method · reaction_plan) | ปลายทางฝั่งการควบคุม |
| **`pe_doc_revisions.ref_kind` (`claim`/`ncr`/`defect`/`downtime`/`mtn`) + `ref_id`** | **ช่องผูกต้นเหตุ — ออกแบบรอไว้ตั้งแต่แรก ยังไม่มีใครเขียน** |
| `noteSimilarity()` (`src/utils/textCluster.js`) | จับคู่ข้อความไทย-อังกฤษแบบทน (3-gram + Jaccard) |
| แผง 3 ขาใน `/order-trace` | **ตรรกะการ map อาการ→PFMEA ทำเสร็จแล้ว** ย้ายมาใช้ซ้ำได้ |
| `/improvements` วัดผลก่อน/หลังจาก `defect_logs` | ใช้ตรวจ D8 effectiveness ด้วยข้อมูลจริง ไม่ใช่คำพูด |

**สรุป: ~70% ของชิ้นส่วนมีแล้ว** ที่ขาดคือ "ตารางเชื่อม + จอ worklist + กติกาปิดงาน"

## 3. โครงที่เสนอ

### 3.1 ตารางเดียวที่ต้องเพิ่ม — `pe_change_requests`

**ทำไมต้องเป็นตารางแยก ไม่ใช่คอลัมน์ใน `qa_capa`:**
1 CAPA แตะได้**หลายบรรทัด**ของหลายเอกสาร (FMEA 3 แถว + CP 2 จุด + เพิ่ม OP 1 ขั้น)
และต้นเหตุไม่ได้มีแค่ CAPA — เคลมลูกค้า / NCR / ของเสียซ้ำ / ใบซ่อม ก็จุดลูปนี้ได้เหมือนกัน

```sql
create table pe_change_requests (
  id            uuid primary key default gen_random_uuid(),
  -- ต้นเหตุ (ใช้ vocabulary เดียวกับ pe_doc_revisions.ref_kind — ห้ามตั้งชุดใหม่)
  ref_kind      text not null check (ref_kind in ('capa','ncr','claim','defect','downtime','mtn','audit','other')),
  ref_id        text not null,
  -- ปลายทาง: ชี้บรรทัดที่ต้องแก้ (อย่างใดอย่างหนึ่ง) หรือชี้ชุดเอกสารกว้างๆ ถ้ายังไม่รู้บรรทัด
  set_id        uuid not null references pe_doc_sets(id) on delete cascade,
  doc_type      text not null check (doc_type in ('fmea','cp','pfc')),
  process_id    uuid references pe_processes(id) on delete set null,
  fmea_item_id  uuid references pe_fmea_items(id) on delete set null,
  cp_item_id    uuid references pe_cp_items(id) on delete set null,
  -- 3 ขาแบบ 8D — บอกว่าแก้เพราะอะไร (ตรงกับ D4 ที่ Ford/GM บังคับ)
  leg           text check (leg in ('occurrence','detection','systemic')),
  origin        text not null default 'suggested' check (origin in ('suggested','manual')),
  confidence    numeric,          -- คะแนนจับคู่ 0-1 (เฉพาะ suggested) — โชว์ให้คนตัดสิน
  proposal      text not null,    -- ระบบร่างให้ / คนพิมพ์เอง
  status        text not null default 'proposed'
                check (status in ('proposed','accepted','applied','rejected')),
  reject_reason text,             -- ปฏิเสธต้องมีเหตุผล (auditor ถามว่าทำไมไม่แก้)
  revision_id   uuid references pe_doc_revisions(id) on delete set null,  -- ผูกตอน applied
  decided_by    text, decided_at timestamptz,
  created_at    timestamptz default now()
);
```

**หัวใจ: `status` เดินทางเดียว `proposed → accepted → applied` (หรือ `rejected` พร้อมเหตุผล)**
`applied` ต้องมี `revision_id` เสมอ — แปลว่า "แก้เอกสารจริงและออก revision แล้ว" ไม่ใช่แค่ติ๊ก

### 3.2 คอลัมน์ที่ต้องเติมของเดิม

| ตาราง | เพิ่ม | เหตุผล |
|---|---|---|
| `qa_capa` | `part_no` · `line_name` | **CAPA ที่ไม่ได้ผูก NCR ตอนนี้ไม่รู้ว่าเป็นของพาร์ทไหนเลย** → หาเอกสารไม่เจอ |

## 4. "Reverse engineer" ทำงานยังไง — 3 ขาแบบ 8D

ตอน CAPA ขึ้นสถานะ `verify` (ส่งตรวจประสิทธิผล) ระบบ **เสนอ** รายการแก้เอกสาร:

### ขา ① Occurrence — "ทำไมถึงเกิด" → PFMEA `causes` / PFC
```
qa_capa.d4_root_cause  ──noteSimilarity──▶  pe_fmea_items.causes (ของพาร์ทนั้น)
   เจอ ≥ threshold  → "สาเหตุนี้มีใน FMEA แล้ว แต่ Occurrence = 3 ทั้งที่เกิดจริง N ครั้ง/เดือน
                        → เสนอทบทวน O และ prevention"
   ไม่เจอ           → 🔴 "สาเหตุนี้ไม่เคยอยู่ใน PFMEA — ต้องเพิ่มแถวใหม่"
qa_capa.d5_corrective ที่มีคำว่า เพิ่มขั้นตอน/ติดตั้ง/เปลี่ยนวิธี → เสนอแก้ PFC (`pe_processes`)
```

### ขา ② Detection — "ทำไมหลุดออกไป" → Control Plan + PFMEA `detection_ctrl`
```
NCR.source = 'customer'  → 🔴 หลุดถึงลูกค้า = ระบบตรวจไม่ทำงาน
   ▶ หา pe_cp_items ของ OP ที่เกี่ยวข้อง แล้วถามตรงๆ:
     · มีจุดควบคุมของลักษณะนี้ไหม → ไม่มี = เสนอเพิ่มจุดควบคุม
     · มีแต่ frequency หลวมไป (EVERY LOT ทั้งที่ควรทุกชิ้น) = เสนอถี่ขึ้น
     · มีแต่ method เป็น VISUAL ทั้งที่ต้องวัด = เสนอเปลี่ยนวิธี
   ▶ ผูกกับ `qa_inspection_items` ด้วย — ใบตรวจจริงต้องมีจุดนี้ ไม่ใช่มีแค่ในกระดาษ CP
```

### ขา ③ Systemic — **ตัวที่คุ้มที่สุด (yokoten)**
```
failure_mode ที่เพิ่งเกิด  ──ค้นข้าม pe_doc_sets ทุกพาร์ท──▶  พาร์ทอื่นที่มี failure_mode คล้ายกัน
   ▶ "อาการนี้มีใน PFMEA ของอีก 4 พาร์ท ที่ยังใช้ control แบบเดิม — จะ deploy การแก้ไปด้วยไหม"
   ▶ กรองด้วย: กระบวนการเดียวกัน (pe_processes.name) หรือ เครื่องเดียวกัน (machine_no)
```
งานนี้คนไม่ทำเพราะต้องเปิดเอกสารทุกพาร์ทมาไล่อ่าน — **เครื่องทำได้ในวินาทีเดียว**
และเป็นสิ่งที่ IATF เรียกว่า *lessons learned* (§10.2.3) ที่แทบไม่มีโรงงานไหนทำจริง

## 5. กติกาที่ห้ามพลาด

| # | กติกา | เหตุผล |
|---|---|---|
| 1 | **ระบบ "เสนอ" เท่านั้น คนกดยืนยันถึงแก้เอกสาร — ห้าม auto-write PFMEA/CP** | เอกสารควบคุม · แก้เองอัตโนมัติ = ประเด็น audit ทันที · กฎเดิมของโปรเจค ("AI intake ต้องให้คนกดยืนยันก่อน insert") |
| 2 | **`confidence` ต้องโชว์บนจอ** และเรียงจากมั่นใจสุด | คนต้องรู้ว่าอันไหนระบบเดา อันไหนชัด |
| 3 | **จับคู่ไม่ได้ ≠ ไม่ต้องแก้** — ต้องขึ้น "ไม่พบใน PFMEA" เป็น**สัญญาณของตัวเอง (สีแดง)** | นั่นคือคำตอบที่มีค่าที่สุดในทั้งลูป: *ตอนออกแบบไม่เคยคิดถึงเลย* |
| 4 | **ปฏิเสธต้องมีเหตุผล** (`reject_reason` บังคับ) | auditor ถามว่า "ทำไมเคสนี้ไม่แก้เอกสาร" ต้องตอบได้ |
| 5 | **ปิด CAPA (D8) ต้องตอบเรื่องเอกสารก่อน** — แต่เป็น *soft gate*: เลือก "แก้แล้ว" / "ไม่เกี่ยว + เหตุผล" ได้ **ห้ามบังคับให้ revise เสร็จก่อนถึงปิดได้** | บังคับแข็งไป คนจะเลี่ยงด้วยการไม่เปิด CAPA เลย (แย่กว่าเดิม) |
| 6 | **`applied` ต้องมี `revision_id` จริง** ไม่ใช่ติ๊กเปล่า | ผูกกับ `pe_doc_revisions` ที่มีอยู่แล้ว → ประวัติ rev เล่าเรื่องเองว่าเกิดจากเคลมใบไหน |
| 7 | **effectiveness วัดจาก `defect_logs` จริง ไม่ใช่ข้อความ** | ใช้สูตรก่อน/หลังของ `/improvements` ที่พิสูจน์แล้ว · ไม่ลด = เสนอเปิด 8D ใหม่ **ห้ามปิดเงียบ** |
| 8 | **ห้ามตั้ง vocabulary ใหม่** — `ref_kind` ใช้ชุดเดียวกับ `pe_doc_revisions` | สองชุดเมื่อไหร่ = join ข้ามฝั่งไม่ได้ (บทเรียนเดิม: ทีมช่างเคยเก็บชื่อ/รหัสปนกัน) |

| 6 | **ต้องบอก `total` ไม่ใช่แค่ top 3** — คำว่า "นัท" มี 35 ข้อในเอกสารเดียว แสดง 3 ข้อโดยไม่บอกว่ามีทั้งหมดเท่าไหร่ = ดูแม่นเกินจริง |
| 7 | `ref_*/set_id` ในคอมเมนต์ JSDoc **ปิด block comment ก่อนเวลา** (`*/`) — build พังแบบ parse error อ่านไม่ออก |

**ผลทดสอบกับเอกสารจริง 306** (FMEA 255 · CP 178 แถว):
· เคลม "นัทไม่มี" → เจอจุดควบคุม **"QUANTITY OF NUT" ที่ OP 130 PROJECTION WELD NUT (70%)** + ชี้ว่า OP 270 FINAL INSPECTION มี 5 จุดแต่ไม่มีจุดไหนแตะอาการนี้
· "งานเป็นครีบ / คมตัดแม่พิมพ์สึก" → เจอ **"- End cut burr" ที่ OP 100 BENDING (55%)**
· "สีลอกหลังอบ" (อาการที่ไม่มีในเอกสาร) → 🔴 **"ไม่เคยอยู่ใน PFMEA — ต้องเพิ่มแถวใหม่"** ถูกต้อง

### ⚠️ ตรวจจับเคลมซ้ำ — ต้องมี 2 ระดับ เกณฑ์เดียวแยกไม่ได้
วัดกับข้อความเคลมจริงแบบไทยแล้ว **คะแนนชนกันพอดี**:

| คู่ข้อความ | คะแนน | ความจริง |
|---|---|---|
| "นัทไม่มี…" ↔ "นัทหาย 2 ตัว" | 0.56 | ✅ ซ้ำจริง |
| "นัทไม่มี…" ↔ **"นัทเชื่อมเยื้องศูนย์"** | 0.56 | ❌ **คนละอาการ** |
| "งานเป็นครีบที่ขอบ" ↔ "มีครีบที่ขอบชิ้นงาน" | 0.69 | ✅ ซ้ำจริง (ข้อความตรงด้วย) |

ลดเกณฑ์ = เตือนผิด · ขึ้นเกณฑ์ = พลาดของจริง → **แยกตาม `via` แทน**
· `both` (ข้อความ + กลุ่มคำตรงกัน) = **🔁 ซ้ำแน่** (แดง — 8D ก่อนไม่ได้ผล)
· `group` (ตรงแค่กลุ่มคำ) = **❓ อาจซ้ำ ต้องเปิดดูเอง** (เหลือง)

**ห้ามยุบสองระดับนี้เป็นระดับเดียว** — เคลมซ้ำเป็นข้อกล่าวหาที่หนัก (แปลว่ามาตรการเดิมล้มเหลว)
เตือนพร่ำเพรื่อแล้วคนจะเลิกสนใจทั้งระบบ

## 10. เฟส 4 — วัดประสิทธิผลจากข้อมูลจริง (2026-08-18)

**IATF 16949 §10.2.4 บังคับให้ "ทวนสอบว่ามาตรการแก้ไขได้ผลจริง"** — เดิมระบบมีแค่ช่องข้อความ
`qa_capa.effectiveness` ที่คนพิมพ์เอง auditor ถามว่า *"รู้ได้ยังไงว่าได้ผล"* แล้วตอบไม่ได้
เพราะไม่มีตัวเลขผูกกับข้อความนั้น

| ไฟล์ | หน้าที่ |
|---|---|
| `supabase/migrations/20260818_capa_effectiveness.sql` (**apply แล้ว 2026-08-19**) | คอลัมน์ `d6_effective_from` / `eff_window_days` / `eff_defect_type_id`+`_label` / `eff_verdict` / `eff_measured_at` / `eff_snapshot` |
| `src/utils/capaEffect.js` | **สูตรทั้งหมด (pure เทสได้)** — `effectWindow` · `splitBeforeAfter` · `judgeEffect` · `effectSummaryText` |
| `src/components/CapaEffectiveness.jsx` | แผงในโมดัล 8D — ตั้งค่าการวัด + แถบเทียบก่อน/หลัง + ปุ่มเติมผลลงช่องประสิทธิผล |

### วิธีวัด
```
ก่อน = [pivot − window, pivot)     หลัง = [pivot, min(วันนี้, pivot + window))
หารด้วย "จำนวนวันที่ไลน์ผลิตจริง" (นับจาก production_sessions) ไม่ใช่วันปฏิทิน
```
เกณฑ์: ลด ≥50% = ได้ผล · 20-50% = ดีขึ้นบางส่วน · <20% = ยังไม่ได้ผล · เพิ่มขึ้น = แย่ลง

### ⚠️ กฎเหล็กของเฟสนี้
| # | กฎ | ทำไม |
|---|---|---|
| 1 | **pivot = `d6_effective_from` (วันที่มาตรการมีผลจริง) ไม่ใช่ `closed_at`** | ใบมักถูกปิดหลังมาตรการมีผลไปแล้วหลายสัปดาห์ (รอผลติดตาม) → ใช้วันปิดจะวัดคร่อมช่วงผิด |
| 2 | **"วัดไม่ได้" ต้องเป็นคำตอบของตัวเอง ห้ามกลายเป็น "ไม่ได้ผล"** | `too_early` / `no_baseline` / `no_data` / `no_pivot` แยกจาก `not_effective` เด็ดขาด (หลักเดียวกับ OEE: ประเมินไม่ได้ = null ห้ามคืน 0) |
| 3 | **ต้องหารด้วยวันผลิตจริง** | ไลน์หยุด 5 วันแล้วของเสียเป็น 0 **ไม่ได้แปลว่ามาตรการได้ผล** — หารด้วยวันปฏิทินจะให้คำตอบเท็จ |
| 4 | **`afterDays < 5` = ยังวัดไม่ได้ ห้ามตัดสิน** | 1-2 วันที่บังเอิญดี/บังเอิญแย่ พลิกคำตอบได้ทั้งใบ |
| 5 | **ก่อนหน้าไม่มีของเสียเลย = `no_baseline` ไม่ใช่ "ได้ผล"** | ไม่มีฐานเทียบ = เกณฑ์ที่ตั้งไว้อาจไม่ตรงกับอาการที่เคลม (ต้องไปแก้เกณฑ์ ไม่ใช่ฉลอง) |
| 6 | **ปิดใบแล้ว = อ่านค่าที่ stamp ห้ามคำนวณใหม่** | ของเสียถูกแก้/เพิ่มทีหลังได้ — คำนวณสดจะทำให้ใบที่ปิดไปแล้วเปลี่ยนคำตอบเองเงียบๆ (หลักเดียวกับ OEE ที่ stamp ตอนปิดกะ) |
| 7 | **เตือนดังตอนปิด แต่ไม่บล็อก + stamp ผลไว้เสมอ** | บล็อกแข็ง คนจะเลี่ยงด้วยการไม่ตั้งค่าการวัดเลย ซึ่งแย่กว่า · แต่ "ปิดทั้งที่ตัวเลขไม่ลด" ต้องเห็นได้ตลอดไปทั้งในลิสต์และ dashboard |
| 8 | **ระบบไม่ auto-reopen ใบ** | รายงานตัวเลข คนเป็นผู้ตัดสิน (หลักเดียวกับตัวเสนอแก้เอกสารในเฟส 2) |
