# 🧭 Navigation & IA Review — เทียบมาตรฐาน Web App ระดับสากล

> รีวิวเรื่อง **"หน้าที่กดจาก sidebar" vs "แท็บข้างในหน้า"** และการจัดระเบียบโครงเว็บ
> สถานะ: **รายงานผลตรวจ + ข้อเสนอ ยังไม่ได้แก้โค้ด** · ตรวจ 2026-08-06 (ตัวเลขวัดจากโค้ดจริง)
> อ่านคู่กับ `docs/UI-CONVENTIONS.md` (กติกา UI) และ `docs/ENGINEERING-PRINCIPLES.md` (หลักการแก้)

## 0. สรุปให้ผู้บริหาร (TL;DR)

ระบบ**ทำงานได้ครบและลึกมาก** แต่ "การจัดระเบียบหน้า" ยังเป็นแบบ **โตตามงานที่เข้ามา** ไม่ใช่แบบที่ออกแบบไว้ล่วงหน้า
ผลคือ 5 อาการที่ web app ระดับสากลไม่ทำกัน:

| # | อาการ | ความรุนแรง | วัดได้ |
|---|---|---|---|
| 1 | **แท็บในหน้าไม่ผูกกับ URL** — refresh/แชร์ลิงก์/ปุ่ม Back แล้วเด้งกลับแท็บแรก | 🔴 สูง | 17 หน้ามีแท็บ · deep-link ได้ **แค่ 3** |
| 2 | **ไม่มี component กลางของ Tab / หัวหน้า / breadcrumb** — แต่ละหน้าวาดเอง | 🔴 สูง | มุมโค้งแท็บ 7 / 8 / 12 / var(--radius-lg) ปนกัน · มีหัวเรื่อง `<h2>` แค่ **22 จาก 56 หน้า** |
| 3 | **เรื่องเดียวเข้าได้หลายทางแบบไม่ตั้งใจ** — เป็นทั้ง route และแท็บของหน้าอื่น | 🟠 กลาง | `/daily-pm` `/lpa` `/pokayoke` (แท็บใน Daily Checker) · `/linesetup` (แท็บใน Layout Setup) |
| 4 | **เมนู 51 รายการใน 8 หมวด ไม่มีช่องค้นหา** — ของใหม่หาไม่เจอ ต้องจำว่าอยู่หมวดไหน | 🟠 กลาง | 51 เมนู · ไม่มี command palette / search |
| 5 | **"ทางกลับ" เป็น ad-hoc** — ใช้ `?from=factory-map` เฉพาะบางเส้นทาง ที่เหลือกดกลับแล้วหลง | 🟡 ต่ำ-กลาง | มี 2 เส้นทางที่ทำ · ที่เหลือไม่มี breadcrumb |

> **แก่นของปัญหา:** ระบบยังไม่มี "กติกาว่าเมื่อไหร่ของควรเป็นหน้า เมื่อไหร่ควรเป็นแท็บ"
> พอไม่มีกติกา แต่ละงานก็ตัดสินใจเองตามสะดวก → ผู้ใช้ต้องจำเป็นรายหน้า แทนที่จะเดาได้จากรูปแบบเดียวกัน

## 1. สิ่งที่ระบบนี้ทำได้ดีอยู่แล้ว (อย่าไปรื้อ)

- **จัดหมวดเมนูตามสายงานจริง** (ภาพรวม → ฝ่ายผลิต → วิเคราะห์ → คน → Store → ซ่อมบำรุง → QA → ตั้งค่า) ตรงกับวิธีคิดของคนโรงงาน ไม่ใช่ตามโครงสร้างเทคนิค
- **สิทธิ์เข้าหน้าเป็น data-driven** (`role_permissions`) — เมนูที่ไม่มีสิทธิ์หายไปเอง ไม่ต้องแก้โค้ด
- **DeptHub เป็นหน้า Hub** พร้อมชิปเมนูที่ดึงจาก `NAV_ITEMS` อัตโนมัติ (single source เดียวกับ sidebar) — อันนี้ถูกหลักมาก
- **หมวดใน sidebar พับ/กางได้ + โฟกัสหมวดอัตโนมัติเมื่อเข้าจาก Hub**
- โครง URL อ่านรู้เรื่อง (`/mtn-repair`, `/daily-report`) ไม่ใช่ `/page?id=17`

## 2. ปัญหาเชิงลึก + มาตรฐานที่ควรยึด

### 2.1 🔴 URL ต้องเป็น "สถานะของหน้า" (URL as state)

**มาตรฐานสากล:** ทุกอย่างที่ผู้ใช้ *มองเห็นว่าตัวเองอยู่ตรงไหน* ต้องอยู่ใน URL — แท็บ, ฟิลเตอร์หลัก, รายการที่เปิดอยู่
เพื่อให้ **แชร์ลิงก์ได้ · bookmark ได้ · refresh แล้วอยู่ที่เดิม · ปุ่ม Back ของ browser ทำงานตามที่คาด**

**ของเรา:** 17 หน้ามีแท็บ แต่ deep-link ได้แค่ `DailyChecker` (`?tab=`), `PMCheckData`, `DeptDashboard` (`?dept=`)

ผลกระทบจริงกับหน้างาน:
- หัวหน้าส่ง LINE ว่า "ดูคลังอะไหล่หน่อย" → ส่งลิงก์ `/mtn-repair` ปลายทางเปิดมาเจอแท็บรายการ MO ต้องกดหาเอง
- อยู่แท็บ KPI แล้ว refresh (จอ TV/เน็ตสะดุด) → เด้งกลับแท็บแรก
- กด Back หวังกลับแท็บก่อนหน้า → เด้งออกจากหน้าไปเลย

**ที่ควรเป็น:** `?tab=spare` `?tab=kpi` ทุกหน้าที่มีแท็บ (ค่า default = แท็บแรก, ค่าที่ไม่รู้จัก = fallback แทนจอว่าง)

---

### 2.2 🔴 ต้องมี component กลาง: `PageHeader` + `Tabs` + `Breadcrumb`

**ของเรา:** ไม่มีเลยสักตัว — แต่ละหน้าวาดหัวเรื่องและแท็บเอง จึงได้:
- มุมโค้งแท็บ 7 / 8 / 12 / `var(--radius-lg)` ปนกันในหน้าที่ผู้ใช้เปิดสลับกันทั้งวัน
- หัวเรื่องหน้า: มี `<h2>` แค่ **22 จาก 56 หน้า** → บางหน้าเปิดมาไม่รู้ว่าตัวเองอยู่หน้าอะไร
- ปุ่ม action ชิดขวาบางหน้าอยู่บน บางหน้าอยู่ล่าง บางหน้าลอย

**มาตรฐาน:** ทุกหน้าควรมีโครงหัวเดียวกัน
```
[ breadcrumb: หมวด › หน้า › แท็บ ]
[ 🔧 ชื่อหน้า        คำอธิบายสั้น 1 บรรทัด ]   [ ปุ่มหลักของหน้า ][ 🔄 ]
[ แท็บ 1 | แท็บ 2 | แท็บ 3 ]                     ← ผูก ?tab=
```
ทำเป็น component เดียว (`<PageHeader title tabs value onChange actions/>`) แล้วไล่เปลี่ยนทีละหน้า
**ได้ 3 อย่างพร้อมกัน:** หน้าตาเท่ากันทุกหน้า · deep-link ฟรี · แก้ที่เดียวมีผลทั้งระบบ

---

### 2.3 🟠 กติกา "หน้า" vs "แท็บ" — ต้องตัดสินด้วยเกณฑ์ ไม่ใช่ความรู้สึก

**เกณฑ์ที่เสนอ (ตัดสินได้ใน 10 วินาที):**

| ให้เป็น **หน้า (route)** เมื่อ | ให้เป็น **แท็บในหน้า** เมื่อ |
|---|---|
| เป็น "งาน" คนละงาน คนละคนทำ | เป็น "มุมมองของเรื่องเดียวกัน" (ลิสต์ / KPI / ตั้งค่าของเรื่องนั้น) |
| ต้องแชร์ลิงก์/bookmark เป็นเอกเทศ | คนที่ใช้แท็บนี้คือคนกลุ่มเดียวกับแท็บอื่น |
| มีสิทธิ์เข้าถึงต่างจากพี่น้อง | ใช้สิทธิ์ชุดเดียวกัน (หรือ gate ด้วย `can()` รายแท็บ) |
| อยู่ในเมนู sidebar ได้อย่างมีเหตุผล | ถ้าใส่ sidebar แล้วเมนูจะรก/ซ้ำซ้อน |

**เอามาจับของจริง:**

| หน้า | แท็บที่มี | ตรงเกณฑ์ไหม | ควรทำอะไร |
|---|---|---|---|
| `/mtn-repair` | รายการ MO · KPI · คลังอะไหล่ · ผังคลัง · ข้อมูลหลัก | ✅ เรื่องเดียวกัน (งานซ่อมบำรุง) | **คงไว้** + เพิ่ม `?tab=` · "ข้อมูลหลัก" ควรเป็นแท็บท้ายสุดเสมอ (setup แยกจากงานประจำวัน) |
| `/qa` | 6 แท็บ (Dashboard/ใบตรวจ/SPC/NCR/CAPA/เครื่องมือวัด) | ⚠️ 6 แท็บเริ่มเยอะ | คงไว้ก่อน + `?tab=` · ถ้าเกิน 7 ให้ยุบเป็นกลุ่ม |
| `/daily-checker` | AM · Poka-Yoke · LPA | ✅ ทำถูกแล้ว (มี `?tab=`) | **ใช้เป็นต้นแบบ** — แต่ **route เดิม `/daily-pm` `/lpa` `/pokayoke` ยังอยู่** ⇒ ของเดียวเข้าได้ 2 ทาง |
| `/layout-setup` | ภาพรวมโรงงาน · ผลิต · MTN · Store/AMR | ✅ | `/linesetup` ยังเป็น route ซ้อนอยู่ |
| `/report` + `/skills-report` | 7 แท็บ + 3 แท็บ (component เดียวกัน `mode`) | ⚠️ หน้าเดียวถูกหั่นด้วย prop | ควรเป็น `/report?tab=` กับ `/skills?tab=` ที่ชัดเจน |

**ข้อสรุปข้อนี้:** โครงแท็บของเรา**ถูกแล้วโดยหลัก** ปัญหาอยู่ที่ (ก) ไม่ผูก URL (ข) route เก่ายังค้างเป็นทางเข้าที่ 2

---

### 2.4 🟠 route ซ้ำซ้อน = ผู้ใช้เห็นระบบไม่ตรงกัน

`/daily-pm` `/lpa` `/pokayoke` `/linesetup` **ไม่อยู่ใน sidebar แต่เข้าได้** และเนื้อหาเดียวกับแท็บในหน้ารวม

ปัญหาที่ตามมา: bookmark เก่าของหัวหน้าคนหนึ่งพาไปหน้าเดี่ยว (ไม่มีแท็บพี่น้อง) อีกคนเข้าจากเมนูเห็นหน้ารวม → **สองคนคุยกันคนละภาพ**

**มาตรฐาน:** route เก่าที่ยุบไปแล้วให้ **redirect** ไปที่แท็บของหน้ารวม (`/daily-pm` → `/daily-checker?tab=pm`) ไม่ใช่ render หน้าซ้ำ
(ลิงก์เก่ายังใช้ได้ + ทุกคนเห็นภาพเดียวกัน — นี่คือวิธีที่ web app มาตรฐานทำเวลารวมหน้า)

---

### 2.5 🟠 เมนู 51 รายการ ต้องมีทางลัด

8 หมวด 51 เมนู — โครงยังโอเค แต่**ไม่มีช่องค้นหา** คนใหม่/คนที่ใช้ไม่บ่อยต้องไล่กางทีละหมวด

**มาตรฐาน:** ช่องค้นหาเมนูบนหัว sidebar (พิมพ์ "ซ่อม" → เจอทุกเมนูที่เกี่ยว) + คีย์ลัด `Ctrl/⌘ + K`
ข้อมูลมีอยู่แล้วใน `NAV_ITEMS` + กรองสิทธิ์ด้วย `navItemsForGroups` → **ทำได้โดยไม่แตะโครงเมนู**

เสริม: **"เข้าล่าสุด/ใช้บ่อย"** 3-5 รายการบนสุดของ sidebar (เก็บใน localStorage) ช่วยคนที่วนอยู่ 3 หน้าเดิมทั้งวัน

---

### 2.6 🟡 Breadcrumb + ทางกลับ

ตอนนี้ทางกลับเป็น ad-hoc: `?from=factory-map` (ผังรวม → Dashboard/ผัง MTN) ส่วนเส้นทางอื่นไม่มี

**มาตรฐาน:** breadcrumb บนหัวหน้า `หมวด › หน้า › แท็บ` — ได้ทั้งบอกตำแหน่งและเป็นทางกลับในตัว
ข้อมูลมีครบแล้วใน `NAV_ITEMS` (`group` + `label`) → **generate อัตโนมัติได้ ไม่ต้องมานั่งใส่ทีละหน้า**

---

### 2.7 🟡 หน้าใหญ่เกินขนาด (สัญญาณว่าควรแตก)

`DailyReport` 6,335 บรรทัด · `Report` 4,247 · `Management` 3,284 · `Dashboard` 2,791

ไม่ใช่เรื่อง IA โดยตรง แต่โยงกัน: หน้าที่ใหญ่ขนาดนี้มัก**ยัดหลายงานไว้ในไฟล์เดียว** ทำให้แตกเป็นแท็บ/หน้าย่อยที่ deep-link ได้ยาก
**ไม่ต้องรีบรื้อ** (เสี่ยงสูง ของใช้งานอยู่ทุกกะ) แต่เวลาแตะหน้าพวกนี้ครั้งหน้า ให้ค่อยๆ ดึงส่วนที่เป็น "แท็บ" ออกเป็น component ไฟล์แยก

## 3. แผนแก้ที่เสนอ (เรียงตามคุ้ม ÷ เสี่ยง)

| เฟส | ทำอะไร | ได้อะไร | เสี่ยง | ขนาด |
|---|---|---|---|---|
| **1** | สร้าง `src/components/PageHeader.jsx` (หัวเรื่อง + คำอธิบาย + ปุ่ม + แท็บ ผูก `?tab=` + breadcrumb อัตโนมัติจาก NAV_ITEMS) | มีมาตรฐานกลางให้ใช้ | ต่ำ (ของใหม่ ไม่แตะของเดิม) | เล็ก |
| **2** | ไล่เปลี่ยน 17 หน้าที่มีแท็บให้ใช้ `PageHeader` — **ทีละ 3-4 หน้า ปล่อยใช้จริงก่อนค่อยทำชุดถัดไป** | deep-link/refresh/Back ใช้ได้ทุกหน้า + หน้าตาเท่ากัน | กลาง (แตะหลายหน้า → ทำทีละชุด) | กลาง |
| **3** | route เก่าที่ยุบแล้ว → **redirect** เข้าแท็บ (`/daily-pm` → `/daily-checker?tab=pm`, `/lpa`, `/pokayoke`, `/linesetup`) | ทุกคนเห็นภาพเดียวกัน · ลิงก์เก่าไม่ตาย | ต่ำ | เล็ก |
| **4** | ค้นหาเมนู + `Ctrl/⌘+K` + "ใช้บ่อย" ใน sidebar | 51 เมนูหาเจอใน 2 วินาที | ต่ำ | เล็ก-กลาง |
| **5** | หน้าที่ยังไม่มีหัวเรื่อง (34 หน้า) ใส่ `PageHeader` ให้ครบ | ทุกหน้าบอกได้ว่าตัวเองคือหน้าอะไร | ต่ำ | กลาง |

**เฟส 1+3 ทำได้ทันทีและแทบไม่มีความเสี่ยง** — แนะนำเริ่มตรงนี้

## 4. กติกาที่จะเพิ่มเข้า `docs/UI-CONVENTIONS.md` (เมื่อเริ่มทำเฟส 1)

1. **ทุกหน้าต้องขึ้นด้วย `<PageHeader>`** — ห้ามวาดหัวเรื่อง/แท็บเอง
2. **หน้าที่มีแท็บต้องผูก `?tab=`** — refresh/แชร์ลิงก์/Back ต้องอยู่แท็บเดิม · ค่าที่ไม่รู้จัก = แท็บแรก (ห้ามจอว่าง)
3. **แท็บ ≤ 7 ตัว** — เกินกว่านั้นให้ยุบกลุ่มหรือแยกหน้า
4. **แท็บ "ตั้งค่า/ข้อมูลหลัก" อยู่ท้ายสุดเสมอ** และ gate ด้วย `can()` (งานประจำวันมาก่อน setup)
5. **ยุบหน้าเข้าเป็นแท็บเมื่อไหร่ ต้อง redirect route เดิม** ห้ามปล่อยให้ render ซ้ำสองทาง
6. **หน้าที่ถูกเปิดจากหน้าอื่น ต้องมีทางกลับ** (breadcrumb หรือปุ่ม ← ระบุปลายทาง)

## 5. สิ่งที่ **ไม่ควร** ทำ (กันแก้เกินจำเป็น)

- ❌ **อย่ารื้อหมวดเมนูใหม่** — หมวดปัจจุบันตรงกับสายงานจริงและคนชินแล้ว (เพิ่งจัดใหม่ 2026-07-20)
- ❌ **อย่าเปลี่ยน URL ของหน้าที่คนใช้อยู่** โดยไม่ทำ redirect — bookmark/ลิงก์ใน LINE จะตายหมด
- ❌ **อย่ายุบ 17 หน้าให้เหลือ 5 หน้ายักษ์** เพราะ "ดูสะอาด" — หน้าใหญ่แก้ยากและ deep-link ยากกว่าเดิม
- ❌ **อย่าทำ 17 หน้าพร้อมกันในคอมมิทเดียว** — ทีละ 3-4 หน้า ปล่อยใช้จริง แล้วค่อยชุดถัดไป (blast radius)
