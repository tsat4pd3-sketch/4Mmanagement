## 4. โมเดลข้อมูลที่เสนอ

### 4.1 ใบขอเติม (หัวใจของลูป)

ใช้ **`wip_replenish_requests`** ต่อ (มีอยู่แล้ว · 0 แถว จึงเปลี่ยนโครงได้อิสระ)
**ห้ามสร้างตารางใบขอเติมตัวที่ 2** — จะซ้ำกับ `rack_requests` / `material_requests` ที่มีอยู่แล้ว

**timestamp ที่ต้องมี (ตัวที่ทำให้วัด lead time ได้):**

| คอลัมน์ | ขั้น | ความหมาย |
|---|---|---|
| `requested_at` | 4 | หัวหน้าไลน์กดยืนยันความต้องการ ← **จุดเริ่มนับเวลา + คีย์เรียงคิว** |
| `picked_at` | 5-6 | สโตร์สแกน mat + lot ครบ = เริ่มจัดของ |
| `delivered_at` | 7 | สแกน QR จุดส่งงาน |
| `received_at` | 8 | ผลิตกดยืนยันรับ ← **จุดจบ · lead time = received_at − requested_at** |

**สถานะ:** `suggested → requested → picking → delivered → received`
บวก **`hold`** (พักไว้ก่อน — กลับมาได้) และ `cancelled` (ยกเลิกจริง — ไม่ใช้พาร์ทนี้แล้ว)

> ⚠️ **แยก 4 หมุดนี้ให้ครบตั้งแต่แรก ห้ามเก็บแค่ "เริ่ม-จบ"**
> ไม่งั้นตอบได้แค่ "ช้า" แต่ตอบไม่ได้ว่า **ช้าตรงไหน** (รอสโตร์หยิบ? รอรถ? รอผลิตมาเซ็นรับ?)
> ซึ่งเป็นคำถามเดียวที่ทำให้เอาไปแก้ได้จริง

> ⚠️⚠️ **`suggested` กับ `hold` ต้องมีจริงในสถานะ ห้ามยุบ** (user เคาะ §6.4)
> · `suggested` = ระบบเสนอแล้วแต่ **ยังไม่มีคนกดยืนยัน** → **สโตร์ต้องมองไม่เห็น** (ไม่ใช่คำสั่ง)
> · `hold` = หัวหน้าเห็นแล้วเลือก "พักไว้ก่อน" → ความต้องการยังอยู่ ต้องกลับมาเตือนได้เอง
>   **ห้ามใช้ `cancelled` แทน** และ **ห้ามให้หายจากจอ** — ของที่ถูกพักแล้วมองไม่เห็น
>   คือต้นเหตุของ "ลืมเบิกจนไลน์หยุด" ที่ระบบนี้มีไว้กัน
> · `requested_at` stamp ตอนกดยืนยัน (`suggested`/`hold` → `requested`) **ไม่ใช่ตอนระบบเสนอ**
>   ไม่งั้น lead time ที่วัดได้จะรวมเวลาที่หัวหน้ายังไม่ได้ตัดสินใจ = โทษสโตร์ทั้งที่ยังไม่ถึงคิวเขา

### 4.3 lot / id (ขั้น 6) — **มีอยู่แล้วบนกระดาษ ไม่ต้องสร้างใหม่** (user ส่งรูป TAG CARD 27/08)

⚠️ **แก้ข้อสรุปเดิมของ doc นี้** — ตอนแรกเขียนว่า "ทั้งระบบไม่มี lot เลย ⇒ ชิ้นใหญ่สุด เลื่อนไปเฟสท้าย"

| ช่องบนบัตร | ตัวอย่างจริง | ใช้กับขั้น |
|---|---|---|

| `BATCH NO.` | `0059589821` | **6** — คือ **lot** |
| `ID NO` | `12039567` | **6** — id ต่อภาชนะ (ไม่ซ้ำ) |

⇒ **ขั้น 6 ไม่ใช่ "สร้างระบบ lot ใหม่" แต่คือ "เก็บสิ่งที่พิมพ์อยู่แล้วตอนสแกน"**
ยิงบัตรใบเดียวได้ครบทั้ง mat + lot + id + จำนวน → **เลื่อนขั้น 6 ขึ้นมาทำพร้อมขั้น 5 ได้**

> #### 🔴 กฎเหล็ก — ตัวเลขในบาร์โค้ด ≠ ตัวเลขที่พิมพ์ ต้อง normalize เสมอ
> บัตรมี **4 บาร์โค้ดต่อใบ** และค่าที่ยิงออกมามี `0` นำหน้า + หลักต่อท้าย:
> ```
> ยิงได้ 03214027426763  →  PROD.NO. 32140274267   (0 + เลข + 63)
> ยิงได้ 012039567013    →  ID NO    12039567      (0 + เลข + 013)
> ยิงได้ 012039754042    →  ID NO    12039754      (0 + เลข + 042)
> ยิงได้ 012039460035    →  ID NO    12039460      (0 + เลข + 035)
> ```
> เทียบตรงตัว = **ไม่มีวันแมตช์** (กับดักเดียวกับ `normCode` ของ QR อุปกรณ์ที่เคยเจอ)
> - ตัวอ่านต้อง **ทนทุกบาร์โค้ดบนบัตร** แล้วบอกว่าแมตช์กับช่องไหน — ห้ามบังคับว่าต้องยิงตัวไหน
>   (หลักเดียวกับ `qrCode.js` ที่ทนทั้ง QR ระบบ / เลขเปล่าจากปืนยิง / QR แบบ URL)
> - แมตช์ไม่ได้ = **บอกว่ายิงอะไรมาและเทียบกับอะไรไม่ตรง** ห้ามเงียบหรือขึ้นแค่ "ผิด"
>
> **⚠️ ยังไม่ยืนยัน 2 ข้อ — ต้องถามก่อนเขียน parser:**
> 1. **บาร์โค้ดตัวไหนคือ MAT.NO.** — จาก layout บาร์โค้ดกลางขวาอยู่เหนือ `MAT.NO.` (คู่กับบาร์โค้ดกลางซ้ายที่อยู่เหนือ `PROD.NO.`)
>    แต่อ่านตัวเลขใต้บาร์โค้ดจากรูปไม่ออก · **ถ้า MAT.NO. ไม่มีบาร์โค้ด ขั้น 5 ต้องเปลี่ยนวิธี**
>    (ยิง P/NO แล้ว map กลับเป็น mat ผ่าน `dr_products.p_no` — ระบบมี `matResolve.js` ทำอยู่แล้ว)
> 2. **หลักต่อท้าย (63/013/042/035) คืออะไร** — check digit หรือลำดับ?
>    ถ้าเป็น check digit ตัดทิ้งได้ · ถ้าเป็นลำดับภายใน batch ต้องเก็บด้วย

> **วิธียืนยันที่เร็วที่สุด: ให้สโตร์เอาปืนยิงทีละบาร์โค้ดลงช่อง Notepad แล้วส่งข้อความที่ได้มา**

| จำนวนบาร์โค้ด | **4** | **1** (Batch No. เท่านั้น) |
| ชื่อช่อง | `MAT.NO.` `BATCH NO.` `ID NO` `PROD.NO.` | `Material No.` `Batch No.` `Prod. Order` `Batch Ref.` `Material Batch` |
| เลขวัสดุ | `10100335` = **MAT SAP ของเรา** | `1790001164` = **เลขของ supplier ไม่ใช่ MAT SAP เรา** |
| ช่องที่เรามีค่าแต่ไม่มีในบัตรเรา | — | `TS 498 / YS 383 / %EL 40` (mech. property = mill cert) · `Material Batch` (heat เหล็ก) · ตรา QA/IQA |

⇒ **ยิงบาร์โค้ดของ supplier แล้วระบบไม่รู้ว่าเป็น MAT ตัวไหนของเรา**

**ผลต่อขั้น 5-6 — แตกเป็น 2 กรณี:**

| ของที่สโตร์ส่งเข้าไลน์ | บัตรที่ติดมา | สแกนได้เลยไหม |
|---|---|---|
| **2xx** พาร์ทผลิตเอง | TAG CARD ของเรา | ✅ รูปแบบเดียว |
| **3xx** พาร์ทซื้อนอก | บัตร supplier | ❌ หลากหลาย |
| **5xx** วัตถุดิบ | บัตร supplier | ❌ หลากหลาย |

> #### 🔴 ทางแก้ที่เลือก — **re-tag at receiving** (ติดบัตรของเราทับตอนรับเข้าคลัง)
> ของเข้าสโตร์ → ยิง/คีย์บัตร supplier **ครั้งเดียวที่ประตูคลัง** → ระบบออก **บัตรของเราเอง**
> (MAT SAP + container id + จำนวน + lot ของ supplier ที่คัดลอกมา) → แปะทับ
> - **ปลายทางทุกจุดสแกนรูปแบบเดียว** ไม่ต้องเขียน parser ต่อ supplier
> - **ได้ traceability กลับไปหา supplier ฟรี** — `Batch No.` / `Material Batch` / `TS·YS·%EL`
>   คือ mill cert ที่มีค่าจริงกับงานเหล็ก · **ตอนนี้ข้อมูลนี้หายที่หน้าประตูคลังทุกวัน**
> - ปิด traceability gap ที่ CLAUDE.md จดไว้แล้ว ("การรับวัตถุดิบเข้า Store ไม่มีช่อง lot no./heat no. ของ supplier")
>
> **ทางเลือกที่ไม่เอา: parser ต่อ supplier** — แต่ละเจ้าเปลี่ยนฟอร์มเมื่อไหร่ก็พังเงียบ ตามแก้ไม่จบ
>
> **⚠️ นี่เป็นการเปลี่ยนกระบวนการของสโตร์ (เพิ่มงานที่จุดรับของ) ต้องให้ user เคาะก่อน**
> และต้องมีเครื่องพิมพ์ป้ายที่จุดรับ · ระบบมีโครงพิมพ์ป้าย QR อยู่แล้วที่ `/qr-labels` + `rack_center`
>
> **รูปแบบบัตรของเราที่เสนอ:** QR `ESM:C:<container_uuid>` — เข้ารหัสแค่ **ตัวตนภาชนะ**
> แล้วให้ DB เก็บ mat / lot / qty / supplier batch (pattern เดียวกับ `ESM:M:<uuid>` ของเครื่องจักร
> ที่เข้ารหัส uuid แล้ว lookup ที่เหลือ — **ห้ามยัดข้อมูลลง QR** ไม่งั้นแก้จำนวนทีต้องพิมพ์ป้ายใหม่)

**⚠️ ยังไม่รู้: ของที่สโตร์ส่งเข้าไลน์ เป็น 2xx กี่ % · 3xx/5xx กี่ %**
ถ้า 2xx เป็นส่วนใหญ่ → เฟส 3 ทำเฉพาะบัตรเราไปก่อนได้ผลเยอะแล้ว
ถ้า 3xx/5xx เป็นส่วนใหญ่ → ต้องทำ re-tag ก่อนถึงจะสแกนได้จริง · **ต้องวัดก่อนตัดสินใจลำดับ**
```sql
-- DR: สัดส่วนประเภทพาร์ทที่ผลิตต้องใช้ (แยกด้วยเลขตัวแรกตาม matPrefix.js)
select left(b.mat_no,1) prefix, count(distinct b.mat_no) parts
from production_sessions ps
join prod_orders o on o.session_id = ps.id and o.status <> 'cancelled' and o.qty > 0
join dr_products p on p.mat_no = o.mat_no
join bom_items b on b.product_id = p.id and b.is_active
where ps.work_date >= current_date - 7 group by 1 order by 2 desc;
```

### 4.4 QR จุดส่งงาน (ขั้น 7)

- ตัวจุดเก็บที่ไหน: `storage_zones` มีอยู่แล้ว · หรือ `transport_nodes` (kind `stop`) ที่ใช้กับรอบขนส่ง

## 6. ข้อสรุปที่ user เคาะแล้ว (2026-08-27) — เป็นสัญญาของงานนี้

### 6.1 โหมดของไลน์: **มีรอบ active = กำหนดรอบ · ไม่มีรอบ = ส่งตามคำขอ**

ทำได้ทั้ง 2 อย่างพร้อมกันโดย **ไม่เพิ่มคอลัมน์/master ใหม่** — โหมด derive จากของที่มีอยู่:
มีแถวใน `kanban_delivery_rounds` ที่ `is_active` = โหมดรอบ · ไม่มี = ส่งตามคำขอ
สลับโหมดทำที่ 📦 Line Stock → ⏰ รอบจัดส่ง (UI เดิม)

- **พักรอบที่ seed ไว้ทั้งหมดแล้ว** — `20260827_park_seeded_delivery_rounds.sql` (snapshot ก่อน ไม่ลบ)
- ⚠️ **ห้ามเพิ่ม `production_lines.store_mode`** — ไลน์อยู่ Main รอบอยู่ DR อ่านข้ามไม่ได้
  และเป็นความจริง 2 แหล่งที่ drift ทันที (ตั้ง mode=round แต่ไม่มีรอบ = ตอบอะไรไม่ได้)

### 6.2 ขั้น 3 แจ้งใคร: **หัวหน้ากลุ่มรายไลน์ = คนตัดสิน · หัวหน้าแผนก = รับรู้**

> *"หัวหน้ากลุ่มรายไลน์เพื่อให้ตัดสินใจต่อว่าจะเบิกงานเพิ่มหรือหยุดพักไว้ก่อน ในเคสจะเปลี่ยนรุ่น
>  หัวหน้าแผนกแค่รับรู้เฉยๆ ก็ได้"*

**2 บทบาทนี้ต้องแยกให้ขาดทั้งการแจ้งและปุ่ม:**

| | หัวหน้ากลุ่ม (leader) | หัวหน้าแผนก (supervisor) |
|---|---|---|
| ได้รับแจ้ง | ✅ | ✅ |
| ปุ่ม "เบิก / พักไว้ก่อน" | ✅ **คนตัดสิน** | ❌ ดูอย่างเดียว |

- ใช้ `notify_recipients` เดิม: `inapp_roles = {leader, supervisor}` + **`inapp_match_section = true`**
  (ไม่งั้นหัวหน้าไลน์ A เด้งเพราะไลน์ B ถึง min — เคสเดียวกับที่เคยแก้ที่ DeptHub telemetry)
- ปุ่มคุมด้วย permission key **ห้ามคุมด้วย role array** (กฎ C ของโปรเจค)
- ⚠️ วัดความถี่ก่อนเปิดกระดิ่ง: ถึง min เป็น **เหตุการณ์ต่อพาร์ท** → เคลียร์ backlog ทีเดียวระเบิดได้
  (บทเรียน `shipping_shipped` 338 ครั้งใน 23 นาที) → **ยุบเป็น 1 ข้อความ/ไลน์/รอบสแกน ห้ามยิงรายพาร์ท**

### 6.3 ค่า min ต่อไลน์ ตั้งโดย: **หัวหน้าไลน์ + หัวหน้าแผนกฝ่ายผลิต** (ไม่ใช่ Planning)

คนที่ยืนอยู่หน้าไลน์รู้ว่าพื้นที่วางได้กี่กล่องและกินเร็วแค่ไหน — Planning ไม่รู้
⇒ สิทธิ์เขียน `line_part_levels` = `leader` + `supervisor` (+admin/manager) · **scope ตามไลน์ของตัวเอง**

### 6.4 ขั้น 4 = ระบบเสนอ คนกดยืนยัน — และ **"ไม่เบิก" คือ hold ไม่ใช่ reject**

> *"ให้คนตัดสินใจซะหน่อย ว่าจะเบิกมาเติมเต็มหรือปล่อยหมด แต่ **ไม่ใช่การปฏิเสธนะ เหมือน hold ไว้ก่อน**"*

**นี่คือข้อที่เปลี่ยนโมเดลข้อมูล ไม่ใช่แค่ถ้อยคำ:**

- ระบบ **ห้าม auto-สร้างใบเบิก** (กฎเดิม: ระบบเสนอ คนตัดสิน)
- `hold` **ไม่ใช่สถานะปลายทาง** — ความต้องการยังอยู่ ต้องกลับมาเตือนเองเมื่อ
  (ก) ยอดลดต่ำลงอีก (ข) ขึ้นกะใหม่ (ค) หัวหน้ากดปลด hold เอง
- ห้ามใช้ `cancelled` แทน hold · `cancelled` = ยกเลิกจริง (เปลี่ยนรุ่นแล้วไม่ใช้พาร์ทนี้อีก)
- **hold ต้องเห็นบนจอเสมอ** พร้อมเหตุผล + เวลาที่ hold — ของที่ถูกพักแล้วหายจากสายตา
  คือต้นเหตุของ "ลืมเบิกจนไลน์หยุด" ซึ่งเป็นสิ่งที่ระบบนี้มีไว้กัน
  (precedent: ใบ 4M ที่ถูกตีกลับต้องขึ้นชิป ✏️ ต้องแก้ ในลิสต์กะ ไม่ใช่หายเงียบ)
