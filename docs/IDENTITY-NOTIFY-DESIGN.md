## 2. ตอบข้อกังวล "ฐานพนักงานจะปนกับ user ไหม"

**ไม่ปนครับ — คนละตาราง คนละหน้าที่ ผูกกันด้วย FK เส้นเดียว** ("ปน" ที่ต้องกลัวมี 2 แบบ แยกให้ออกก่อน)

| | `employees` (ทะเบียนคน) | `profiles` (บัญชีใช้งาน) |
|---|---|---|
| ตอบคำถามว่า | **คนนี้คือใคร สังกัดไหน** | **บัญชีนี้ล็อกอินแล้วทำอะไรได้** |
| ใครดูแล | หัวหน้าแผนก / ฝ่ายบุคคล (`/operator`, `/register`) | admin (`/add-user`) |
| ขนาดจริงวันนี้ | **212 คน** (active) | **94 บัญชี** |
| มีบัญชีล็อกอินไหม | **ส่วนใหญ่ไม่มี** — 191/212 คนไม่เคยมีบัญชี (พนักงานหน้าไลน์) | ทุกแถว = 1 บัญชี |
| เก็บอะไร | ชื่อ · รหัสพนักงาน · แผนก/ส่วนงาน/ไลน์/ทีม · รูป · สกิล · วันเริ่มงาน | อีเมล · role · scope · ลายเซ็น |
| ผูกกันยังไง | `profiles.employee_id → employees.id` (unique, nullable) | ← เส้นเดียวเท่านั้น |

⇒ **"ปนแบบที่ 1 — ทะเบียนคนปนกับบัญชี" ไม่เกิด** การผูกคือชี้ว่า *บัญชีนี้คือคนคนนี้* ไม่ได้ย้ายข้อมูล
มารวมกัน · คนที่ไม่มีบัญชียังอยู่ในทะเบียนเฉยๆ เหมือนเดิม · บัญชีที่ไม่ใช่คน (จอ TV) ยังไม่ต้องผูก

⇒ **"ปนแบบที่ 2 — คนทางอ้อมปนกับคนหน้าไลน์"** *อันนี้เกิดจริงถ้าทำมักง่าย* และคือสิ่งที่ต้องออกแบบ
(§5) — ใส่ QA/ธุรการ/วิศวกรเข้าทะเบียนเฉยๆ โดยไม่มีธงแยก = ตัวเลข**กำลังคน/เข้างาน/turnover เพี้ยนทันที**

## 4. รากปัญหาเชิงโครงสร้าง — 3 แกนที่ต้องแยกกัน

### 4.1 วันนี้เป็นยังไง

| แกน | ควรอ่านจาก | สถานะ |
|---|---|---|
| **ตัวตน** — คนนี้คือใคร สังกัดแผนก/ส่วนงาน/ไลน์/ทีมไหน | `employees` ← `profiles.employee_id` | 🔴 ครอบคลุมแค่สายผลิต ⇒ 78% ของบัญชีไม่มีตัวตน |
| **สิทธิ์** — ทำอะไรได้ | `role` + `role_permissions` | 🟢 โครงถูกแล้ว (รายละเอียด → `PERMISSIONS-DESIGN.md`) |
| **ผู้รับแจ้งเตือน** — ใครควรรู้เรื่องนี้ | `notification_rules` | 🔴 เลือกได้จริงแค่ `role` |

### 4.2 จุดที่ทำให้ "สิทธิ์กระทบแจ้งเตือน" (คำถามตรงของ user)

`notification_rules.inapp_roles` = **แกนเดียวที่ใช้ได้จริง** (แกนส่วนงานใช้ได้บางส่วน · แกนแผนกตายสนิท)
⇒ เกิดผลข้างเคียง 2 ทางที่ไม่มีใครตั้งใจ:

- **ให้ role เพื่อ "เข้าหน้า" = สมัครรับแจ้งเตือนของ role นั้นไปด้วย** — ธุรการที่ได้ role `mtn`
  เพื่อเปิดหน้าใบซ่อม จะได้ทุกขั้นของทุกใบซ่อมไปด้วยโดยไม่มีใครกดอะไรเลย
- **อยากให้ใครได้ยินเรื่องหนึ่ง ต้องยกชุดสิทธิ์ให้เขา** — ซึ่งเป็นการแจกสิทธิ์เกินความจำเป็นเพื่อแลกกับ
  การแจ้งเตือน (ผิดหลัก least privilege และเป็นเหตุผลที่ระบบสิทธิ์ดู "มั่ว" ทั้งที่ตัวมันไม่ผิด)

> 🔑 **หลักที่จะยึด: "ทำอะไรได้" กับ "ควรรู้เรื่องอะไร" เป็นคนละคำถาม ต้องตั้งแยกกัน**
> หัวหน้าที่ลาออกจากทีมซ่อมยังต้องกดปุ่มซ่อมได้ (สิทธิ์) แต่ไม่ต้องได้ยินทุกใบแล้ว (ผู้รับ) — และกลับกัน
> จอ TV ต้อง *เห็น* ทุกอย่าง แต่ไม่ต้อง *ได้ยิน* อะไรเลย

## 5. แกนตัวตน — ทางเลือก (ต้องให้ user เลือก)

### ทางเลือก A (แนะนำ) — ทะเบียนคนครอบคลุมทุกคนที่มีบัญชี + ธง `staff_kind`

```sql
alter table employees add column staff_kind text not null default 'direct';
-- 'direct'   = พนักงานสายผลิต (นับกำลังคน/เช็คชื่อ/OEE manpower) — 212 คนเดิมทั้งหมด
-- 'indirect' = พนักงานทางอ้อม (QA/PE/ธุรการ/สโตร์/ช่างสำนักงาน) — ไม่นับกำลังคนไลน์
```

- แถวเดิม 212 คน = `direct` อัตโนมัติ ⇒ **วันที่ apply ไม่มีตัวเลขไหนขยับแม้แต่นิดเดียว**
- คนทางอ้อมเพิ่มเข้ามาเป็น `indirect` (`line_id` null · `section` null = "ขึ้นตรงฝ่าย" ตาม
  `ORPHAN_SECTION` ที่มีอยู่แล้ว หรือใส่ section ถ้าสังกัดจริง) แล้วบัญชีของเขาผูกได้ = `person`
- `shared` เหลือเฉพาะสิ่งที่ **ไม่ใช่คน**: `Display` · `Display.MonitorPD3` · `Room Monitor …` ·
  บัญชีกลางประจำกะ (`maintenance` · `warehouse1` · `delivery1` …) ≈ **13 ใบตามดีไซน์เดิม**

| ข้อดี | ข้อเสีย / ที่ต้องระวัง |
|---|---|
| ตัวกรองแผนก/ส่วนงานของแจ้งเตือนใช้ได้ทั้งระบบทันที (78% → ~0% ที่ไม่มีตัวตน) | **ต้องไล่ใส่ธง `staff_kind` ที่ทุกจอที่นับคน** ไม่งั้นกำลังคนเพี้ยน (§7 blast radius) |
| ตอบ "ใครเป็นใคร" ได้ที่เดียวทั้งบริษัท ไม่ต้องเดา | ต้องมีคนคีย์ข้อมูลคนทางอ้อม ~30-40 คนครั้งเดียว (ทำจาก `/add-user` ได้ ไม่ต้องไปอีกหน้า) |
| ลายเซ็น/ผู้อนุมัติ/mention/รูปโปรไฟล์ ใช้แหล่งเดียวกันหมด | `employee_id_code` ของคนทางอ้อมอาจไม่มีรหัสจริง → ต้องตกลงรูปแบบ (§8 Q3) |

### ทางเลือก B — คงทะเบียน = สายผลิต แล้วเพิ่มประเภทบัญชีที่ 3

`account_kind` เพิ่มค่า `'person_external'` = คนจริงที่ไม่มีในทะเบียนพนักงาน (กรอกชื่อ/แผนก/ส่วนงานในบัญชีเอง)

| ข้อดี | ข้อเสีย |
|---|---|
| งานน้อยสุด ไม่กระทบตัวเลขกำลังคนเลย | **ขัดกฎเหล็กที่เพิ่งตั้งไปเอง** (2026-08-21 "ตัวตนอยู่ที่ `employees`") — กลับไปให้ admin กรอกสังกัดเอง = เคสทีมสลับกันจะกลับมาอีกรอบ |
| | ตัวกรองแผนกยังตายสำหรับ 30 บัญชีนี้ (ต้องเพิ่มคอลัมน์ `department` ซ้ำใน `profiles` = ข้อมูลซ้ำ 2 ที่อีกครั้ง) |
| | ลายเซ็น/mention/สกิล ของคนกลุ่มนี้ยังไม่มีที่อยู่ |

### ทางเลือก C — แยกตาราง `people` ใหม่ (คนทั้งองค์กร) แล้ว `employees` เหลือแค่ข้อมูลสายผลิต

สะอาดที่สุดในแง่โมเดล แต่ต้องย้าย 292 แถว + แก้ read path ทุกหน้าที่อ่าน `employees` (**36 จุดใน src/**)
+ FK จากสกิล/เช็คชื่อ/OJT/LPA/BBS **ประเมิน: งานใหญ่ ความเสี่ยงสูง ผลลัพธ์เท่ากับ A** ⇒ ไม่แนะนำตอนนี้

> **ที่แนะนำ: A** — เพราะได้ผลเท่า C ด้วยความเสี่ยงระดับ B และไม่ขัดกฎที่ตั้งไว้เมื่อ 21/08

## 6. แกนผู้รับแจ้งเตือน — ออกแบบ

### 6.1 เพิ่มแกนที่ขาด (ให้เลือกผู้รับได้โดยไม่ต้องยุ่งกับ role)

| แกน | เก็บที่ | ทำไมต้องมี |
|---|---|---|
| แผนก `inapp_depts` | **มีแล้ว** — รอแค่ตัวตนครบ (§5) | "งานซ่อมของ JIG MTN" ไม่ควรเด้งหา DIE MTN |
| **ทีมช่าง** `inapp_mtn_teams` (ใหม่) | `profiles.mtn_teams[]` (13 คนตั้งไว้แล้ว) | ช่าง 7/13 คนไม่มี section ตามดีไซน์ ⇒ **แกน section กรองช่างไม่ได้เลย** ต้องมีแกนของตัวเอง |
| **ไลน์** `inapp_match_line` (ใหม่) | `employees.line_id` / `profiles.line_id` | หัวหน้าไลน์ควรได้เฉพาะไลน์ครอบครัวตัวเอง ไม่ใช่ทั้ง section |
| **สมัคร/ถอนรายคน** `notification_subscriptions` (ใหม่) | ตารางใหม่ `(user_id, event_key, mode)` | ให้คน **เพิ่มตัวเอง**เข้าเรื่องที่ตัวเองรับผิดชอบ และ **ถอนตัวเอง**ออกจากเรื่องที่ไม่เกี่ยว โดยไม่ต้องแตะ role ของใคร — นี่คือตัวตัดขาด "สิทธิ์ ↔ แจ้งเตือน" จริงๆ |

### 6.2 แก้ fail-open (ต้องทำคู่กับ §5 เสมอ ห้ามทำก่อน)

วันนี้: *ไม่มี scope = ได้ทุกส่วนงาน* — ปลอดภัยแบบผิดทาง (กันเงียบด้วยการส่งเกิน)
ที่ควรเป็น: **ไม่มี scope = ไม่ส่ง + ขึ้นป้ายเตือนที่ `/add-user` และ `/notification-config` ว่า
"บัญชีนี้ยังไม่มีส่วนงาน จะไม่ได้รับ N เรื่องที่กรองตามส่วนงาน"**

> 🔴 **ห้ามสลับ 2 อย่างนี้พร้อมกันโดยไม่มีป้ายเตือน** — ปิด fail-open ตอนที่ตัวตนยังไม่ครบ =
> คนที่เคยได้ยินจะเงียบทันทีโดยไม่มีใครรู้ (กฎ ENGINEERING-PRINCIPLES: ห้ามล้มเหลวเงียบ)
> ลำดับที่ปลอดภัย: ผูกตัวตนครบ → เปิดจอ preview ให้เห็นว่าใครจะหาย → ค่อยปิด fail-open

### 6.3 ความหมายของ "ส่วนงานของฉัน" ต้องเหลือนิยามเดียว

`notify_recipients()` ต้องตีความ scope **แบบเดียวกับ `effectiveSections()`** (รวมข้อยกเว้น
`FACTORY_WIDE_ROLES` — QA ทั้งโรงงาน) ⇒ ทางที่ยั่งยืน: ทำฟังก์ชัน SQL `effective_sections(uid)`
ให้เป็นคู่แฝดของ JS แล้วให้ทั้ง RLS และแจ้งเตือนเรียกตัวเดียวกัน
**มีเทสล็อกว่า 2 ฝั่งให้ผลตรงกัน** (เคสตัวอย่าง: qa/PD3 → ทั้งโรงงาน · supervisor/PD3 → [PD3])

## 7. ลำดับเฟส · blast radius · rollback

| เฟส | ทำอะไร | กระทบอะไร | rollback |
|---|---|---|---|
| **0** วัดซ้ำ | รันคิวรี §10 เก็บ baseline ก่อนแตะอะไร | ไม่มี | — |
| **1** ตัวตน (ไม่เปลี่ยนพฤติกรรม) | `staff_kind` (default `direct`) · ปุ่ม **"+ เพิ่มคนนี้เข้าฐานพนักงาน"** ใน `/add-user` · ช่องค้น normalize ช่องว่าง · เปลี่ยนคำปุ่มเป็น **"บัญชีกลาง/อุปกรณ์ (ไม่ใช่คน)"** + เตือนเมื่อชื่อดูเป็นคน · ผูกคืน 14 บัญชีที่ชื่อตรง | **ศูนย์** — เพิ่มคอลัมน์ที่ default = ค่าเดิม + แก้ฟอร์ม | drop column · revert commit |
| **2** ไล่ใส่ธง `staff_kind` ที่จุดนับคน | `Checkin.jsx` · `WorkforceInsight.jsx` · `Management.jsx` · `stdManpower` · `/operator` | 🟡 ต้องเทียบตัวเลขกำลังคนก่อน-หลัง ให้เท่าเดิมเป๊ะ (ยังไม่มี `indirect` สักคน ⇒ ต้องเท่าเดิมโดยอัตโนมัติ) | revert commit |
| **3** คีย์คนทางอ้อม ~30-40 คน + ผูกบัญชี | ข้อมูล ไม่ใช่โค้ด | 🟡 จอที่ลืมใส่ธงจากเฟส 2 จะเริ่มนับเกิน ⇒ **เฟส 2 ต้องจบก่อน ห้ามสลับลำดับ** | ลบแถว `indirect` |
| **4** แจ้งเตือน | แกน `mtn_teams`/line · `notification_subscriptions` · `effective_sections()` SQL · ปิด fail-open | 🔴 เปลี่ยนผู้รับจริง — ต้องมีจอ preview "ก่อน/หลัง" รายกฎ (ต่อยอด `notifReach.js`) และประกาศล่วงหน้า | `notify_recipients()` เป็น `create or replace` → คืนเวอร์ชันเดิมได้ทันที · ตารางใหม่ drop ได้ |

**จุดที่ห้ามพลาด (บทเรียนจากของเดิมในรีโป):**
- ทุก write ต้องผ่าน `checkWrite()` — RLS ปฏิเสธ UPDATE = 0 แถวไม่มี error (กฎเหล็ก DB ข้อ 1-2)
- ตารางใหม่ (`notification_subscriptions`) ต้องมี policy ครบ 4 cmd + `has_perm()` ตรงกับปุ่มบนจอ (ข้อ 3)
- `staff_kind` ที่เพิ่ม → **ต้องเพิ่มใน mock ของ `audit/crashsweep.mjs` และแถว `NULLISH()`** ไม่งั้นโค้ดสายนี้ไม่เคยถูกรันใน harness
- กฎใหม่ที่ grep ได้ (เช่น "ห้ามนับ `employees` โดยไม่กรอง `staff_kind`") → เพิ่มใน `regressionGuards.test.mjs` คอมมิทเดียวกัน

## 8. คำถามที่ user ต้องตัดสิน (ยังไม่ลงมือจนกว่าจะตอบ)

1. **แกนตัวตน เลือก A / B / C?** (แนะนำ **A**) — §5
2. **คนทางอ้อมให้ `section` ไหม?** เช่น QA 20 คน: ใส่ `section=null` ("ขึ้นตรงฝ่าย" — เห็น/ได้ยินทั้งโรงงาน)
   หรือใส่ `PD3` (ผูกกับส่วนงานที่ประจำอยู่จริง) · **ข้อนี้ตัดสินว่า §3.4 จะหายหรือไม่**
3. **รหัสพนักงานของคนทางอ้อมใช้อะไร?** รหัสจริงจาก HR / ปล่อยว่าง / ออกรหัสชั่วคราว (`IND-001`)
   — `employee_id_code` เป็น `not null` ต้องมีค่าอะไรสักอย่าง
4. **จอ TV / บัญชีกลางประจำกะ ควรได้รับแจ้งเตือนในแอปไหม?** (วันนี้ `display` มี 3 บัญชี และไม่มี scope
   ⇒ รั่วผ่านตัวกรองทุกส่วนงาน) — แนะนำ: **ไม่ส่งเลย** จอไม่มีคนอ่านกระดิ่ง
5. **ปิด fail-open เมื่อไหร่** — ทันทีที่ตัวตนครบ หรือรอให้ทุกคนตั้ง section ครบก่อน (มีจอ preview ช่วยตัดสิน)
6. **`role` ยังควรเป็นแกนผู้รับแจ้งเตือนอยู่ไหม** หลังมีแกนแผนก/ทีม/รายคนแล้ว
   — แนะนำ: **เก็บไว้เป็นค่าตั้งต้น** (ไม่งั้นต้องตั้งผู้รับใหม่ทั้ง 61 กฎ) แต่เลิกใช้เป็นแกนเดียว

## 10. คิวรีสำหรับวัดซ้ำ (MAIN · `ewhdfqwfwofivojtsizn`)

```sql
-- 3.1 สัดส่วนประเภทบัญชี
select account_kind, count(*) from profiles group by 1;

-- 3.1 บัญชี shared ที่ "น่าจะเป็นคนจริง" (มีชื่อตรงในฐานพนักงานแบบตัดช่องว่างแล้ว)
select p.full_name, p.role::text, p.position
  from profiles p
 where p.account_kind = 'shared'
   and exists (select 1 from employees e where e.is_active
                and lower(regexp_replace(e.name,'\s+','','g'))
                  = lower(regexp_replace(p.full_name,'\s+','','g')));

-- 3.2 ทะเบียนคนครอบคลุมแผนกไหนบ้าง
select coalesce(department,'(null)'), count(*) , count(*) filter (where line_id is null)
  from employees where is_active group by 1 order by 2 desc;

-- 3.3 บัญชีที่ตัวกรองแผนกเอื้อมไม่ถึง
select count(*) from profiles where employee_id is null;

-- 3.4 ใครได้รับจริง (เปลี่ยน event_key / section ได้)
select p.role::text, count(*) from notify_recipients('qa_ncr_opened','PD1') r
  join profiles p on p.id = r group by 1;
```
