# Production Plan — วางแผนการผลิต (Active Planner, 2026-07-15)

> ย้ายมาจาก `CLAUDE.md` (2026-09-03 — แยกไฟล์เพื่อลด context) · โหลด**เฉพาะเมื่อแตะโมดูลนี้** · แก้ไฟล์นี้แทน CLAUDE.md เมื่อกฎของโมดูลเปลี่ยน


หน้า `/production-plan` (หมวด **ฝ่ายผลิต** + โผล่ซ้ำใน **Logistic-แผนงาน** ผ่าน `alsoIn` — 2026-09-17) — จากยอดลูกค้า (order รายวัน + forecast รายเดือน) เทียบ **"กำลังผลิตที่ทำได้จริง"** → บอกว่าต้องเปิดกี่กะ กี่วัน วันไหนเปิด OT/กะดึก/ทำวันหยุด วันไหนไม่ต้อง เพื่อทันดิว · **เฟส 1 อ่านอย่างเดียว ไม่เขียน DB**

- **กำลังผลิต = median(ยอดดีจริงต่อกะ) ใน 60 วันล่าสุด** ต่อ (ไลน์+พาร์ท) — util กลาง `src/utils/capacityModel.js` · median ตัดค่าโดด (วันเทพ/หายนะ) + บวก OEE/เบรค/NG ไว้ในตัว · พาร์ทที่มีประวัติ < 3 กะ fallback = (นาทีกะ×60÷CT)×OEE median ของไลน์ + ติดป้าย "ข้อมูลน้อย" · เลือกโหมดวางแผน **median (สมจริง)** หรือ **P25 (ปลอดภัยไว้ก่อน)**
  - **normalize กะที่แชร์ไลน์ (2026-07-21):** กะที่พาร์ทวิ่งไม่เต็มกะ (แชร์กับพาร์ทอื่น) ทำให้ยอด/กะต่ำ → median กำลังต่ำเกิน → OT/backlog เกินจริง · ProductionPlan โหลด `opened_at`/`confirmed_at` คิด run-min ต่อ (session,mat) แล้ว: กะวิ่ง **50–90%** ของกะ → คูณกลับเป็นเต็มกะ (scale ≤2×) **cap ด้วยกำลังทฤษฎี `shift×60÷CT` กัน over-scale** (overstate = วางแผนน้อยไป อันตราย) · กะวิ่ง **<50% = ตัดทิ้ง**จาก median (สัญญาณน้อยเกิน) · ไม่มี timestamp = ใช้ค่าดิบเดิม

### 🔴 กฎเหล็ก 1 — **1 กะของสไลด์ = 7.75 ชม. (465 นาที) ไม่ใช่ 490 นาทีของแท็บรายวัน**

**ตั้งใจให้ต่าง เพราะคนละนิยาม:**
- **490** = เวลาที่เดินเครื่องได้ → ใช้ตอบ "กะนี้ทำได้กี่ชิ้น" (แผนรายวัน)
- **465** = เวลาที่ฝ่ายวางแผนใช้คิดเพดานรายเดือน (ตัดเวลาเตรียม/ส่งงานออกอีกชั้น)

  ผลรวมของคอลัมน์แยกลูกค้าต้องเท่ากับคอลัมน์ "รวมทุกลูกค้า" เสมอ

**③ ⏱️ แผง JPH — มาตรฐาน vs ของจริง** (`src/utils/jph.js` · เทส 18 เคส)

| ตัว | สูตร |
|---|---|
| มาตรฐาน | `3600 ÷ CT` |
| ควรได้ (×OEE) | `มาตรฐาน × OEE` |
| ของจริง | `ยอดต่อกะ (median ใบที่ปิดแล้ว) ÷ ชม.ทำงานสุทธิ` |

🔴 **กฎเหล็ก 1 — "ของจริง" ต้องมาจาก `est.method === 'actual'` เท่านั้น**
`estimateCapacity()` มี fallback: ใบปิด < 3 กะ ⇒ คืน `perShift` ที่คำนวณจาก **CT × OEE** แล้วตั้ง `method='ct'`
⇒ เอาค่านั้นมาเทียบกับ "ควรได้" (= std × OEE) **คือตัวเลขเดียวกัน** จอจะขึ้น "ตรงเป๊ะ 100%"
ทุกพาร์ทที่ไม่มีข้อมูล = **เทียบตัวเองกับตัวเอง** (จอโกหกแบบที่ดูไม่ออก) ⇒ ต้องคืน `actual = null`
· ProductionPlan จึงส่ง **`estOf` (est ดิบที่มี `method`)** ไม่ใช่ `perShift` — ห้ามเปลี่ยนเป็นส่งแค่ตัวเลข

🔴 **กฎเหล็ก 2 — งานคู่ RH/LH ห้ามคูณ 2** · std ของพาร์ทนี้ = `3600 ÷ CT` เท่าเดิม
(ชั่วโมงเดียวกันได้พาร์ทคู่อีกเท่าตัว แต่นั่นเป็นยอดของ mat อีกตัว) · ติดป้าย 👯 บนจอแทน

🔴 **กฎเหล็ก 3 — `actual > std` = CT master ผิด ไม่ใช่ไลน์เก่ง** ⇒ ธง `ct_suspect`
(เจอบ่อยเมื่อ CT ถูกกรอกเป็น "เวลาต่อชิ้นของงานคู่" แทนเวลาต่อ shot)

🔴 **กฎเหล็ก 4 — `ratio` (actual ÷ std) ควรใกล้ OEE** — 2 ตัวนี้วัดเรื่องเดียวกันจากข้อมูลคนละชุด
= ตรวจสอบกันเอง · ห่างเกิน 20 จุด ⇒ ธง `mismatch` (CT ผิด / ฐานเวลา OEE ไม่ตรง / ยอดผลิตไม่ครบ)

· ตารางเรียง **ตัวที่น่าสงสัยขึ้นก่อน** (ct_suspect → mismatch → no_ct → no_actual → ok)
· **แถวที่คิดไม่ได้ต้องอยู่ในตารางด้วย ห้ามกรองทิ้ง** + สรุปบอกว่าเทียบได้กี่พาร์ทจากทั้งหมด
· ค่าเฉลี่ย **ถ่วงน้ำหนักด้วยจำนวนชิ้น** ไม่ใช่เฉลี่ยธรรมดา (พาร์ทที่ผลิตเยอะมีผลต่อกำลังไลน์มากกว่า)
