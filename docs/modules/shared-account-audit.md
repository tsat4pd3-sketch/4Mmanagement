## 1. ขนาดของปัญหา (นับจาก `src/` · 13/10)

| สิ่งที่นับ | จำนวน | ฝั่ง Main | ฝั่ง DR (**ไม่มีด่าน DB**) |
|---|---|---|---|
| `.delete()` ต่อ Supabase | ~139 จุด / 66 ไฟล์ | ~72 | ~66 |
| ↳ ปุ่มลบที่คนกดจริง (มี `confirm()`) | ~82 จุด | | |
| `insert/update/upsert` | ~749 จุด / 131 ไฟล์ | ~308 | ~438 |
| "ลบ" ที่เป็น `update` (`is_active:false` · `status:'cancelled'`) | ~30 จุด | | ส่วนใหญ่ |
| RPC ที่เขียนข้อมูล | 12 จุดเรียก / 9 ฟังก์ชัน | 5 | 7 |
| **ผ่าน `canDelete()` ของกลาง (หลังแก้ 13/10)** | **11 จุด** | | |

⇒ สิ่งที่ปิดไปแล้ว (ปุ่มลบที่ผ่าน util + คีย์ `:delete` ฝั่ง Main) **ยังห่างจาก "view-only" มาก**

## 2. ชั้นความเสี่ยงที่ต้องตัดสินใจ (เรียงจากกระทบงานหน้างานน้อย → มาก)

| ชั้น | ตัวอย่าง | กระทบงานประจำ |
|---|---|---|
| 1. **ลบ + soft-delete** | ลบสินค้า/เครื่องจักร/ใบ LPA/กะผลิต · `is_active:false` · `status:'cancelled'` | น้อยสุด — ตรงคำขอหน้างาน |
| 2. **อนุมัติ / เซ็น / ปิดใบ** | ใบ MO ขั้น 5-8 + ช่องเซ็นรูป · อนุมัติ 4M (SV/QA) · ปิดกะ/อนุมัติปิดกะ · QA ตัดสินของสงสัย · ใบรายงานของเสีย 3 ช่องอนุมัติ · ใบเบิกสโตร์ · ลายเซ็น LPA | ⚠️ ต้องเช็คก่อน — บางขั้นบัญชีกลางเป็นคนทำจริง |
| 3. **แก้ master data** | `*:manage_master` · ทะเบียนสินค้า/เครื่อง/อะไหล่ · แม่แบบ NPI/PE · taxonomy | ปลอดภัยพอควร |
| 4. **ธุรกรรมประจำวัน** | เปิดใบ MO · ลงผลซ่อม · เบิกอะไหล่ · ยืนยันรอบส่ง · สแกนคัมบัง · ลงบันทึกผลิต | 🔴 **ปิดแล้วงานหยุด** |

🔴 **ลายเซ็นของบัญชีกลาง = สอบกลับไม่ได้** (ใครนั่งเครื่องนั้นก็เซ็นได้) ⇒ ชั้น 2 เสี่ยงเท่าชั้น 1

## 3. ของที่จะติดถ้าปิดเหมาเป็น view-only

| บัญชี (role · จำนวน) | งานที่จะทำไม่ได้ |
|---|---|
| `maintenance` · `jigmaintenance` · `toolingmaintenance` (mtn · 3) | **ใบ MO ตายทั้งสาย** — รับ/จ่ายงาน · ลงผลซ่อม+รูป · เบิกอะไหล่ · ลงค่าแรง · เซ็นขั้น 5-8 · PM daily check · ทะเบียนช่าง/เครื่อง |
| `warehouse1/2` · `delivery1/2` · `billing` (warehouse_delivery · 5) | ยืนยันรอบส่ง · ออเดอร์ลูกค้า · transport rounds · ภาชนะ |
| `planningstore` (planner_store · 1) | อัปโหลด forecast/order · บอร์ด Monitoring · จ่ายของเข้าไลน์ · แผนล็อต |
| `qa` (14) | ใบตรวจ QA · ตัดสินของสงสัย (ชี้ %Q) · ค่าวัด |
| `display` / `TV-1..13` (16) | **view อยู่แล้ว — ปิดได้ฟรี** |
| `ADMIN` · manager 1 · supervisor 2 | เสี่ยงสุด ปิดก่อนได้เลย |

⚠️ **วัดจากของจริง 30 วัน:** ใบ MO ทั้งหมด 426 ใบ — บัญชีกลางเปิดเอง **6 ใบ** · รับงาน **4 ใบ**
· เซ็นอนุมัติ **0 ใบ** ⇒ **ปิดชั้น 1-2 กระทบจริงแค่ ~1-2%** (คนละเรื่องกับ "ปิดชั้น 4")
🔴 แต่ `docs/modules/role-system.md` ระบุว่า **ช่าง 25 คนยังไม่มีบัญชีของตัวเอง** ⇒ ถ้าจะปิดชั้น 4
ต้องแจกบัญชีช่างก่อน ไม่ใช่ปิดแล้วค่อยแจก

## 4. ทางเลือก "ปิดที่จุดเดียว" (ยังไม่ลงมือ — รอ user ตัดสิน)

| ทาง | ทำอะไร | ✅ | ⚠️ |
|---|---|---|---|
| **A. ห่อ client** ที่ `src/supabaseClient.js` (ต่อจาก `withActorStamp` ที่ห่อ `from()` อยู่แล้ว) | ถ้า `isSharedAccount()` + ตาราง×คำสั่งไม่อยู่ allowlist → คืน `{error}` ให้ `checkWrite` โชว์ toast | ครอบ **100% ทั้ง Main + DR** รวม soft-delete และโค้ดใน `lib/`/`utils/` · แก้ไฟล์เดียว · ของใหม่ที่เขียนทีหลังถูกกันเอง | ต้องมี allowlist ไม่งั้นงานหน้างานตาย · ต้องแยก flag เป็นโมดูลเล็กกัน import วน · เปลี่ยนพฤติกรรมวงกว้าง ต้องรัน sweep ครบ |
| **B. `canWrite(resource, action, role)`** ใน `utils/permissions.js` + ด่าน build | ปิดตามชั้น (`delete`/`approve*`/`manage*` ปิด · `record`/`scan`/`service` เปิด) | ตรงแนวทางเดิม · error เห็นชัด · granular · ย้อนง่าย | ต้องไล่แก้ ~100+ จุด · drift ได้ถ้าด่าน grep ไม่แม่น · ไม่ครอบ `lib/`/`utils/` |
| **C. restrictive policy ฝั่ง Main + Edge Function ฝั่ง DR** | บังคับที่ DB จริง | ข้ามจอไม่ได้ (ยิง REST ตรงก็โดน) | ฝั่ง DR **ทำไม่ได้จนกว่าจะมี Edge Function** (known gap) ⇒ ครอบแค่ ~308/749 จุด · ย้อนยาก · เป็น "เปลี่ยน RLS วงกว้าง" = ต้องถาม user ก่อนตามกฎ branch workflow |

**ลำดับที่คุ้มสุด:** A (บังคับจริง) + ด่าน build ของ B (กันของใหม่หลุด) · C ไว้เฟสหลัง

## 5. ก่อนทำอะไรต่อ — ล้างข้อมูลทะเบียนก่อน

บัญชีกลางหลายตัวเป็น **ชื่อคนจริง** ที่ถูกตั้งประเภทผิด (qa 14 ตัว · `ขวัญพร` · `ชัยยุทธ`)
⇒ แก้ **ประเภทบัญชี → "บัญชีของคน"** ที่ `/add-user` ก่อน แล้วตัวเลขผลกระทบจะเล็กลงมาก
🔴 **ห้ามแก้ `account_kind` ให้เงียบๆ จาก AI session** — มันคือตัวตนของบัญชี คนต้องยืนยัน
