## 3. 🔴 กฎเหล็ก

### 3.1 เลขทุกตัวออกจาก `buildGrid()` ที่เดียว
แถว UNBOUND/BALANCE/ค้างที่ร้านชุบ เป็น **recurrence** (ค่าวันนี้กินค่าเมื่อวาน)
ก๊อปสูตรไปคิดในหน้า = ลืมบวกตัวเดียว เพี้ยนทั้งแถวโดยช่องยังมีเลขอยู่ ดูปกติทุกประการ
· มีด่าน `monitor-grid-math-via-helper`

### 3.2 "ว่าง" กับ "ไม่รู้" ไม่ใช่ตัวเดียวกัน
- ช่องกลางแถวที่ว่าง = วันนั้นไม่มีของไหลจริง ⇒ **นับเป็น 0** (Excel ก็คิดแบบนี้)
- **ช่องตั้งต้น (คอลัมน์แรก) ว่าง = ไม่รู้ยอดยกมา ⇒ ทั้งแถวเป็น `null`**
  ห้ามเดา 0 — "ยกมา 0" กับ "ไม่รู้ว่ายกมาเท่าไหร่" ตัดสินใจคนละแบบสิ้นเชิง
  จอต้องเขียนว่าพาร์ทไหนยังไม่ใส่ (`gridSummary().seedMissing`)

### 3.3 ค่าที่คนกรอกชนะค่าที่ระบบดึงเสมอ
หน้างานเห็นของจริงที่ระบบยังไม่รู้ · ระบบห้ามลบของที่คนยืนยัน (จัดการใน `buildGrid`)

### 3.4 ⚠️ Total SL — 2 ชีทในไฟล์เดิมคิดคนละสูตร **อย่ายุบเอง**
```
800T r3  =SUM(Q6:AU6)      → Σ แถว OUT        (ของที่ส่งออกไปจริง)
110T r3  =SUM(R4:AV4)+Q7   → Σ แถว IN + ยอดยกมา (ของที่ "มีให้ส่ง")
```
2 ชีทตอบคนละคำถามใต้ชื่อคอลัมน์เดียวกัน ⇒ **%SL ของ 2 ไลน์เทียบกันตรงๆ ไม่ได้**
เก็บไว้ทั้ง 2 แบบเป็นการตั้งค่า (`sl_row` + `sl_includes_seed`) แล้วให้จอเขียนว่านับจากแถวไหน
**ยุบให้เหลือสูตรเดียว = เปลี่ยนตัวเลขที่ทีมใช้อยู่โดยไม่มีใครสั่ง** — ต้องถามทีมวางแผนก่อน
· ทั้ง 2 ชีท**ข้ามคอลัมน์ยอดยกมา**ในการ Σ (`skipSeed` default true)

### 3.5 ไม่ตั้ง MIN = ไม่เตือน
หลักเดียวกับ `line_part_levels` — ระบบไม่เดา min ให้ · เทียบได้เฉพาะเมื่อรู้ทั้ง BALANCE และ MIN

### 3.6 แถวที่คำนวณได้ ห้ามเก็บลง `monitor_cells`
เก็บ = มี 2 แหล่งความจริง แล้ววันที่สูตรเปลี่ยน ของเก่าไม่ตามไปด้วย
**ยกเว้นช่อง "ยอดยกมา"** (คอลัมน์แรก) ซึ่งเป็น input จริงๆ · ตอน import ก็เก็บแค่ช่องนั้น

## 6. กับดักที่เจอจริงตอนทำ (คนถัดไปน่าจะเจอซ้ำ)

1. **ชีท RA ถูกส่งเข้าตัวแกะผิดตัว** — หัวคอลัมน์ `Diff Forecast` ของ RA ชนกับป้าย
   `Diff forecast` ของชีทงานชุบ ⇒ ต้องตรวจด้วยป้าย**ที่เป็นเอกลักษณ์** (`TSAT4 to JRPE` /
   `Stock Vendor`) เท่านั้น · ผลตอนพลาด: RA ได้ 0 ช่อง + เตือนป้ายมั่ว 10 ตัว
2. **ชีท 824-825: 1 บล็อก = 1 พาร์ท ที่มีเลข SAP 2 ตัว** (ก่อนชุบ / หลังชุบ)
   เปิดพาร์ทใหม่ทุกครั้งที่เจอเลข 6 หลัก = ได้ 2 พาร์ทที่แถวไม่ครบคนละครึ่ง ⇒ สูตรคิดไม่ได้ทั้งใบ
   · แยกบล็อกด้วยคอลัมน์ขั้น (`ก่อนชุบ`) ไม่ใช่ด้วยเลข MAT
3. **ชีท 824-825 มีคอลัมน์ยอดยกมาที่ไม่มีวันที่กำกับ** (Stock Vendor = 849 อยู่ก่อนคอลัมน์
   2026-09-01 ซึ่งมี 599) ⇒ ยกให้เป็นคอลัมน์ "วันก่อนวันแรก" ให้โครงเหมือนชีทไลน์ปั๊ม
   ทิ้งไป = สูตรเริ่มจาก null = ทั้งแถวว่าง
4. **`MAT_HEADS` ไม่มี `MATLSAP`** — ชีท mat เขียนหัวว่า `" Mat'l SAP"` ⇒ แกะไม่ได้ทั้งใบ
   · เพิ่มแล้ว + ตรวจว่าไม่กระทบ `detectMonitoringKind` (ชีท mat ยังคืน null เหมือนเดิม
   ⇒ `MonitoringUpload` จอเดิมยังข้ามชีทนี้เหมือนเดิม **ไม่มีพฤติกรรมไหนเปลี่ยน**)
5. **ห้ามเอาป้ายของชีทงานชุบไปใส่ `LABELS_PRESS`** — `detectMonitoringKind` ใช้ลิสต์นั้น
   ใส่เข้าไป ชีท 824-825 จะกลายเป็น `kind='press'` แล้วจอ `MonitoringUpload` (23/09) จะเริ่ม
   เขียน "ส่งไปชุบ" เป็นยอดส่งลูกค้า ซึ่งเป็นบั๊กที่คอมเมนต์ของมันเตือนไว้ตรงๆ

6. 🔴 **คอลัมน์ที่โค้ด `upsert` ต้องมี unique index แบบ "เต็ม" ห้ามเป็น partial** (02/10 · หลุดถึงมือ user)
   `monitor_board_parts_uniq` เดิมเขียน `where mat_no is not null and is_active` ⇒ PostgREST
   `.upsert({ onConflict: 'board_id,mat_no' })` ขึ้น **`there is no unique or exclusion constraint
   matching the ON CONFLICT specification`** นำเข้าไม่ได้เลยสักชีท
   · Postgres จับคู่ partial index ให้ก็ต่อเมื่อคำสั่งมี WHERE ตรงกับ predicate ซึ่ง PostgREST ส่งไม่ได้
   · `monitor_cells_uniq` เป็น index เต็มอยู่แล้วจึงไม่ล้ม — ล้มเฉพาะตารางพาร์ท
   · **บั๊กคลาสนี้ build/lint/เทส/สวีปจอ จับไม่ได้เลย** เห็นตอนกดใช้จริงเท่านั้น
     ⇒ ตารางใหม่ที่ client จะ upsert **ต้องลองยิง upsert จริง 1 ครั้งก่อนปิดงาน**
   · แก้ด้วย `20261002_monitoring_parts_uniq_fix_dr.sql` (สร้าง index เต็มชื่อ `…_bm_uniq`)
     ⚠️ `ON CONFLICT` จับคู่ด้วย**คอลัมน์ ไม่ใช่ชื่อ index** · index partial เดิมยังอยู่ (ซ้ำซ้อน
     แต่ไม่เป็นอันตราย) เพราะ `DROP INDEX` ผ่าน MCP timeout ซ้ำๆ — เป็นงานค้างให้ลบทีหลัง

## 🔴 FG ห้ามลงเป็น min/max ที่ไลน์ (2026-10-02 · user แจ้งจากหน้างานสโตร์)

> user: *"เลข mat sap ที่โชว์คือ 10088639 คือ mat sap ที่เป็น FG หลังกระบวนการผลิตจบ
> แต่สโตร์จะไม่รู้เลขนี้ สโตร์จะมองหาเลขที่เค้าต้องตัดจ่ายเข้าไลน์ผลิตคือพวก 5xxx 3xxx 2xxx"*

### ลูกโซ่ของบั๊ก (ตามจากจอ → ต้นตอ)
1. สโตร์เห็นใบในคิวเติม WIP ที่เลข MAT เป็น **1xxxxxxx (FG)** ซึ่งตัดจ่ายไม่ได้
2. ใบนั้น `source='line'` = ไลน์กดขอเบิกมา — แต่จอไลน์ (`LinePartCallPanel`) **ไม่ได้ให้พิมพ์เลขเอง**
   มันเสนอจากทะเบียน `line_part_levels` (min/max ของพาร์ท "ต่อไลน์")
3. `line_part_levels` ที่ใช้งานอยู่ **60 แถว มาจากการนำเข้า Monitoring ทั้งหมด** และ **28 แถวเป็น FG**
4. ตรวจกับ `dr_products`: FG ทุกแถว `line_name` ของทะเบียน = **ไลน์ที่ผลิตพาร์ทนั้นเอง** (ตรงกันทุกตัว)

⇒ ตัวนำเข้า 23/09 เขียน min/max ให้ **ทุก** พาร์ทในชีทไลน์ปั๊ม ซึ่งมีทั้ง FG และชิ้นส่วน
(วัดจริง: FG 38 / ชิ้นส่วน 68 จาก 106) ⇒ **ไลน์ถูกเสนอให้ "เบิกของที่ตัวเองผลิต"**

### กฎ
🔴 **`line_part_levels` = ของที่ต้องมีอยู่ที่ไลน์เพื่อ "ป้อนการผลิต" ⇒ FG (1xxx) ไม่เข้าพวก**
FG คือ**ขาออก**ของไลน์ · ของที่สโตร์ตัดจ่ายเข้าไลน์คือ **2xxx (ผลิตเอง) · 3xxx (ซื้อ) · 5xxx (วัตถุดิบ)**

⚠️ ไม่ได้แปลว่า FG ห้ามเข้าไลน์เสมอไป — FG ของไลน์หนึ่งเป็นชิ้นส่วนป้อนไลน์ประกอบได้จริง
(ตู้ "Store FG → ไลน์ประกอบ") **แต่ตัวนำเข้า Monitoring map พาร์ทกลับไปที่ "ไลน์ที่ผลิตมัน" เสมอ**
⇒ ในบริบทนี้ FG = ขาออกเสมอ · ด้วยเหตุนี้การเตือนบนการ์ดจึงอยู่เฉพาะ**คิวเติม WIP** ไม่ใช่ทุกตู้

### ที่แก้ไป
- `monitoringSheet.js` — `monitoringToRecords` กัน FG ออกจาก `levels` ทั้ง 2 ทาง (ชีทไลน์ปั๊ม + ชีทลูกค้า)
  · คืน `fgLevelsSkipped` ออกมาให้จอนำเข้ารายงาน **ห้ามข้ามเงียบ** · มีเทส 4 เคส
  · FG ยัง**ลง forecast/ออเดอร์ได้ตามปกติ** — กันเฉพาะ min/max ที่ไลน์
- ปิดใช้งานทะเบียนที่ผิด 28 แถว (`is_active=false` + เขียนเหตุผลต่อท้าย `note` · **ไม่ลบ ย้อนได้**)
- `HeijunkaKanban` — การ์ดคิวเติม WIP ขึ้นแถวเตือนเมื่อเลขเป็น 1xxx (**เตือนอย่างเดียว ไม่บล็อก** —
  ดัดค่าที่คนกรอก = เดาแทนคน) · ใบเก่าที่ค้างอยู่ 1 ใบจึงอธิบายตัวเองได้บนจอ

### rollback

## 🔁 เลข MAT ซ้ำในชีทเดียว → รวมเป็นพาร์ทเดียว (2026-10-05 · เคสจริงชีท Argen)

**อาการ:** นำเข้าแล้วขึ้น *"พาร์ทของ Argen ไม่สำเร็จ: ON CONFLICT DO UPDATE command cannot affect row a second time"*
และบอร์ดนั้นล้มทั้งบอร์ด
**ต้นเหตุ:** `monitor_board_parts` เป็น unique `(board_id, mat_no)` แต่ชีทมี MAT เดียวกันหลายบล็อก
⇒ upsert ก้อนเดียวมีคีย์ซ้ำ Postgres จึงปฏิเสธทั้งก้อน
**กฎ** (`mergeDuplicateParts` ใน `src/utils/monitoringSheet.js` · ทุกชนิดชีทผ่าน `parseSheetForBoard` · เทส `monitorDupMat.test.mjs`):
- ยอดไหล (PLAN/IN/OUT/ORDER REQUIREMENT/ส่งชุบ/order) ของ MAT ซ้ำ = **บวกกัน**
- ยอดระดับ/คงเหลือ (BALANCE/UNBOUND/WIP/MIN/MAX/STOCK W/H/ค้างที่ร้านชุบ), ข้อความ และแอตทริบิวต์ = **แถวแรกชนะ**
  (นับของชิ้นเดียวกัน 2 รอบ = สต็อกปลอม) · แอตทริบิวต์ที่แถวแรกว่างให้เติมจากแถวหลัง
- ทุก MAT ที่ซ้ำ และทุกค่าคงเหลือที่ขัดกัน **ต้องขึ้นเป็นคำเตือนบน preview** ให้ทีมวางแผนไปแก้ไฟล์ต้นทาง ห้ามรวมเงียบ
