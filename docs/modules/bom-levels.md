## โมเดลใหม่ (migration `20260916_bom_level_parent_mat.sql` — **apply แล้ว 16/09 · ตรวจกลับ 0/0/506**)

| คอลัมน์ | ความหมาย |
|---|---|
| **`parent_mat`** (text · null) | ตัวแม่ของบรรทัดนี้เป็น **mat_no** — ใครก็เป็นแม่ได้ ไม่ต้องเป็น `dr_products` · **null = พฤติกรรมเดิมเป๊ะ** |

### 🔴 กฎเหล็ก — ต้นไม้ BOM ต้องผ่าน `buildBomIndex` เท่านั้น

```js
import { buildBomIndex } from '../utils/bomTree';
const ix = buildBomIndex(bomRows, matOfProductId);   // parent_mat ชนะ product_id
ix.bomOf('10100817')   // ลูกชั้นถัดไป
ix.parentOf(row)       // ตัวแม่ของบรรทัด
ix.orphans             // แถวที่หาตัวแม่ไม่ได้ — ⚠️ ต้องโชว์ ห้ามกลืน (บรรทัดหายจากต้นไม้เงียบๆ)
```

- **ห้ามเขียน `matOf[b.product_id]` เองในหน้าอีก** — มี **ด่านสแกนทั้งรีโป** แล้ว
  (`regressionGuards.test.mjs` กฎ `bom-tree-via-buildBomIndex` · ตกด่าน = build ล่ม)
  เหตุผล: เขียนเองตั้งแต่มี `parent_mat` แล้ว = **มองข้ามชั้นที่คนตั้งไว้เงียบๆ** คนละจอเห็นโครงคนละแบบ
- ย้ายชั้นผ่าน **`moveBomLine(row, toMat, bomOf)`** — กันย้ายใต้ตัวเอง/ใต้ลูกหลานตัวเอง (วนลูป) · pure + มีเทส

## ทำไม "เหนือ SAP" — เพราะเรามีชั้น OP

SAP แยก **BOM** (ต้นไม้วัสดุ) กับ **Routing** (ขั้นตอน) การผูก component→operation เป็น optional
ที่แทบไม่มีใคร maintain · ของเรา **BOM บรรทัดเดียวตอบทั้ง 2 คำถาม**: ประกอบจากอะไร + ใส่ตอนขั้นไหน

⇒ จุดที่ได้ประโยชน์ทันทีเมื่อกรอก `op_no` ครบ:
ของเสียหลุดขั้นไหนก็ตัดถูก (`scrapExplode`) · WIP ต่อขั้น (`wipChain`) · part-call ส่งของถูกขั้น/ถูกไลน์
(`bom_items.source_line` ว่างทั้ง 408 แถว = สโตร์ยังเดาเอง) · ต้นทุนต่อขั้นในอนาคต
