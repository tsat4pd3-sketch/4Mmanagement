## 🔴 บั๊กที่ทำให้ต้องมีไฟล์กลาง (26/10)

`/register` **ไม่เคยเขียน `staff_kind` เลย** ตั้งแต่มีคอลัมน์นี้ (21/09) ⇒ ตกไปที่ `default 'shopfloor'`

⇒ QA · วิศวกร · ธุรการ · สโตร์ ที่ถูกลงทะเบียนทางนั้น **ถูกนับเป็นกำลังคนหน้าไลน์เงียบๆ**
(เข้าแผงสกิล · เข้าตัวหาร manpower ของไลน์ · เข้า turnover — ดู `staffKind.js` §แกนที่ 1)
สังเกตไม่ได้จากจอไหนเลย เพราะคอลัมน์ไม่ได้ว่าง มันมีค่าที่ "ดูปกติ"

**บทเรียน:** คอลัมน์ `not null default` + ทางเข้าหลายทาง = คลาสบั๊ก "ค่าเริ่มต้นเงียบ"
ทางที่ลืมเขียนจะไม่ล้ม ไม่เตือน และได้ค่าที่ดูถูกต้อง ⇒ **ต้องบังคับเขียนทุกครั้งผ่านตัวประกอบแถวตัวเดียว**

## กฎ

1. ทุกทางเข้าประกอบแถวด้วย **`newEmployeeRow({...})`** — เพิ่มคอลัมน์ใหม่ = เติมที่นั่นครั้งเดียว
2. `staff_kind` **ต้องอยู่ในแถวเสมอ** ไม่ส่ง = `'shopfloor'` (ตรงกับ default ของคอลัมน์ เจตนาชัด)
3. **สายสนับสนุน = `line_id`/`team`/`group_name` เป็น `null` เสมอ** — `newEmployeeRow()` ตัดให้
   และ**จอต้องปิดช่องนั้นด้วย** ไม่งั้นจอสัญญาอย่าง ฐานเก็บอีกอย่าง
4. ข้อความอธิบายใต้ตัวเลือกประเภท อ่านจาก **`staffKindHint()`** ห้ามเขียนคำอธิบายชุดที่ 2 ในหน้า
5. insert ต้องผ่าน `checkWrite()` (กฎการเขียน DB ข้อ 1) — เดิม `/register` ใช้ `throw` ในก้อน try
   ซึ่งไม่เงียบ แต่ไม่เข้าชุดเดียวกับหน้าอื่น

## 🔁 รหัสซ้ำต้องตอบเป็นคน ไม่ใช่ชื่อ constraint (2026-11-09)

**เกิดจริง 09/11:** หัวหน้า PD2 ลงทะเบียน 3 คน (2103622 เจนนิภา · 2103793 ขันทอง · 2103242 สุทธวีร์) ที่ `/register` ไม่ได้
toast ขึ้น `duplicate key value violates unique constraint "employees_employee_id_code_key"` — ทั้ง 3 คน**มีอยู่ในฐานแล้ว**
(สร้างจาก /add-user 21–23/09 · 06/10) แต่เป็นสายสนับสนุน `section` ว่าง/PD1 และ 1 คนถูกปิดใช้งาน
⇒ `/operator` ของ PD2 กรองตาม scope จึงมองไม่เห็น ⇒ คิดว่ายังไม่มี ⇒ เพิ่ม ⇒ ชนรหัส ⇒ ตัน ("มีอยู่ในฐานแต่มองไม่เห็น" ซ้ำรอบ 23/09)

**กฎ (เจ้าของ `employeeIdentity.js`):**
- ทุกทางเข้า **ถาม `findEmployeeByCode(client, code)` ก่อน insert** · คืน `{ row, error }` — `error` = อ่านไม่ได้ ⇒ **ไม่เพิ่ม** (fail-closed) ห้ามตีเป็น "ไม่มี"
  (RLS SELECT ของ `employees` = `true` สำหรับ authenticated ⇒ เห็นข้ามส่วนงานได้ ตรวจ 09/11)
- เจอแถวเดิม ⇒ ข้อความจาก **`duplicateEmployeeText(row, { code, scopeSecs })`**: ชื่อ · ประเภท · ส่วน/แผนก · ใช้งาน/ปิดอยู่ · แก้ที่ไหน
  — ปิดใช้งาน → "เปิดกลับที่ /operator" · นอก `scopeSecs` → "ให้ admin ย้ายส่วนงาน" · ในขอบเขต → "แก้ของเดิมที่ /operator"
- insert แล้วได้ 23505 (สองคนกดพร้อมกัน) ⇒ **`isDuplicateEmployeeError(err)`** แล้วตอบข้อความเดียวกัน **ก่อน** `checkWrite()`
- `/add-user` เดิมเช็คซ้ำจากลิสต์ `emps` (โหลดเฉพาะ `is_active`) ⇒ คนที่ถูกปิดใช้งานหลุดด่าน — ตอนนี้ถามฐานซ้ำเสมอ
- ด่าน `employee-identity-single-entry` ตรวจว่าทุกไฟล์ที่ insert `employees` เรียกทั้ง 2 ฟังก์ชัน · เทส `employeeDuplicate.test.mjs`

## 🪪 บัตรพนักงาน = ทางเช็คชื่อ (2026-11-10 · คำสั่ง user)

QR บนบัตร = **รหัสพนักงานล้วน** → `employees.employee_id_code` (กติกาจับคู่ + `findByBadge` อยู่ `src/utils/badgeCheckin.js`)
ตอนนี้มี **2 ประตู** ที่ยิงบัตรแล้วเช็คชื่อได้ และทั้งคู่เขียน `daily_production_logs` ผ่าน
**`src/lib/checkinSave.js` ชุดเดียว** (`checkinLogRow` / `upsertCheckin` / `checkinByBadge`) — ห้ามประกอบแถวเอง

| ประตู | ใช้ตอนไหน | "มางานอยู่แล้ว" ตัดสินยังไง |
|---|---|---|
| `/checkin` → ปุ่ม 🪪 เปิดกล้องยิงรัว | หัวหน้าเช็คทั้งไลน์ | ดูจาก **state บนจอ** ⇒ **เขียนซ้ำเสมอ** เพราะ "มางาน" อาจเป็นแค่ติ๊กค้างที่ยังไม่เคยลงฐาน |
| `/scan` → ยิงบัตรใบเดียวแล้วจบ | ใครก็ได้ ยิงบัตรคนเดียว | ดูจาก **แถวในฐาน** ⇒ `already` = **ไม่เขียนซ้ำ** (กันทับ `checked_by` คนแรก) |

🔴 ทั้ง 2 ทาง: เขียนไม่ติด = **ห้ามขึ้น ✓** (จอต้องบอกว่ายังไม่ได้เช็ค ให้ยิงซ้ำ) ·
merge ของเดิมเสมอ ไม่ทับ PPE/OT/ลา · ลาเต็มวันแล้วมายิงบัตร = มาจริง ⇒ ล้างการลา (ครึ่งวันคงไว้)
· `/scan` ต้องเช็คขอบเขตชั้น ③ เอง (ไม่มีรายชื่อมากรองให้) — ดู `docs/modules/qr-equipment-scan.md` §เฟส 4
