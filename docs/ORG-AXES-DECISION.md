## 3. หลักฐานว่าแกน "สังกัด" พังจริง (ไม่ใช่ความเห็น)

### 3.1 ชื่อแผนกซ้ำกัน 2 หน่วย — `department` ตัวเดียวบอกไม่ได้ว่าอยู่ฝ่ายไหน

| แผนกในผัง | อยู่ใต้ฝ่าย |
|---|---|
| `ทั่วไป` | **PD2** |
| `ทั่วไป` | **PD4** |

⇒ พนักงาน **15 คน** ที่ `department = 'ทั่วไป'` (PD2 8 คน · PD4 7 คน)
**จับคู่กับผังด้วยชื่อไม่ได้เด็ดขาด** — ได้ 2 คำตอบเสมอ
⇒ ทุกตัวกรอง/ทุกกฎแจ้งเตือนที่เดินผ่าน "ชื่อแผนก" ตัดสินคนกลุ่มนี้ผิดหรือได้ทั้งคู่

### 3.2 ข้อความที่พิมพ์มือ ไม่ตรงผัง

| ค่าใน `employees.department` | จำนวนคน | ตรงกับผังไหม |
|---|---|---|
| `ฝ่ายผลิต` | **28** | ❌ ไม่ใช่ชื่อแผนก — เป็นคำเรียกรวม |
| `ฝ่าผลิต` (พิมพ์ตก "ย") | 1 | ❌ |
| `Smail Press` (สะกดผิด `SMALL PRESS`) | 1 | ❌ |
| *(ว่าง/null)* | 3 | ❌ |

**รวม 30 คนที่ระบบไม่รู้ว่าอยู่แผนกไหน** · + **20 คนไม่มี `section` เลย** · + **20 บัญชี** ที่
`profiles.section` เป็นข้อความที่ไม่ตรงผัง

### 3.3 แกนเดียว เก็บ 11 ที่

```
employees :  section · department · group_name · line_id · team · mtn_team        (6)
profiles  :  section · sections[] · line_id · team · mtn_teams[]                  (5)
org_nodes :  id · parent_id · kind   ← ผังจริง แต่ไม่มีใครชี้มา                    (0 ตัวอ้าง)
```
⇒ ย้ายคน 1 คน = ต้องแก้ให้ตรงกันเองหลายที่ · แก้ไม่ครบ = สิทธิ์/แจ้งเตือนเพี้ยนเงียบ

## 4. หลักฐานว่าแกน "ระดับพนักงาน" **สะอาดแต่ไม่ถูกใช้**

`positions` = 12 ตำแหน่ง / **7 ระดับ** · `employees.position` ตรงกับทะเบียน **100% (0 ไม่ตรง)**
`profiles.position` ไม่ตรง 2 แถว

**แต่** เอกสารเขียนไว้เองว่า `profiles.position` = *"ตำแหน่งจริง — แสดงผลเท่านั้น"*
⇒ **ระดับไม่เคยถูกใช้ตัดสินขอบเขตการเห็นเลยแม้แต่จุดเดียว**
⇒ นี่คือสาเหตุตรงๆ ของอาการที่ user ทัก: *"job level manager (role manager) มองได้หมด
ซึ่งความจริงต้องดูด้วยว่าเค้าอยู่แผนกไหน ส่วนงานไหน"*

วันนี้ `role = manager` ให้ทั้ง **"ทำอะไรได้"** และ **"เห็นกว้างแค่ไหน"** พร้อมกัน
— ซึ่งเป็นคนละเรื่อง และเป็นที่มาของการปนกันทั้งหมด

## 5. 🎯 คำตัดสิน — เหลือ 3 แกนตัดสิน + 2 แกนอ้างอิง

> **กฎข้อเดียวที่ใช้ทั้งระบบ ตั้งแต่ปุ่ม · หน้า · แถวข้อมูล · จนถึงแจ้งเตือน:**
>
> ## เห็น / ทำ / ได้แจ้งเตือน  =  (**สิทธิ์**: ทำอะไรได้) ∩ (**สังกัด × ระดับ**: ครอบคลุมถึงไหน)
>
> วันนี้มีแต่ครึ่งซ้าย · ครึ่งขวาไม่เคยถูกบังคับ → นั่นคือทั้งหมดของปัญหา

| แกน | ชื่อที่ใช้เรียกต่อจากนี้ | ตัดสินอะไร | source of truth |
|---|---|---|---|
| **A** | **สังกัด** (WHERE) | อยู่ตรงไหนของผัง | **`org_nodes.id` เท่านั้น** — ข้อความทุกคอลัมน์ลดชั้นเป็น *สำเนาไว้โชว์* |
| **B** | **ระดับ** (HOW FAR) | เห็นกว้างแค่ไหน**นับจากสังกัดตัวเอง** | `positions.level` → `scope_depth` |
| **C** | **สิทธิ์** (WHAT) | ทำอะไรได้ | `role` × `role_permissions` (เหมือนเดิม) |
| — | ประเภทคน | นับกำลังคนไหม / คิดต้นทุนยังไง | อ้างอิงเท่านั้น — **ห้ามใช้ตัดสินสิทธิ์** |
| — | ตัวตน | คนนี้คือใคร | `employees` (ตบแล้ว) |

### 5.1 A — สังกัดผูก id ไม่ผูกชื่อ

```
profiles.org_node_id   uuid → org_nodes.id     "บัญชีนี้สังกัดหน่วยไหน"
employees.org_node_id  uuid → org_nodes.id     "คนนี้สังกัดหน่วยไหน"
```
- ไล่ขึ้น-ลงด้วย `parent_id` เอง ⇒ **ไม่ต้องเก็บ section/dept/line/team แยกอีกต่อไป**
- คอลัมน์ข้อความเดิม **ไม่ลบ** — เขียนต่อได้ในฐานะ *สำเนาไว้โชว์/ไว้ export* ที่ระบบเติมจาก id ให้
  (backward-compatible · หน้าเก่าที่อ่านข้อความยังทำงานเหมือนเดิมทุกหน้า)
- ⚠️ **ชื่อซ้ำ (`ทั่วไป`) หายไปเองทันทีที่ผูก id** — dropdown โชว์เป็น `PD2 › ทั่วไป` / `PD4 › ทั่วไป`

### 5.2 B — ระดับกำหนด "ความกว้าง" ไม่ใช่ "อำนาจ"

| `scope_depth` | ความหมาย | ระดับที่ควรได้ (ข้อเสนอ) |
|---|---|---|
| `self` | ตัวเองคนเดียว | พนักงาน |
| `unit` | หน่วยที่สังกัด (ไลน์/ทีมตัวเอง) | หัวหน้าไลน์ · หัวหน้างาน |
| `branch` | หน่วยตัวเอง **+ ทุกหน่วยที่อยู่ใต้ลงไป** | หัวหน้าแผนก · ผู้จัดการฝ่าย |
| `all` | ทั้งโรงงาน | ผู้บริหาร · admin |

- **ค่าเริ่มต้นมาจากระดับ (`positions.level`) แต่ override รายบัญชีได้** — ของจริงมีข้อยกเว้นเสมอ
  (เช่น QA ต้องเห็นข้ามฝ่าย ทั้งที่ระดับไม่สูง)
- **`branch` คือคำตอบของ "manager ควรเห็นแค่ฝ่ายตัวเอง"** — manager ของ PD3 ได้ `branch`
  ที่โหนด PD3 ⇒ เห็น PD3 + แผนก/ไลน์/ทีมใต้ PD3 ทั้งหมด **แต่ไม่เห็น PD1/PD2/PD4**

### 5.3 C — สิทธิ์ไม่เปลี่ยนแนวคิด แค่ล้าง hardcode

- 196 คีย์ในทะเบียน · **0 คีย์ตาย** (โค้ดไม่เรียกคีย์ที่ไม่มีในทะเบียน — ตรวจแล้ว 23/09) ✅
- 20 คีย์ในทะเบียนที่ไม่มีโค้ดเรียกตรงๆ — ส่วนใหญ่ถูกใช้ผ่าน `canDelete()` (ลายเซ็นคนละแบบ) ต้องแยกแยะทีละตัว
- **147 จุด hardcode `role === '...'`** = สิทธิ์ที่ปรับจาก `/permissions` ไม่ได้ (หนักสุด: Report 31 · DailyReport 15 · AddUser 10)

### 5.4 ประเภทคน — 2 แกนที่ชื่อค่าซ้ำ ต้องแยกให้ขาด

| | `org_nodes.labor_type` | `employees.staff_kind` |
|---|---|---|
| เก็บที่ | **แผนก** | **รายคน** |
| ตอบ | คิดต้นทุนเป็นแรงงานตรงไหม | เช็คชื่อ/นับกำลังคนไหม |
| ช่าง MTN | `indirect` | `direct` (เช็คชื่อครบ 25/25) |

**ค่าเหมือนกันเป๊ะแต่ตอบคนละคำถาม และขัดกันจริงที่ช่าง** ⇒ เสนอเปลี่ยนชื่อค่าฝั่ง `staff_kind`
เป็น **`shopfloor` / `support`** (จอโชว์ 🧑‍🏭 หน้างาน / 🗂️ สนับสนุน อยู่แล้ว)
· **ทั้ง 2 แกนนี้ห้ามใช้ตัดสินสิทธิ์หรือผู้รับแจ้งเตือนเด็ดขาด**

## 7.5 โมเดลนี้มีชื่อทางการ — และมีข้อบังคับติดมา

สูตร **(สิทธิ์) ∩ (สังกัด × ระดับ)** = **role-centric RBAC-A** ตามนิยาม NIST
(role = เพดาน · attribute ตัด*ให้แคบลง*เท่านั้น ห้ามขยาย) — เป็นแบบที่ NIST ชี้ว่า
**ยังตอบคำถาม audit ได้ว่า "role นี้ทำอะไรได้บ้าง"** ต่างจากแบบ attribute-centric

⇒ **ข้อบังคับที่ตามมา: ไม่ตั้งขอบเขต ต้องแปลว่า "เห็นเฉพาะของตัวเอง" ไม่ใช่ "เห็นทุกอย่าง"**
วันนี้เรากลับด้าน (fail-open 11 บัญชี + `notify_recipients`) — ผิดทั้งนิยาม role-centric
และผิดหลัก deny-by-default ของ OWASP พร้อมกัน

## 7.6 สถานะแกน "ระดับ" — ทำอะไรไปแล้ว / ยังไม่ได้ทำอะไร (24/09)

**ทำแล้ว — ของที่ "เดาเงียบๆ" กลายเป็น "ค่าที่เห็นได้":**
- `profiles.scope_depth` (self/unit/branch/all) + `scope_depth_src` (ที่มาของค่า)
- backfill ให้ผลลัพธ์ **เท่าพฤติกรรมวันนี้เป๊ะทุกใบ** — 97 บัญชี: `branch` 45 · `all(role)` 40 · **`all` แบบ `legacy_open` 12**
- จอ `/add-user` เลือกความกว้างได้ + แนะนำค่าตามระดับตำแหน่ง + เตือนเมื่อเลือก "ทั้งโรงงาน"
- คิวทบทวน 12 บัญชีโชว์บนหน้า (ISO 27001 A.5.18) — เคลียร์แล้วหายไปเอง
- **แถวใหม่ default = `unit` (แคบ)** ⇒ ของใหม่เริ่มที่ deny-by-default แล้ว

**🔴 ยังไม่ได้ทำ — พฤติกรรมของจอทุกจอยังเหมือนเดิมทุกประการ:**
`effectiveSections()` / `scopedLineNames()` / `notify_recipients()` **ยังไม่อ่าน `scope_depth` เลย**
⇒ fail-open ยังอยู่ · การสลับตัวคำนวณคือขั้นถัดไป และมีเงื่อนไขบังคับ:

> **ก่อนสลับ ต้องรันเทียบ "ขอบเขตที่ได้แบบเก่า vs แบบใหม่" กับบัญชีจริงครบทั้ง 97 ใบ
> แล้วพิสูจน์ว่าต่างกันเฉพาะใบที่ตั้งใจให้ต่าง** — สลับดื้อๆ = คนหายจากจอ/ไม่ได้แจ้งเตือนเงียบๆ
> และเป็นคลาสบั๊กที่ผู้ใช้จะไม่มีทางรู้ว่าเกิด

## 8. ห้ามทำ

- ❌ ลบคอลัมน์ข้อความเดิมในเฟสนี้ (หน้าเก่าอ่านอยู่ ~11 คอลัมน์ × หลายสิบหน้า)
- ❌ แก้ RLS แบบเหมาทุกตารางพร้อมกัน (กฎเหล็ก CLAUDE.md — เคยพังทั้งระบบมาแล้ว)
- ❌ เอา `labor_type` / `staff_kind` ไปตัดสินสิทธิ์
- ❌ ให้ระบบ "เดา" สังกัดจากชื่อที่จับคู่ไม่ติด แล้วเงียบ — ต้องโชว์ว่าไม่รู้
