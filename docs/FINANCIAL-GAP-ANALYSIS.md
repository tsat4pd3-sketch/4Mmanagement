## 0. สรุปสั้น (TL;DR)

**ฝั่งต้นทุน (cost) ระบบมีโครงอยู่แล้วพอสมควร · ฝั่งรายได้ (revenue) ยังไม่มีอะไรเลยแม้แต่คอลัมน์เดียว**

ตรวจแล้วทั้ง Main (`ewhdfqwfwofivojtsizn`) และ DR (`eyhclzkifitbhbljgoav`):
ไม่มีตาราง/คอลัมน์ใดที่เก็บ **ราคาขาย** ของพาร์ท — `price` ที่มีคือ `mtn_spare_parts.unit_price` (ราคาอะไหล่ซ่อม)
และ `mtn_labor_rates.price` (ค่าแรงช่าง) ซึ่งเป็น**ฝั่งจ่าย ไม่ใช่ฝั่งขาย**

การเพิ่ม "ช่องราคาขาย" ไม่ใช่งานเติมคอลัมน์เดียว — มี **6 ช่องว่างที่ต้องตัดสินใจก่อนเขียนโค้ด**
โดย 2 ข้อแรกเป็น **blocker จริง** (ทำผิดแล้วต้องรื้อ ไม่ใช่แค่แก้):

| # | ช่องว่าง | ระดับ |
|---|---|---|
| **B1** | **ราคาขายจะไปอยู่ DR project = เปิด anon อ่านได้ทั้งโลก** (กฎเหล็ก `supabaseDR` ไม่เคย authenticate) | 🔴 blocker |
| **B2** | **ไม่มีมิติ "ลูกค้าที่ขาย" ที่สะอาด** — ช่อง customer ปนกัน 3 ความหมาย (ship-to code / ชื่อรุ่น / โปรแกรม) | 🔴 blocker |
| G3 | ราคาไม่มี effective date → เปลี่ยนราคาแล้วยอดขายย้อนหลังเพี้ยนทั้งกระดาน | 🟠 |
| G4 | ไม่มีจุด "รับรู้รายได้" ที่ตกลงกันไว้ (chain รอบส่งมี 5 สถานะ + เฟสท้ายตั้งค่าได้) | 🟠 |

| G6 | ข้อมูลจริงบางมาก — order ในระบบมีแค่ **24 วัน** · FG มีต้นทุน **27/128 ตัว** | 🟡 |

## 2. ช่องว่างที่ต้องปิด (เรียงตามความเสี่ยง)

### 🔴 B1 — ราคาขายบน DR project = เปิดให้ anon อ่าน

**ข้อเท็จจริงที่วัดแล้ว:** RLS ของ `parts_master` ฝั่ง DR คือ
`pm_select` (SELECT · role `public` · `qual = true`) · `pm_insert` · `pm_update` (`qual = true`)
คือ **ใครถือ anon key ก็อ่าน/แก้ได้ทั้งตาราง** และ anon key อยู่ในบันเดิลหน้าเว็บ (static site)

และตามกฎเหล็กใน CLAUDE.md: **`supabaseDR` ไม่เคยมี JWT** → จะไปแก้ policy เป็น `TO authenticated` ไม่ได้ (เคยทำพังทั้งระบบมาแล้ว)

⇒ วาง `sell_price` ไว้ข้าง `material_cost` ใน `parts_master` = **ประกาศราคาขายต่อลูกค้าให้ทุกคนที่เปิดเว็บอ่านได้**
(ต้นทุนก็โดนอยู่แล้ววันนี้ — แต่ราคาขายเป็นข้อมูลสัญญาลูกค้า ความอ่อนไหวคนละชั้น)

**3 ทางเลือก:**

| | ทาง | ได้ | เสีย |
|---|---|---|---|
| **A ⭐ แนะนำ** | ตาราง `part_prices` อยู่ **Main project** (authenticated + RLS `has_perm('price:view'/'price:manage')`) · join กับพาร์ทด้วย `mat_no` (text) เหมือนที่ `pe_core_documents` ทำอยู่แล้ว | ปลอดภัยจริง · คุมด้วย `/permissions` ได้ · ได้ audit ฟรีจาก `fn_audit` ฝั่ง Main | join ข้าม project ต้องทำในหน้าเว็บ (fetch 2 ฝั่งแล้วต่อใน memory) — pattern นี้มีใช้แล้วหลายหน้า |
| B | อยู่ DR + Edge Function เป็นด่าน (client ไม่แตะตารางตรง) | พาร์ทกับราคาอยู่ project เดียวกัน | ต้องเขียน+ดูแล edge function · เป็น known gap ที่ทั้งระบบยังไม่เคยทำสักที่ |
| C | อยู่ DR เปิด anon เหมือนตารางอื่น | ง่ายสุด เร็วสุด | **ราคาขายรั่วทั้งหมด — ไม่ควรทำ** |

> **ข้อเสนอ: ทาง A** และถือโอกาสย้าย/มิเรอร์ `material_cost`/`standard_cost` ไปอยู่ชั้นเดียวกันในอนาคต
> (ตอนนี้ยัง ปล่อยไว้ที่เดิมได้ — `defectUnitCost` ทั้งระบบอ่านจาก `parts_master` อยู่ ห้ามหักดิบ)

### 🔴 B2 — ไม่มีมิติ "ลูกค้าที่ขาย" ที่สะอาดพอจะ group ยอดขาย

ราคาขายในอุตสาหกรรมนี้คือ **ราคาต่อ (ลูกค้า × พาร์ท × ช่วงเวลา)** ไม่ใช่ราคาต่อพาร์ทเฉยๆ
พาร์ทตัวเดียวกันขาย FVL / FTM / AAT คนละราคาได้ (กฎ OEE ของระบบเองก็ยอมรับว่า "MAT เดียวกันแตกตามลูกค้า")

**แต่ช่อง `customer` วันนี้ปนกัน 3 ความหมาย:**

| แหล่ง | ค่าจริงที่เจอ | จริงๆ คืออะไร |
|---|---|---|
| `customer_shipping_orders.customer` | `GBJWC` · `GBL9A` · `GRBNA` · `GBJWA` · `GBJWE` · `HPUDA` (6 ค่า + null 2 ใบ) | **ship-to code** (จุดส่ง) |
| `ship_to_plants.customer_name` | AAT · FTM · FVL · ARGENTINA · SOUTH ARFICA · MYANMAR | ปนกัน — บางตัวคือบริษัท บางตัวคือ**ประเทศปลายทาง** |
| `customers` (ทะเบียนใหม่ 2026-09-08) | `FORD` · `FTM` · `AAT` · `GWM` · **`P703 REDBACK 22B`** · **`FORD MY20 U704`** · **`ASSY GOR297`** · `ISUZU RT50` | ปนกัน 3 ชั้น: บริษัท / **รุ่นรถ** / **ชื่องานประกอบ** |

⇒ ถ้าตั้งราคาโดยผูกกับ "customer" ตามที่เป็นอยู่ **ยอดขายจะ group ผิดตั้งแต่วันแรก**
และ `GBJWC` (ARGENTINA) มียอด 131,224 ชิ้น = ก้อนใหญ่สุด ซึ่งเป็น**งานส่งออก → เกือบแน่ว่าไม่ใช่เงินบาท (ดู G7)**

**ต้องแยกให้ขาด 2 ชั้น (ภาษาเดียวกับ SAP):**
- **Sold-to party** = คนที่เราออกบิลให้ ← **นี่คือตัวที่ราคาผูกด้วย**
- **Ship-to party** = จุดส่งของ ← `customer_shipping_orders.customer` ที่มีอยู่ = ตัวนี้

ข้อเสนอ: เพิ่ม `ship_to_plants.sold_to_code` ชี้ไปทะเบียนลูกค้า (สะสาง `customers` ให้เหลือแต่ "บริษัทที่ออกบิลได้" · ย้ายชื่อรุ่น/โปรแกรมไปเป็น field อื่น หรือ `is_billable` flag)
**ห้ามลบแถวทิ้ง** — `dr_products.customer` อ้างชื่อรุ่นพวกนี้อยู่จริง (เป็น text ไม่ผูก FK ตามกฎ 2026-09-08)

### 🟠 G3 — ราคาไม่มี effective date = ยอดขายย้อนหลังเพี้ยนทุกครั้งที่ขึ้นราคา

`material_cost` / `standard_cost` วันนี้เป็น **scalar ตัวเดียว ไม่มีประวัติ** — แก้ทับแล้วของเก่าหายไปเลย
ถ้าราคาขายทำแบบเดียวกัน: ขึ้นราคา ก.ย. → **ยอดขาย ส.ค. ที่ปิดไปแล้วเปลี่ยนตัวเลขตามทันที** = รายงานที่พิมพ์ไปแล้วกับที่เปิดดูวันนี้ไม่ตรงกัน

ระบบมี pattern ที่ถูกต้องอยู่แล้ว — `cost_center_rates` ใช้ `effective_from` + helper `rateFor(rates, cc, refDate)` เลือกแถวล่าสุดที่ ≤ วันอ้างอิง
⇒ **ราคาขายต้องเป็น effective-dated ตั้งแต่วันแรก** (`valid_from` / `valid_to`) และมี `priceFor(prices, mat, soldTo, refDate)` เป็นสูตรกลางตัวเดียว
เพิ่มทีหลัง = ต้องไล่ backfill ราคาย้อนหลังทั้งหมดซึ่งไม่มีใครจำได้แล้ว

**พ่วงมาด้วย:** ราคามัก**ย้อนหลังได้จริง** (เจรจาจบเดือน ต.ค. มีผลตั้งแต่ ก.ค.) → ต้องตอบให้ได้ว่ายอดที่ปิดไปแล้วจะ restate หรือลง adjustment เดือนปัจจุบัน → นำไปสู่ G8 (period close)

### 🟠 G4 — ยังไม่มี "จุดรับรู้รายได้" ที่ตกลงกันไว้

chain รอบส่งคือ `pending → confirmed → prepared → loaded → shipped` และตามกฎเหล็ก 2026-08-26:
- **เฟสท้ายสุด ตั้งค่าได้** (จบที่ `loaded` ก็ได้ เพราะรถ milk run ลูกค้ามารับ)
- **จุดหักสต็อก ตั้งค่าได้** (`shipping_workflow_steps.deducts_stock` — seed ไว้ที่ `prepared` ตาม SAP)
- **สถานะจบใน DB ยังเป็น `'shipped'` เสมอ ห้ามเปลี่ยน**

⇒ ต้องตัดสินว่า **ยอดขายนับตอนไหน** และ**ห้ามผูกติดกับจุดหักสต็อก** (คนละเรื่อง — SAP เองก็หัก stock ตอน prepared แต่ออก invoice ทีหลัง)

| ทางเลือก | ความหมาย | ข้อสังเกต |
|---|---|---|
| ตอน `deducts_stock` | ของออกจากคลัง | ผูกกับ config ที่คนแก้ได้ → ยอดขายขยับตามการตั้งค่า **อันตราย** |
| **ตอนสถานะจบ (`shipped`)** ⭐ | ส่งของครบแล้ว | ตรงกับ ledger ที่มี `ref_shipment_id` · derive ได้จากข้อมูลที่มีอยู่แล้ว |
| ตอนออก invoice | รับรู้จริงทางบัญชี | **ระบบยังไม่มี invoice เลย** (ดู G9) |

**และต้องตอบด้วยว่ายอดขายคิดจาก `qty` ที่สั่ง หรือจำนวนที่ส่งจริง** — ปัจจุบัน `customer_shipping_orders` มีแต่ `qty` ช่องเดียว ไม่มี `qty_shipped` แยก ⇒ **ส่งไม่ครบ = ยอดขายเกินจริงเงียบๆ**

### 🟠 G5 — `parts_master` ไม่มี audit trigger (ผิดกฎ traceability ของโปรเจคเอง)

| ตาราง | `trg_audit` | `trg_set_updated_at` |
|---|---|---|
| `dr_products` | ✅ | ✅ |
| `kanban_standards` | ✅ | ✅ |
| **`parts_master`** | ❌ **ไม่มี** | ❌ **ไม่มี** |

`parts_master` ไม่ได้อยู่ในลิสต์ของ `20260724_audit_log_dr.sql` ทั้งที่มันคือ**ทะเบียนกลางที่ถือต้นทุนต่อชิ้น**

(ตารางนี้ยัง `updated_at` ไม่ขยับเองด้วย ทั้งที่มีคอลัมน์)

⇒ **ต้องปิดช่องนี้ก่อนใส่ราคาขาย** — ข้อมูลการเงินที่แก้แล้วไม่รู้ว่าใครแก้ = ใช้ยืนยันกับบัญชี/ผู้ตรวจไม่ได้

### 🟡 G7 — สกุลเงิน / VAT / Incoterm ยังไม่มีที่อยู่

ลูกค้าที่มี order จริงมี **ARGENTINA · SOUTH AFRICA · MYANMAR** = งานส่งออก
⇒ ราคาน่าจะเป็น **USD** (หรือสกุลอื่น) ไม่ใช่บาททั้งหมด · และยอดที่ผู้บริหารอยากเห็นมักเป็น**บาทรวม**

ที่ยังไม่มีเลย: `currency` · อัตราแลกเปลี่ยนที่ใช้ตอนรับรู้ (ต้อง snapshot ไม่ใช่คำนวณสดทุกครั้ง ไม่งั้นยอดเก่าเปลี่ยนทุกวัน) · VAT/ไม่ VAT · Incoterm (FOB/CIF — ใครออกค่าขนส่ง กระทบว่าราคานั้นรวมอะไร) · ค่าขนส่ง/packaging ที่เรียกเก็บแยก

**ข้อเสนอขั้นต่ำเฟส 1:** เก็บ `currency` (default `THB`) + `fx_rate` snapshot ตอนรับรู้ · ที่เหลือรอ user ยืนยันว่าจำเป็นไหม
**ห้าม hardcode "บาท" ในสูตร** — `fmtBaht()` ใช้แสดงผลได้ แต่ตัวเลขที่เก็บต้องรู้ว่าเป็นสกุลอะไร

### 🟡 G8 — ไม่มีการปิดงวด (period close) → ตัวเลขเปลี่ยนย้อนหลังได้ตลอด

ทุกตัวเลขในระบบวันนี้ derive สดจากข้อมูลดิบ — เยี่ยมสำหรับ operation แต่**ผิดหลักการเงิน**
ถ้ามีคนแก้ order เดือนที่แล้ว / เติมราคาย้อนหลัง / เปลี่ยน ship-to → **ยอดขายเดือนที่ปิดไปแล้วขยับ** โดยไม่มีใครรู้

ต้องมี: ล็อกงวด (เดือนที่ปิดแล้ว = read-only หรือแก้ได้แต่ต้องลง adjustment) + snapshot ยอดที่ปิด + ใครปิด/เมื่อไหร่
`KpiMonthly` (ตาราง KPI × เดือน) จะเจอปัญหาเดียวกันเมื่อผูกกับยอดขาย

### 🟡 G9 — ไม่มีเอกสารฝั่งขาย (invoice / delivery note / ASN)

ระบบมี paperless เกือบครบทุกฟอร์มโรงงานแล้ว (LPA · OJT · Scrap · BBS · ใบเบิก FM-STO-003 …)
แต่**ฝั่งขายยังไม่มีเอกสารสักใบ** — ไม่มีใบส่งของ ไม่มี invoice ไม่มีเลขอ้างอิงที่คุยกับบัญชีได้

⇒ ตอนนี้ยอดขายจะเป็น "ตัวเลขในจอ" ที่**กระทบยอดกับบัญชีไม่ได้** (reconcile ไม่ได้ = ผู้บริหารไม่เชื่อ)
อย่างน้อยต้องมีช่อง **เลขอ้างอิงเอกสารฝั่งบัญชี** (invoice no. / DO no.) ให้คีย์เข้ามาผูกกับรอบส่ง แม้ยังไม่ออกเอกสารเอง

> ⚠️ **ถ้าทำเอกสารพิมพ์/export ใดๆ ต้อง register เข้า `/doc-forms` เสมอ** (กฎบังคับใน CLAUDE.md — seed แถว `doc_forms`, อ่านผ่าน `src/utils/docForms.js`, รายงานภายในอย่างน้อยห่อ `withDocFoot(html, doc_key)`) · **ห้าม hardcode เลขฟอร์ม/Rev/โลโก้**

### 🟡 G10 — สิทธิ์ "ใครเห็นเงินได้" ยังไม่มีคีย์

วันนี้มีแค่ `cost_rate:manage` (สิทธิ์ **แก้** activity rate) — **ไม่มีคีย์คุมการ *มองเห็น* ตัวเลขเงินเลย**
ใครเข้า `/oee-analytics` หรือ `/improvements` ได้ ก็เห็นมูลค่าของเสีย/ต้นทุนทั้งหมด

ราคาขายอ่อนไหวกว่ามาก (leader/operator ไม่ควรเห็นราคาที่ขายให้ Ford) ⇒ ต้องมี:
`price:view` (เห็นราคา/ยอดขาย) · `price:manage` (แก้ราคา) · `sales_report:view` (เห็นสรุประดับบริษัท)
โดย **policy RLS ต้องใช้ `has_perm('<คีย์เดียวกับปุ่มบนจอ>')` ห้าม hardcode role array** (กฎเหล็กข้อ 3 จาก audit 2026-09-04)

## 4. คำถามที่ต้องให้ user ตัดสิน (ก่อนเขียนโค้ดบรรทัดแรก)

1. **ราคาผูกกับลูกค้าไหม** หรือพาร์ทหนึ่งมีราคาเดียวทุกลูกค้า? (ตอบข้อนี้ = ตอบ B2 ไปครึ่งหนึ่ง)
2. **ยอดขายนับตอนไหน** — ส่งของเสร็จ (`shipped`) / ตอนหักสต็อก / ตอนออก invoice?
3. **สกุลเงิน** — งานส่งออก (ARGENTINA/SOUTH AFRICA/MYANMAR) คิดเป็น USD หรือบาท?
4. **ใครควรเห็นราคา** — จำกัดที่ระดับไหน (ผู้จัดการขึ้นไป? เฉพาะ sale + ผู้บริหาร?)
5. **`kpi_raw_inputs` (มี `sales_total` 11 แถว) เป็นของที่ยังใช้อยู่ไหม** — ถ้าใช่ ฟื้นแทนสร้างใหม่ได้เลย
6. **ราคาย้อนหลัง** — เจรจาราคาใหม่มีผลย้อนหลัง จะ restate ยอดเดือนเก่า หรือลง adjustment เดือนปัจจุบัน?
