## 1. ปัญหาที่ dashboard ส่วนงานต้องแก้ (ไม่ใช่ "อยากมีกราฟสวย")

ตอนนี้ระบบมีหน้าวิเคราะห์เยอะแล้ว (`/oee-analytics`, `/factory-map`, `/morning-meeting`, `/dashboard`, `/group-overview`, KPI ในหน้าแจ้งซ่อม, `/store-monitor`)
**สิ่งที่ยังไม่มีคือ "จอเดียวที่ตอบว่า วันนี้ส่วนงานฉันต้องทำอะไร และอะไรกำลังจะเป็นปัญหา"**

**เกณฑ์ตัดสินว่า dashboard ใบไหนคุ้มสร้าง:**
1. ตอบคำถาม **"ต้องลงมือทำอะไร"** ไม่ใช่แค่ "ตัวเลขเป็นเท่าไหร่"
2. **ไม่ซ้ำ**กับหน้าที่มีอยู่ — ถ้าซ้ำ ให้ลิงก์ไปหน้าเดิม ไม่ต้องวาดกราฟใหม่
3. **มีข้อมูลจริงรองรับ** (ดู §2) — dashboard ที่เปิดมาแล้วว่าง คนเลิกใช้ภายในสัปดาห์เดียว

> ### ข้อสรุปสำคัญ
> **ส่วนงานที่ข้อมูลยังไม่มา ไม่ควรได้ "analytics dashboard" — ควรได้ "adoption dashboard"**
> คนละหน้าที่กัน:
> - **Analytics** (ข้อมูลเยอะ): ชี้ว่า *อะไรแย่ ต้องแก้อะไรก่อน* — พาเรโต, เทรนด์, เทียบเป้า
> - **Adoption** (ข้อมูลน้อย): ชี้ว่า *ใคร/ไลน์ไหนยังไม่ได้บันทึก* + ทางลัดไปบันทึก ← ทำให้ข้อมูลเกิด แล้วค่อยอัพเกรดเป็น analytics
>
> เช่น QA เฟสแรก **ไม่ควร**โชว์กราฟ Cpk (measurements = 0 → ว่างเปล่า)
> แต่ควรโชว์ **"วันนี้ 7 ไลน์เดินกะ · มีบันทึกของเสียแค่ 2 ไลน์ · ไลน์ที่เหลือคือของดี 100% จริงหรือยังไม่ได้ลง?"**

## 3. โครงกลางที่ทุก dashboard ใช้ร่วมกัน (สำคัญ — ห้ามทำแยกหน้าใครหน้ามัน)

ตามหลัก single source of truth: **1 component + config ต่อส่วนงาน** ไม่ใช่ 8 หน้าแยก

```
src/pages/DeptDashboard.jsx          ← หน้าเดียว รับ ?dept=production|people|store|...
src/config/deptDashboards.js         ← config: ส่วนงานไหนมีแผงอะไร ใช้ข้อมูลไหน สิทธิ์อะไร
src/components/dash/*.jsx            ← แผงมาตรฐานที่ reuse ข้ามส่วนงาน
```

**เพิ่มส่วนงานใหม่ = เพิ่ม entry ใน config** (pattern เดียวกับ `METRICS` ใน FactoryMap, `TABS` ใน DailyChecker)

### เลย์เอาต์มาตรฐาน 4 ชั้น (ทุกใบเหมือนกัน — คนย้ายแผนกก็อ่านเป็นทันที)

| ชั้น | ชื่อ | หน้าที่ | กติกา |
|---|---|---|---|
| 1 | 🚨 **ต้องทำตอนนี้** | คิวงานค้างที่ *ฉัน* ต้องลงมือ (อนุมัติ/ปิด/ตอบ) | ว่าง = ขึ้น "✅ ไม่มีงานค้าง" ห้ามซ่อนแผง · ทุกแถวคลิกไปหน้าที่ทำงานจริงได้ |
| 2 | 📊 **KPI ส่วนงาน** | 4-6 ตัวเลข พร้อม**เทียบ**เมื่อวาน/สัปดาห์ก่อน/เป้า | ตัวเลขลอยๆ ไม่มีตัวเทียบ = ไม่ผ่าน · ใช้ `kpi-lift` + สี Andon |
| 3 | 📈 **ชี้เป้าให้แก้** | พาเรโต ABC / เทรนด์ / ไลน์ที่แย่สุด | ใช้ `ParetoAbcChart` ตัวกลาง ห้ามวาดพาเรโตเอง |
| 4 | 🔗 **ทางลัด** | ลิงก์ไปหน้าที่ทำงานจริง (พร้อมตัวเลขค้างบนปุ่ม) | ห้ามทำ CRUD ในหน้า dashboard |

### กฎเหล็กของ dashboard ทุกใบ

- **ห้ามคำนวณ KPI เอง** — OEE/A/P/Q/เฉลี่ยถ่วงน้ำหนัก ผ่าน `src/utils/oee.js` · ยอดผลิตนับคู่ RH/LH ผ่าน `pairAwareTotal` · NG ยึด `defect_logs`
- **scope ตามมาตรฐานเดิม** — leader = family ไลน์ตัวเอง · role อื่น = ตาม `sections` · **dropdown ก็ต้องกรอง**
- **สิทธิ์เข้าหน้าเดียว `page:/dept-dashboard`** แล้วแผงในหน้า gate ด้วย `can(resource, action)` → คนเห็นเฉพาะแผงที่ตัวเองมีสิทธิ์ (ไม่ต้อง seed หน้าใหม่ทุกส่วนงาน = เลี่ยงกับดัก `enum_range`)
- **ทุกแผงต้องบอกที่มาและช่วงเวลา** ("กะที่ปิดแล้ว 7 วันล่าสุด") — เลขที่ไม่รู้ที่มา = ไม่มีใครกล้าใช้ตัดสินใจ
- **ข้อมูลไม่ครบต้องพูด** — "3 ไลน์ยังไม่ปิดกะ ตัวเลขจึงยังไม่ครบ" ห้ามโชว์ค่าที่ดูสมบูรณ์ทั้งที่ยังขาด
- **โหลดแบบ lazy ต่อแผง** — ส่วนงานหนึ่งไม่ควรยิง query ของอีก 7 ส่วนงาน

### 4.2 🏢 ฝ่ายผลิต — ระดับส่วนงาน/แผนก (supervisor, manager) 🟢 **แนะนำทำก่อน**

**ผู้ใช้:** หัวหน้าส่วน/ผู้จัดการ (ดู 3-8 ไลน์) · เปิดเช้า-เย็น + ก่อนประชุม
**คำถาม:** *ส่วนงานฉันวันนี้เป็นยังไง · ไลน์ไหนต้องเข้าไปช่วย · มีอะไรรออนุมัติจากฉัน*

**ช่องว่างจริง: ตอนนี้ไม่มีหน้าไหนตอบครบ ต้องเปิด 5 หน้าประกอบเอง**

| ชั้น | เนื้อหา |
|---|---|
| ต้องทำ | **คำขอปิดกะรออนุมัติ** · 4M รออนุมัติ (แยก SV/QA) · Downtime ค้าง >15 นาที · ใบซ่อมที่ไลน์ตัวเองค้าง · action item จากประชุมเช้าที่ยังไม่ปิด |
| KPI (ทั้งส่วนงาน) | ผลิต/เป้า % · **OEE ถ่วงน้ำหนัก** (+ OEE จริง strict) · DT นอกแผน · NG/PPM · คนเข้างาน · OT ที่จองไว้ |
| ชี้เป้า | ตาราง **ไลน์เรียงจากแย่สุด** (ผลิต/เป้า/OEE/DT/NG/คน) · พาเรโต DT ระดับส่วนงาน · เทรนด์ OEE 14 วันแยกไลน์ |
| ทางลัด | ผังรวมโรงงาน · OEE Analytics · ประชุมเช้า · ตารางกะ |

**ข้อมูลพร้อม 100% · สูตรมีครบ · เขียนใหม่เฉพาะการจัดวาง** → คุ้มที่สุด

| CT master ที่น่าสงสัย (%P สูงผิดปกติ >110 หรือต่ำซ้ำ <70 หลายกะ) | prod_orders + CT |
| พาร์ทที่ยังไม่ตั้ง CT / ยังไม่ตั้ง process_type / ยังไม่ตั้ง pair_mat_no | dr_products |
| ไลน์ที่ยังไม่ตั้ง `line_type` / `parallel_stations` | production_lines |
| โปรเจคปรับปรุงที่กำลังทำ + ผลก่อน/หลัง | improvements (ยัง 0) |

**ตัวนี้คือ "dashboard คุณภาพของ master data"** — มีประโยชน์ทันทีเพราะเราเจอปัญหา master ไม่ครบซ้ำๆ (p_no เป็นเลขเครื่อง, line_type ว่าง 13 ไลน์, CT ไม่ตั้ง)

## 6. สิ่งที่ต้องระวัง (จากบทเรียนในโปรเจคนี้)

- **อย่าให้ dashboard กลายเป็นแหล่งความจริงที่ 2** — ทุกตัวเลขต้องมาจากสูตร/หน้าเดิม ไม่งั้นจะเจอ "จอ A ว่า 82% จอ B ว่า 76%" เหมือนที่เคยเกิดกับ OEE
- **อย่ายัดทุกอย่างลงจอเดียว** — เกิน 6 KPI คนอ่านไม่ทัน · เกิน 4 แผงคนเลื่อนไม่ถึง
- **แผงที่ไม่มีใครกดใน 1 เดือน = ตัดทิ้ง** (จดวันที่เพิ่มไว้ในคอมเมนต์จะได้รู้)
- **ข้อมูลน้อย = ต้องบอกตรงๆ ว่าน้อย** ("อิงจาก 7 ใบซ่อม — ยังสรุปแนวโน้มไม่ได้") ห้ามวาดกราฟให้ดูเหมือนมีข้อมูลเยอะ
- **จอ TV กับมือถือคนละโจทย์** — ส่วนงานที่ขึ้นจอ TV (ผลิต) ต้องอ่านจากไกล ฟอนต์ใหญ่ ไม่ต้องกด · ส่วนงานที่ดูบนมือถือ (หัวหน้าเดินไลน์) ต้องกดง่ายนิ้วโป้ง

## 7. ก่อนเริ่มลงมือ ต้องตัดสินใจ 3 เรื่อง (ถาม user)

1. **เริ่มใบไหนก่อน** — แนะนำ "ฝ่ายผลิตระดับส่วนงาน" หรือ "บุคคล & กำลังคน"
2. **หน้าเดียวสลับส่วนงาน (`/dept-dashboard?dept=`) หรือแยก route ต่อส่วนงาน** — แนะนำหน้าเดียว (สิทธิ์ง่าย เพิ่มส่วนงานง่าย)
3. **จอ TV ด้วยไหม** — ถ้าใช่ ต้องมีโหมดฟอนต์ใหญ่ + auto-refresh + ไม่มี interaction ตั้งแต่ออกแบบ
