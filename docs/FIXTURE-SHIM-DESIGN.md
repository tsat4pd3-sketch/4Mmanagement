## 1. โจทย์ที่แท้จริง

Shim record ไม่ใช่ "สมุดบันทึกว่าใส่ชิมกี่แผ่น" — มันคือ **ตัววัดว่า fixture เบี่ยงจาก design intent ไปแล้วเท่าไหร่**

การใส่ชิมคือ **การชดเชย ไม่ใช่การซ่อม** ทุกครั้งที่ใส่ = ยอมรับว่าจิ๊กเสื่อมไปอีกขั้น
ถ้าไม่บันทึกจะเกิด 4 อย่างที่ auditor จับได้:

1. ไม่รู้ว่าห่างจาก baseline เท่าไหร่ — ชิ้นงานผ่าน CMM เพราะชิมชดเชยไว้ ไม่ใช่เพราะ process capable
2. ชิมซ้อนชิม — กะเช้าใส่ 0.2 กะดึกไม่รู้ ใส่เพิ่มอีก 0.3
3. ซ่อมใหญ่/สร้างใหม่แล้วไม่รู้จะกลับไปค่าไหน (as-built หายไปแล้ว)
4. การใส่ชิม = **4M Machine change** แต่ไม่มี traceability ว่ากระทบล็อตไหน

## 4. การนับ shot (จำนวนครั้งที่จิ๊กทำงาน)

### 4.1 หน่วยที่ถูกคือ "shot" ไม่ใช่ "ชิ้น"

การสึกของ locator pin เกิดต่อ **ครั้งที่จับ-ปล่อยชิ้นงาน** ไม่ใช่ต่อชิ้นที่ออก

`fixture_shot_config.pieces_per_cycle` (ระดับ fixture — user ยืนยันว่าพอ):

| รูปแบบ | shot |
|---|---|
| 1:1 | = จำนวนชิ้น |
| 1 ครั้งออก 2 ชิ้น (พาร์ทเดียวกัน) | = ชิ้น ÷ 2 |
| 1 ครั้งออกคู่ RH+LH | = **max(RH, LH)** |

ที่ใช้ `max` เพราะถ้า RH เสีย 5 ชิ้น จิ๊กก็ยังจับ-ปล่อยเท่าจำนวนครั้งของ LH
**`pairAwareTotal` (`src/utils/pairTotals.js`) ใช้ `max` อยู่แล้ว — reuse ห้ามเขียนใหม่**
ข้อมูลจริงยืนยัน: `jigs.part_no` = `MB3B-16C274-C/MB3B-16C275-C` = คู่ RH/LH ในจิ๊กตัวเดียว

### 4.2 🔴 ต้องจับกลุ่มด้วย "เลขพาร์ทลูกค้า" ไม่ใช่ MAT SAP

FG ตัวเดียวแตกหลาย MAT SAP ตามลูกค้า (`10100384` FTM / `10100385` AAT / `10106790` FVL → `RB3B-16E060-BA` เดียวกัน)

**จิ๊กไม่สนใจว่าชิ้นนั้นจะส่งลูกค้าไหน มันจับเหมือนกันทุกชิ้น** → ต้องรวมทุก MAT ที่เป็นพาร์ทเดียวกัน ไม่งั้นนับขาด 2-3 เท่า

> **ไม่ขัดกับกฎ "ห้าม net ข้าม MAT SAP"** — กฎนั้นคุมเรื่อง **สต็อกและออเดอร์**
> (ของเลข A เอาไปส่งแทนเลข B ไม่ได้ ยอด SAP จะเพี้ยน)
> ส่วนนี่คือ **การนับการสึกของเหล็ก** ไม่เกี่ยวกับปลายทางการส่ง — คนละคำถาม รวมได้และต้องรวม

### 4.3 ลำดับความน่าเชื่อถือของการนับ (ห้ามสลับ)

| ลำดับ | วิธี | ความแม่น |
|---|---|---|
| ① | ผูกพาร์ทตรง (`fixture_parts.p_no`) → นับยอดผลิตของพาร์ทนั้น | แม่นสุด |
| ② | อยู่บนผังไลน์ + **ไลน์นั้นผลิตพาร์ทเดียว** → นับยอดทั้งไลน์ | ใช้ได้ |
| ③ | อยู่บนผังไลน์ + ไลน์ผลิตหลายพาร์ท + ไม่รู้ว่าจับตัวไหน | **ตอบว่า "ไม่รู้" ห้ามเดา** |

**ทำไมข้อ ② ใช้เดี่ยวไม่ได้:** LASER-345 มี **16 fixture** ทำคนละพาร์ท
ถ้าเอายอดทั้งไลน์ให้ทุกตัว = เกินจริง 16 เท่า

**ข้อมูลที่ยืนยัน:** HDF1/HDF2 มี **สินค้าผูกไลน์ = 0** (สินค้าผูกกับไลน์แม่ HYDROFORM + มีชั้น OP `90031601`)
⇒ ไลน์ hydroform นับจากไลน์ไม่ได้เลย ต้องผ่านพาร์ท/OP เท่านั้น

### 4.4 ผังไลน์ให้อะไรเพิ่ม

`machine_points` (Main) ผูกด้วย **`line_name` + `machine_no` (text)** → เชื่อมข้าม project ได้

- ให้ **relation กับไลน์** โดยไม่ต้องกรอกซ้ำ (ตามที่ตั้งข้อสังเกตไว้)
- ให้ **ตำแหน่งในสาย** → รู้ว่า fixture อยู่ช่วงไหนของ 1-piece flow (HDF1 → LASER-345 → Assy)
- ระบบมี `part_routings` + ชั้น OP (`is_operation`) รองรับ → เฟส 2 ผูก fixture กับ OP ได้แม่นขึ้น

**เฟส 1 ผูกแค่พาร์ทก่อน** — จิ๊กต้นน้ำ shot จะเกินจริงเล็กน้อยถ้ามีของเสียกลางทาง **ยอมรับได้ แต่ต้องเขียนกำกับบนจอ**

### 4.5 ข้อบังคับการแสดงผล

- **ต้องเขียนกำกับว่าเป็นค่าประมาณจากยอดผลิต ไม่ใช่ตัวนับที่เครื่อง** — ห้ามโชว์ให้ดูแม่นเท่าที่ไม่ใช่
- จุดที่ผูกพาร์ทไม่ได้ = **ตกกลับไปใช้ความถี่ตามเวลาอย่างเดียว + บอกเหตุผลบนจอ** ห้ามเงียบ
- **ห้ามตีเป็น 0 shot** (0 = "ไม่เคยใช้งาน" คนละเรื่องกับ "ไม่รู้")

## 5. ความถี่การตรวจรายจุด (2 แกน)

```
ครบกำหนด = min( last_check_at + interval_days ,
                 วันที่คาดว่า shot สะสมจะถึง interval_cycles )
```

**ต้องบอกด้วยว่าอันไหนเป็นตัวขับ** — ระบบมี pattern นี้แล้วที่ `pm_plans.next_due_reason` ยืมแนวคิดมาใช้ระดับจุด

| แกน | ใช้กับ |
|---|---|
| `interval_days` | สนิม · ยางเสื่อม · โบลท์คลาย — ไม่เกี่ยวกับการใช้งาน |
| `interval_cycles` | เสียดสี · กระแทก — สึกตามการจับ-ปล่อย |

### 5.1 ผลกระทบต่อหน้าตรวจ (ต้องยอมรับ)

จุดครบกำหนดไม่พร้อมกัน → หน้า PM ไม่ใช่ "เช็คลิสต์ตายตัว" แต่เป็น **"รายการที่ครบกำหนดวันนี้"**

- **ต้องมีปุ่ม "ตรวจทั้งใบ" ให้เลือกเสมอ** (ถอดจิ๊กออกมาทั้งตัวแล้ว ตรวจทีเดียวจบคุ้มกว่า)
- ตรวจจุดที่ยังไม่ครบกำหนด = **ต้องนับให้ด้วย แล้วรีเซ็ตรอบของจุดนั้น** ไม่ใช่ทิ้ง
- **backward-compatible:** จุดที่ `interval_days`/`interval_cycles` เป็น null = ตามความถี่ของใบเหมือนเดิมเป๊ะ
  → **98 แผน PM ที่ใช้อยู่ไม่กระทบสักแผน**

## 6. Tool life — อย่าใช้ตัวเลข cycle เป็นเกณฑ์ตัดสิน

ค้นมาตรฐานภายนอกแล้ว (2026-09-01) **ไม่มีมาตรฐานสากลกำหนดอายุ locator pin เป็นจำนวน cycle**
สิ่งที่อุตสาหกรรมใช้จริงคือ **เกณฑ์เชิงมิติ + ความถี่ตามเวลา**:

| เกณฑ์ | ค่า |
|---|---|
| สึกที่เส้นผ่าศูนย์กลางจุดระบุตำแหน่ง → เปลี่ยน | เกิน **0.0005"** (~0.013 mm) |
| clearance pin ↔ รูชิ้นงาน | ไม่เกิน **0.10 mm** |
| engagement depth ลดลง (มี spatter ในบุช) | เกิน 0.1 mm |
| ตรวจด้วยตา (spatter / งอ / แตก) | **ทุกกะ** |
| วัดขนาด | **รายสัปดาห์** |
| เปลี่ยน pin เป็น planned maintenance | **รายไตรมาส** |
| re-certification ทั้ง fixture | เดือนละครั้ง (volume สูง) · ไตรมาส (กลาง) · **ทุกครั้งหลัง crash/ซ่อม** |
| วัสดุ | tool steel D2/A2 ชุบ 58–62 HRC |

**เหตุผลที่ตัวเลข cycle ไม่ portable:** pin ตัวเดียวกันในไลน์ที่ spatter เยอะสึกเร็วกว่าไลน์สะอาดหลายเท่า
และแค่เปลี่ยนไปใช้ pin เคลือบเซรามิก ผู้ผลิตเคลมว่าอายุยืดได้ถึง **14 เท่า**

### 6.1 วิธีที่เสนอ

```
เกณฑ์ตัดสิน  = ค่าวัดขนาด pin (0.013 mm / clearance 0.10 mm)   ← ของจริง
ตัวคาดการณ์  = shot สะสม                                        ← เตือนล่วงหน้า
tool life    = ระบบเรียนรู้จากประวัติของเราเอง
               "pin จุดนี้ เปลี่ยนครั้งที่แล้วตอน 38,400 shot"
```

ตั้ง `default_life_cycles = 30000` ไปก่อนได้ **แต่ให้ระบบเสนอค่าจริงเมื่อมีประวัติเปลี่ยนครบ 3 ครั้ง**
(เสนอ — ไม่แก้ให้เอง ตามหลัก "ระบบเสนอ คนตัดสิน")

- https://industrialmonitordirect.com/blogs/knowledgebase/designing-robot-welding-cells-with-interchangeable-fixtures
- https://www.cncpioneer.com/blog/cnc-locating-pins
- https://techqualitypedia.com/welding-fixture-pm-check-list/

## 7. การกรอกชิม — ค่ารวมคือความจริง

**เก็บ `shim_after_mm` (ค่ารวมหลังทำ) เป็นความจริง · +/- เป็นแค่วิธีกรอก**

หน้าจอ 2 โหมด แต่คำนวณกลับไปหาค่ารวมเสมอ:
- พิมพ์ `+0.2` → แสดง `รวมใหม่ = 0.5 + 0.2 = 0.7` ให้เห็นก่อนกดบันทึก
- พิมพ์ค่ารวม `0.7` → แสดง `(+0.2 จากเดิม 0.5)` ให้ตรวจ

> ⚠️ **ห้ามเก็บ delta เป็นความจริงแล้วบวกสะสม** — พลาดรายการเดียวค่ารวมเพี้ยนตลอดกาลและหาต้นตอไม่เจอ
> เก็บค่ารวมทุกครั้ง = ตรวจนับจริงแล้วพิมพ์ทับได้เลย (`action='recount'`) โดยไม่ต้องคิดย้อน

## 8. Workflow และสิทธิ์

```
ช่างเสนอ/บันทึก  →  วัดก่อน  →  ใส่ชิม  →  วัดหลัง  →  หัวหน้าช่าง JIG อนุมัติ
                                                    ↓
                              เกินเพดาน? → เตือนแรง + ชวนเปิดใบซ่อม MO แทน
```

| permission key | ทำอะไร | seed |
|---|---|---|
| `fixture_shim:record` | บันทึกการใส่/ถอดชิม | admin · manager · mtn |
| `fixture_shim:approve` | อนุมัติ (หัวหน้าช่าง JIG) | admin · manager |
| `fixture_point:manage` | จัดการทะเบียนจุด + baseline + เกณฑ์ | admin · manager · mtn |

> ⚠️ **seed ต้องระบุ role ชัดเจน ห้ามใช้ `enum_range`** — ไม่งั้น role ที่เพิ่มทีหลังเข้าไม่ได้แบบ fail-closed
> ⚠️ ต้องเพิ่มแถวใน **`permission_catalog`** (คอลัมน์ `resource` + `action` แยกกัน ไม่ใช่ `permission_key`)
> `group_name` = 'การตรวจสอบและซ่อมบำรุง' · `sort` ในช่วง 6xx ที่ยังว่าง

**หน้าจอ (ข้อเสนอ — รอเคาะ):** หน้าใหม่ `/fixture` ในหมวดการตรวจสอบและซ่อมบำรุง
สมมาตรกับ `/die-registry` (แม่พิมพ์) · 3 แท็บ: 📋 ทะเบียนจุด · 🔧 บันทึกชิม · 📊 สถานะ
ต้องเพิ่ม `page:/fixture` ใน **`PAGE_GROUPS`** (`PermissionsManagement.jsx`) ในคอมมิทเดียวกับ route

## 9. ตัวชี้วัด sustainability

| ตัวชี้วัด | ใช้ตัดสิน |
|---|---|
| shim stack ปัจจุบัน / เพดาน ต่อจุด | จุดไหนใกล้ตัน = ต้องซ่อมจริง ไม่ใช่ใส่เพิ่ม |

| shim ที่ไม่มีใบอ้างอิง | ช่องโหว่ traceability ที่ auditor จะจับ |

### 9.1 ลูปที่ปิดกับความถี่และคุณภาพ

```
จุดนี้ใส่ชิมบ่อย       →  สึกเร็วกว่าที่ตั้ง interval ไว้
                       →  ระบบ เสนอ ให้ลด interval (ไม่แก้ให้เอง)

                       →  เข้าคิวเปลี่ยนชิ้นส่วน/overhaul ล่วงหน้า

                            →  สูตรมีอยู่แล้วที่ src/utils/capaEffect.js (reuse)
```

## 11. กฎเหล็กของโมดูลนี้

1. **ห้ามสร้างทะเบียน fixture ใหม่** — ตัวตนอยู่ที่ `machines` (`equipment_kind='jig'`)
2. **ค่ารวมคือความจริง delta เป็นวิธีกรอก** — ห้ามบวกสะสมจาก delta
3. **`max_shim_mm = null` = ยังไม่ตั้งเกณฑ์ = ไม่เตือน** ห้ามตีเป็น 0
4. **`baseline_shim_mm` แก้ทับไม่ได้** — แก้ = ออก revision พร้อมเหตุผล
5. **shot เป็นค่าประมาณ ต้องเขียนกำกับบนจอ** — ไม่รู้ = บอกว่าไม่รู้ ห้ามตีเป็น 0
6. **นับ shot รวมทุก MAT SAP ของพาร์ทเดียวกัน** (จับกลุ่มด้วย `p_no`)
7. **งานคู่ RH/LH ใช้ `max` ผ่าน `pairAwareTotal`** ห้ามเขียนสูตรใหม่
8. **จับคู่พาร์ทได้ชัดตัวเดียวเท่านั้นถึงผูกให้** กำกวม = ให้คนเลือก
9. **จุดที่ไม่ตั้งความถี่ = ตามใบเหมือนเดิม** (backward-compatible)
10. **ระบบเสนอ คนตัดสิน** — ไม่ auto-สร้าง 4M, ไม่ auto-ตั้งเกณฑ์, ไม่ auto-แก้ interval
11. **ห้าม backfill `equipment_kind` จากชื่อ** — ให้ช่างชี้เอง
