# 🏷️ เลิกพิมพ์ TAG CARD จาก SAP — ใช้ ESM เป็น Information Signal

> **สถานะ: ออกแบบแล้ว ยังไม่เขียนโค้ด** (2026-08-21 · ไอเดียจาก user + รูปหน้างานจริง)
> เอกสารนี้เป็น "สัญญา" ของโมดูล — เริ่มลงมือเมื่อไหร่ให้อ่านทั้งไฟล์ก่อน แล้วอัพเดทกลับทุกครั้งที่ตัดสินใจต่าง

---

## 1. โจทย์ (คำพูด user)

> *"ทำยังไงไม่ต้อง print tag card จากระบบ SAP ออกมาเพื่อเป็น information signal
> แต่ยังให้ตัวเลขต่างๆ ของ SAP คอนโทรล transaction ตัดจ่าย/โอนยอดในระบบ SAP อยู่
> แต่ใช้ระบบเราเป็น information signal แทน เพื่อสื่อสารกันระหว่าง W/H — Production — Store"*

**สรุปเป็นประโยคเดียว: SAP = ระบบบัญชี (record) · ESM = ระบบสัญญาณ (signal)**
กระดาษทำหน้าที่เดียวคือ "พาข้อมูลไปบอกคนถัดไป" ซึ่งจอทำได้ดีกว่าและไม่มีต้นทุน
ส่วน "ยอดคงเหลือ / ตัดจ่าย / โอนยอด" ยังเป็นของ SAP เหมือนเดิม **ไม่แตะ**

## 4. โมเดลที่เลือก

```
SAP  ── prod order / ยอดคงเหลือ / ตัดจ่าย / โอนยอด ──►  เจ้าของ "ตัวเลขทางบัญชี"
 │
 │  (planner อัพไฟล์รายการ prod order เข้ามา · ทางเดียว · ไม่ต่อ API ในเฟส 1)
 ▼
ESM  ── ใครต้องทำอะไร / ของอยู่ไหน / ถึงแล้วยัง / ขาดไหม ──►  เจ้าของ "สัญญาณ"
 │
 └──►  จอเทียบ: "เคลื่อนไหวใน ESM แล้ว แต่ยังไม่ post ใน SAP"  →  worklist ให้คนไล่เคลียร์
```

### ⚠️ กฎเหล็ก 1 — ห้ามเกิดแหล่งความจริงที่ 3 เรื่องยอด
ระบบมี ledger ของตัวเองอยู่แล้ว (`line_stock_transactions` → `line_stock_summary`)
และยอดนั้น **เพี้ยนจากของจริงอยู่แล้ว** (ขาเข้า 3,384 : ขาออก 33)
→ การเคลื่อนไหวจากสัญญาณใหม่ **ต้องเขียนลง `line_stock_transactions` ตัวเดิมเสมอ**
**ห้ามสร้าง ledger ใหม่ · ห้ามให้บัตรถือยอดของตัวเอง**

### ⚠️ กฎเหล็ก 2 — ESM ไม่ใช่ระบบบัญชี ห้ามทำท่าว่าเป็น
จอที่แสดงยอดต้องเขียนกำกับว่าเป็น **"ยอดตามสัญญาณหน้างาน"** ไม่ใช่ยอด SAP
ไม่งั้นวันหนึ่งจะมีคนเอาไปอ้างแทน SAP แล้วตัวเลขไม่ตรงจนเลิกเชื่อทั้งสองระบบ

### ⚠️ กฎเหล็ก 3 — `prod_no` ≠ PROD.NO. ของ SAP
มันคือ **ID NO ของ tag card** (ดู §2.2) · ถ้าวันหนึ่งจะเก็บเลขใบสั่งผลิตจริง
ให้เพิ่มคอลัมน์ใหม่ **ห้ามเขียนทับ `prod_no`** (ข้อมูลเก่า 8,389 ใบจะกำพร้าทันที)

## 5. เฟส 1 — ขอบเขตที่ user เลือก

**สาย Store → ไลน์ (พาร์ทย่อย 2xx/3xx) · ไม่เชื่อม API SAP · มีจอเทียบให้คนไล่เคลียร์**
แบ่ง 3 ก้อน ทำแยกกันได้ — ก้อน A ไม่ต้องรอ B

### ก้อน A — รายการ prod order ล่วงหน้า (ตัวที่ทำให้เลิกพิมพ์ tag ได้จริง)

**ตารางใหม่ `sap_prod_orders` (DR)**
```
sap_prod_no text      -- PROD.NO. จริงจาก SAP (32140277033)
mat_no text           -- MAT.NO (10100384)
p_no text             -- P/NO เลขลูกค้า (RB3B 16E060 BA)
qty_total integer     -- ยอดทั้งใบสั่ง
qty_per_container int -- QUANTITY บนบัตร = กี่ชิ้นต่อภาชนะ
line_name text        -- ไลน์ที่ผลิต (จาก dr_products.line_name ถ้าไฟล์ไม่มี)
receiver text         -- RECEIVER (W403)
batch_no text
due_date date
status text           -- open | running | done | cancelled
source text           -- upload | manual
uploaded_by / uploaded_at
unique (sap_prod_no, mat_no)
```

**flow:** planner อัพไฟล์ (พรีวิวก่อนเสมอ แบบเดียวกับตัวนำเข้า Parts Master / PE Excel)
→ ผลิตกดปุ่ม **"📋 เลือกจากรายการ"** ข้างปุ่ม Scan เดิมใน Daily Report
→ เห็นเฉพาะรายการของไลน์ตัวเองที่ยังไม่ครบยอด → กดเลือก = เปิดใบ 1 ภาชนะ (เท่า `qty_per_container`)
→ ปิดใบเหมือนเดิมทุกประการ (`prod_orders` โครงเดิม ไม่แตะ) → ครบยอด → `status = done` เอง

**⚠️ ห้ามถอดปุ่มสแกนออก** — ต้องอยู่คู่กันตลอด (บัตรเก่ายังค้างหน้างาน · ไฟล์ยังไม่อัพ · ไลน์ที่ยังใช้กระดาษ)
ถอดเมื่อไหร่ = บังคับให้ทุกไลน์เปลี่ยนพร้อมกัน ซึ่งจะพัง

**⚠️ ต้องกันเปิดเกินยอด** — เลือกจากจอง่ายกว่าสแกน จึงกดเกินง่ายกว่า
ครบยอดแล้วต้องเตือน (**ไม่บล็อกแข็ง** — หน้างานมีเคสผลิตชดเชยของเสีย) และนับ over ให้เห็น

### ก้อน B — สัญญาณ Store ↔ ไลน์ (ไม่มีตารางใหม่)

1. **ลงข้อมูลรอบส่งให้ครบตามตู้จริง (8 รอบ/วัน)** — งานข้อมูล ไม่ใช่โค้ด
2. **จอ "Waiting Post" ที่จำลองตู้ PW KANBAN** — ช่องตามช่วงเวลา บัตรที่ถึงคิววางในช่องนั้น
   ต่อยอดบนบอร์ด `/heijunka` ที่ระเบิด demand เข้ารอบส่งอยู่แล้ว **ห้ามสร้างบอร์ดใหม่**
3. ป้าย QR ที่ชั้นวาง/กล่อง → สแกนเรียกเติม ใช้ pattern เดิมของ `/rack-center`
   (deep-link เปิดฟอร์มกรอกครบ เหลือกดยืนยัน) · เพิ่มชนิดใหม่ที่ `QR_KINDS` ใน `src/utils/qrCode.js` **จุดเดียว**
4. Store กดจ่าย (`type='issue'`) → ผลิตกดรับ (full/partial) — กลไกเดิมทั้งหมด

### ก้อน C — จอเทียบกับ SAP (ทำคู่กับ A เสมอ ห้ามทิ้งไว้ทีหลัง)

- **เคลื่อนไหวใน ESM แล้ว แต่ยังไม่ post SAP** → คิวให้คนไปคีย์
- **prod order ที่ planner อัพมา แต่ไม่มีการเคลื่อนไหวใน ESM เลย** → ของหลุดสายตา

**⚠️ ไม่มีจอนี้ = ของจะหายทางบัญชีเงียบๆ** เพราะสัญญาณเดินหน้าแต่ SAP ไม่รู้เรื่อง

## 8. เริ่มลงมือเมื่อไหร่ ให้เช็คกฎพวกนี้

- **กฎ MAT prefix** — แยกประเภทด้วย **เลขตัวแรกตัวเดียว** ผ่าน `src/utils/matPrefix.js` ห้ามเทียบ 3 หลัก
- **กฎชั้น Operation** — พาร์ทที่ติดธง `is_operation` ห้ามเข้าคลัง / ห้ามเข้า BOM / ห้ามเข้า kanban
- **กฎ rename ไลน์** — ตารางใหม่ที่เก็บ `line_name` ต้องไปเติมใน `handleRenameLine` (LineSetup.jsx)
- **กฎ 1000 แถว** — query ที่โตเกิน 1000 ต้อง `.range()` เสมอ
- **กฎ `.in()`** — ดึงแถวลูกด้วย id ต้องผ่าน `fetchByIds` (แบ่งก้อน 120 + แบ่งหน้า 1000)
- **กฎ egress** — จอที่ refresh เอง ใช้ `usePolling` + `RATE.*` · master ผ่าน `cachedMaster`
- **กฎ audit** — ตาราง master ที่แก้ได้ ต้องผูก audit + มีคอลัมน์ `updated_by_name` (ฝั่ง DR)
- **กฎ permission** — หน้าใหม่ต้องเติม `PAGE_GROUPS` · action ใหม่ต้อง insert `permission_catalog`
  · **เลี่ยงได้ให้ reuse key เดิม** (`products:edit` / `line_stock:issue`) กันกับดัก seed `enum_range`
- **กฎ migration** — เขียนแล้วต้อง apply แล้วบันทึกวันที่ apply ใน CLAUDE.md ทันที
- **กฎ tolerant** — คอลัมน์ additive ที่อาจยังไม่ apply ต้องเช็ค `error` แล้วขึ้น toast **ห้าม `try{}catch{}` เปล่า**

## 9. คำถามที่ยังไม่มีคำตอบ (ถามก่อนเริ่มข้อ 3)

1. **ไฟล์ที่ export จาก SAP หน้าตายังไง** — คอลัมน์อะไรบ้าง ชื่อคอลัมน์ภาษาอะไร
2. **ตาราง V5 (8 รอบ) ตัวเลขจริงคืออะไร** — อ่านจากรูปยังไม่ชัด ต้องขอไฟล์/ถ่ายใกล้
3. planner ปล่อย prod order ล่วงหน้ากี่วัน (กระทบว่าจอควรโชว์ช่วงไหน)
4. `qty_per_container` มาจากไหน — ไฟล์ SAP มีให้ หรือใช้ `parts_master.qty_per_pkg` ที่มีอยู่แล้ว
5. ใบสั่งที่ผลิตไม่ครบแล้วถูกยกเลิกฝั่ง SAP — planner บอกระบบยังไง (อัพไฟล์ทับ / กดยกเลิกในจอ)
6. **PW kanban ที่ยังใช้กระดาษอยู่ — จะเลิกด้วยไหม หรือคงไว้** (เฟสนี้ตั้งใจคงไว้)
