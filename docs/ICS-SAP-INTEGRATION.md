### Master Data ของ ICS (ทั้งหมดมีแค่นี้)
`Line` · `Component Material` (MAT SAP) · `Description` · **`Mvt` (Movement Type)** ·
`Qty` · **`Origin SLOC`** (ต้นทาง) · **`Receive SLOC`** (ปลายทาง)

⇒ **มันคือ "แม่แบบ transfer posting ของ SAP ต่อ (ไลน์ × พาร์ท)" ไม่ใช่ master สินค้า**
คนกรอกเอง **ไม่ได้ sync มาจาก SAP**

### Flow (5 ขั้น)
```
1. Assy เบิก      เลือกรอบเวลา → เลือกไลน์ → สแกน MAT SAP หลายรายการ → "Sent"
                  ⇒ ได้ "ใบจอง" เลขที่ YYYYMMDD+running4  (เช่น 2023 01 27 0013)
2. Store เตรียม   print ใบจอง (ต้องใช้ PC) → ไปจัดของ
3. Store จ่าย     สแกนบาร์โค้ดใบจอง 1 ครั้ง → สแกน MAT ตามจำนวนที่จ่ายจริง → "Sent"
4. Assy รับ       สแกนใบจอง → สแกน MAT ที่รับ (จากใบคัมบังเหลือง / Tag One-way) → "Sent"
5. ปิดใบ          กด "Sent to SAP"  ← จุดเดียวที่ข้อมูลออกจาก ICS
```
**จ่ายไม่ครบ = สแกนเท่าที่จ่ายจริง แล้วให้ Assy เบิกรอบถัดไป** (ระบบรองรับ partial)
**ห้ามสแกนเกินที่เบิก — "ระบบจะไม่สามารถโยนไปหา SAP ได้"**

## 2. 🔴 ICS ต่อ SAP ยังไง (หัวใจของคำถาม)

```
ICS  ──เขียน Text File──►  SAP T-code ZMME0003 (staging/inbound)
                                    │
                          batch auto-sweep ตามรอบ
                                    ▼
                       transfer posting  Origin SLOC → Receive SLOC
                          (backup ไฟล์ที่ T-code AL11)
```

| | TSAT / TSESA | TSPT |
|---|---|---|
| รอบกวาด | **ทุก 1 ชั่วโมง** | **5 รอบ/วัน** 08:00 · 13:00 · 18:00 · 22:00 · 02:00 |

**Error handling:** ถ้าใน `ZMME0003` มีข้อความในช่อง `Message` = ยอดใน SAP ไม่พอ
→ ต้องให้ **QA ปลดงาน** ก่อน (เจ้าหน้าที่สโตร์ต้องเข้าไปตรวจ T-code เอง)

> ### ⚠️⚠️ ข้อสรุปที่สำคัญที่สุด — **ICS ไม่ได้ "อ่าน" อะไรจาก SAP เลย**
> มันเป็น **ท่อทางเดียว (write-only, file-drop + batch)** ไม่ใช่ API สองทาง
> ⇒ **"เกาะ ICS เพื่อได้ข้อมูลจาก SAP" ทำไม่ได้ เพราะ ICS เองก็ไม่มีข้อมูลนั้น**
>
> สิ่งที่ ICS ถืออยู่มีแค่: master ที่คนกรอกเอง + ประวัติใบจอง/สแกนจ่าย/สแกนรับ
> **ไม่มี**: ยอดคงเหลือ (MB52) · material master · BOM · PO/PR · MRP · ราคา/ต้นทุน · order ลูกค้า

## 4. ทางเลือก 4 ทาง

### 🅰️ ขอ read-only จาก SAP ตรง — **ตรงกับสิ่งที่ user อยากได้ที่สุด**
ไม่ต้องผ่าน ICS เลย ขอ IT ให้อย่างใดอย่างหนึ่ง:
- SAP OData / RFC read-only (stock, material master, BOM, PO)
- **หรือถูกกว่า:** export ไฟล์รายวัน (MB52 stock · material master · BOM) วาง share drive → เรา import
✅ ได้ข้อมูลจริงจาก SAP · ✅ ไม่เสี่ยงเขียนอะไรผิด · ❌ ต้องขออนุมัติ IT/Security

### 🅱️ เกาะ `ZMME0003` แบบเดียวกับ ICS (write path)
เราเขียน text file รูปแบบเดียวกันลง AL11 directory → SAP กวาดให้
✅ **แก้ปัญหาคีย์ 2 ที่ + ปิดรูขาออกที่เราค้างอยู่** · ❌ **ยังไม่ได้ข้อมูลจาก SAP** (ทางเดียวเหมือนเดิม)
ต้องมี: สิทธิ์เขียนไฟล์บน SAP app server · spec layout ของไฟล์ · IT เพิ่ม source ใหม่ใน Z-program

> #### 🔴 ความเสี่ยงที่ใหญ่ที่สุดของทาง B — **ตัดสต็อกซ้ำ 2 เท่าใน SAP**
> ถ้าทั้ง ICS และ ESM ยิงเข้า `ZMME0003` สำหรับของก้อนเดียวกัน = SAP ตัดสองรอบ
> **ต้องเลือกเจ้าของการโพสต์ให้ชัดเจนก่อนเสมอ — ห้ามเปิดทั้งคู่**
> (คู่ขนานกับปัญหาที่เรามีอยู่แล้ว: `child_lot_requests` ปิดล็อต vs สแกนปิดใบ = สต็อกโผล่ 2 ที่)

### 🅲 ขอ read access เข้า **ฐานข้อมูลของ ICS** — **quick win ที่เป็นไปได้จริงที่สุด**
ICS เป็น .aspx = มี DB (น่าจะ SQL Server) เก็บใบจอง + สแกนจ่าย/รับ ทั้งกลุ่ม
✅ ได้ **"ขาออกที่เกิดจริง"** ซึ่งเป็นรูใหญ่สุดของเราตอนนี้ (`issue` 5,908 : `consume` 40)
✅ ได้ mapping `Line × MAT → Mvt/SLOC` มาใช้ต่อฟรี · ❌ ยังไม่ใช่ข้อมูล SAP โดยตรง

### 🅳 อยู่เฉยๆ ใช้คู่กัน (สถานะของ TSPT/TSESA วันนี้)
คนคีย์ 2 ที่ต่อไป — ❌ ตรงข้ามกับเป้าหมายของโปรเจค

## 5. คำแนะนำ + คำถามที่ต้องถาม `TSG.App` ก่อน

**ลำดับที่แนะนำ: 🅲 → 🅰️ → 🅱️** (ได้ข้อมูลก่อน ค่อยพูดเรื่องเขียนกลับ)
เพราะ 🅲/🅰️ **อ่านอย่างเดียว = ไม่มีทางทำ SAP พัง** จึงขออนุมัติง่ายกว่ามาก
ส่วน 🅱️ แตะบัญชีสต็อกจริง ต้องมีเจ้าของชัดเจนก่อนเสมอ

### คำถามที่ต้องได้คำตอบ
1. **TSAT4 (โรงเรา) เปิดใช้ ICS อยู่แล้วหรือยัง?** — คู่มือเป็นของ TSAT และ IT เขียนเอง
   ถ้ามี instance อยู่แล้วแค่โรงเรายังไม่เปิด → ทุกอย่างง่ายขึ้นมาก
2. ICS เก็บข้อมูลใน DB อะไร · ขอ **read-only view/replica** ได้ไหม
3. `ZMME0003` รับ input ได้จากแหล่งเดียว (ICS) หรือหลายแหล่ง · layout ของ text file เป็นอย่างไร
4. SAP มี **OData/API อ่านสต็อก (MB52) / material master / BOM** ให้ระบบภายในเรียกไหม
   ถ้าไม่มี — ขอ **export รายวันเป็นไฟล์** ได้ไหม
5. ถ้าจะให้ ESM โพสต์เข้า SAP แทน ICS สำหรับไลน์ที่ ESM ดูแล — **ต้องปิดฝั่ง ICS ของไลน์นั้นอย่างไร** ไม่ให้ตัดซ้ำ

## 6. ⚠️ กฎที่ต้องยึดถ้าวันหนึ่งได้ต่อจริง

หลักเดียวกับที่ตกลงไว้เรื่อง SCADA (`docs/SCADA_REALTIME_DESIGN.md`):
**SAP = เจ้าของบัญชีสต็อกทางการ · ESM = เจ้าของกระบวนการหน้างานและสูตรทั้งหมด**

- **ห้ามให้ ESM คำนวณยอดสต็อกแล้วเขียนทับ SAP** — ยิงเฉพาะ "เหตุการณ์ที่เกิดจริง" (จ่าย/รับ เท่าไหร่ เมื่อไหร่)
- **ห้ามโชว์ยอดจาก SAP คู่กับยอดที่เราคำนวณโดยไม่บอกว่าตัวไหนคือตัวไหน** — 2 ตัวเลขที่เถียงกันเอง
  ทำให้คนเลิกเชื่อทั้งคู่ (บทเรียนเดิมของโปรเจคทุกครั้งที่มีตัวเลข 2 ชุด)
- **การโพสต์เข้า SAP ต้อง idempotent + มี marker กันซ้ำ** (precedent: `child_demand_explosions`
  ที่กันการระเบิด BOM ซ้ำตอนถอยใบแล้วสแกนปิดใหม่)
- **โพสต์ล้มเหลวห้ามเงียบ** — ต้องมีคิว/สถานะให้เห็นบนจอ + ให้คนกดยิงซ้ำได้
  (แบบเดียวกับช่อง `Message` ใน ZMME0003 ที่ต้องมีคนไปตรวจ)
- **ยิงตอน "คนยืนยัน" ไม่ใช่ตอนระบบเดาว่าเสร็จ** — ICS ก็ทำแบบนี้ (Assy กด "Sent to SAP" เอง)

## 7. สิ่งที่ควรหยิบมาใช้ทันที ไม่ต้องรอต่อ SAP

1. **เก็บรหัส SLOC ของ SAP ในระบบเรา** — ตอนนี้เรามี `move_code` แล้ว แต่ยังไม่มี Origin/Receive SLOC
   เพิ่มลงทะเบียนพาร์ท/ไลน์ = พร้อมต่อทันทีวันที่ได้ท่อ และมีประโยชน์กับใบเบิกกระดาษด้วย
2. **ยืนยันกติกา prefix → SLOC** (`2xx`→S101 · `3xx`→S102) ตรงกับ `matPrefix.js` ของเราอยู่แล้ว
3. **รูปแบบเลขใบจอง `YYYYMMDD+running`** ใช้กับ `material_requests.doc_no` ได้เลย (สื่อสารกับคนที่ชินกับ ICS ง่ายขึ้น)
4. **ลำดับ "Store สแกนจ่าย → Assy สแกนรับ" เป็น 2 ขั้นแยกกัน** — ของเรายังมีขั้นเดียว
   2 ขั้นนี้คือสิ่งที่ทำให้ยอดตรงกันจริง (ทั้งสองฝ่ายยืนยัน) และเป็นที่มาของ "จ่ายไม่ครบ" ที่ track ได้
