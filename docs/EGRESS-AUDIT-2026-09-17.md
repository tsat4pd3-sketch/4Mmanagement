## 1. บทเรียนวิธีวัด — สิ่งที่ทำผิดมา 2 รอบ

รอบ 15-16/09 ผมจัดลำดับความสำคัญจาก **จำนวน request** ต่อ path
แล้วสรุปว่า `production_sessions` (10,952 ครั้ง/วัน) คือตัวใหญ่สุด

**นั่นผิด** — Supabase คิด egress เป็น**ไบต์** ไม่ใช่จำนวนครั้ง
`production_sessions?select=line_name,status` = **0.5 KB/ครั้ง**
`mtn_orders?select=*` = **1,590 KB/ครั้ง** (ต่างกัน **3,000 เท่า**)

⇒ ตารางอันดับตามจำนวน request **ชี้ผิดตัวเกือบทั้งใบ**

### กับดักที่ทำให้มองไม่เห็น

| กับดัก | อาการ | ทางออกที่ใช้จริง |
|---|---|---|
| **PostgREST ไม่ส่ง `Content-Length`** (chunked) | `edge_logs` รวมไบต์ REST ได้ **0.1 MB จาก 68,910 req** ⇒ ดูเหมือนคิวรีไม่กิน egress เลย | วัดเองจากฝั่ง DB: `octet_length(json_agg(t)::text)` ของคิวรีจริง |
| `request.search` ถูกมองข้าม | ไม่รู้ว่าแต่ละ path เลือกคอลัมน์อะไร | group by `(path, request.search)` → ได้ตัว `select=*` โผล่มาเอง |
| เน็ตใน session ของ AI ต่อ `*.supabase.co` ไม่ได้ (proxy 403) | วัด gzip จริงไม่ได้ | ใช้ `pg_column_size()` บน temp table = pglz (อนุรักษ์นิยมกว่า gzip) เป็นตัวแทน |

**กฎที่ตกผลึก:** เวลาไล่ egress ให้จัดอันดับด้วย **(จำนวนครั้ง × ไบต์ต่อครั้ง)** เสมอ
ห้ามจัดอันดับด้วยจำนวนครั้งอย่างเดียว

## 4. ตัวการอันดับ 2 — รูปผังเป็น PNG

| ไฟล์ | ขนาดจริง |
|---|---:|
| `layouts/layout_LINE_APRON_ASSY_*.png` | **8.4 MB** |
| `layouts/layout_test_*.png` | 3.0 MB |
| `layouts/layout_LINE_MAIN_TSRA_2_*.png` | 2.5 MB |
| `factory/map_*.png` | 2.4 MB |
| `layouts/layout_HYDROFORM_*.png` | 2.3 MB |
| `jig-images/facility/*.png` (ผังเครื่องจักร) | 1.1 MB |

**สาเหตุ:** โค้ดส่งเข้า `imageCompression({ maxSizeMB: 2.5, maxWidthOrHeight: 2560, initialQuality: 0.9 })`
แต่ **ไม่ระบุ `fileType`** ⇒ ไลบรารีคืนชนิดเดิม = **PNG ซึ่งเป็น lossless** ⇒ `maxSizeMB` แทบไม่มีผล

**สิ่งที่ห้ามทำ:** ลดความละเอียดลง — มีคอมเมนต์เตือนไว้ในโค้ดอยู่แล้วว่า *"อย่าลดกลับไป 1600px/0.5MB เคยเบลอ"*
ผังต้องซูมอ่านชื่อสถานี/เลขเครื่องได้

**วิธีแก้:** `src/utils/layoutImage.js` → `compressLayoutImage()`
**คงความละเอียด 2560px เท่าเดิม แต่แปลงเป็น WebP** (เก็บ alpha ได้ · เล็กกว่า PNG ~70-85% ที่คุณภาพเท่ากัน)
· รองรับจอ TV ที่ใช้จริง (webOS 23 = Chromium 94 · WebP มีตั้งแต่ Chrome 32)
· ⚠️ **กับดัก:** Safari < 16.4 เขียน WebP ไม่ได้แล้ว**เงียบๆ คืน PNG** ⇒ ฟังก์ชัน derive นามสกุลจาก
`blob.type` ที่ได้จริงเสมอ ห้ามตั้ง `.webp` ล่วงหน้า (ไม่งั้นได้ไฟล์ PNG ชื่อ .webp = รูปเสีย)

จุดที่แก้แล้ว: `LineSetup` (ผังไลน์) · `FactoryMap` (ผังโรงงาน) · `MtnMachineLayout` (ผังเครื่องจักร)

> **⚠️ แก้โค้ดช่วยเฉพาะรูปที่อัปใหม่** — รูปเดิมยังเป็น PNG ก้อนโตอยู่
> ต้องมีตัว re-compress ของเดิม (ดู §6 งานค้าง)

## 5. cacheControl — ตรวจแล้ว ไม่ใช่ปัญหา

ทุก object ที่ตรวจมี `max-age=31536000` (1 ปี) ครบ — งาน `uploadOpts()` + migration backfill 11/09 ทำงานถูกต้อง

## 5c. รอบ 2 (21/09) — รูปจุดตรวจ PM เป็น WebP

หลังตัด `mtn_orders` ออก **ก้อนใหญ่สุดที่เหลือกลายเป็น Storage ฝั่ง DR**:

| โฟลเดอร์ | ครั้ง/วัน | เฉลี่ย/ใบ | รวม/วัน |
|---|---:|---:|---:|
| **`jig-images/jigs/`** (รูปจุดตรวจ PM + เฟรมหมุน) | 1,033 | 89 KB | **90.1 MB** |
| `mtn-images/after` + `before` (รูปซ่อม) | 241 | ~165 KB | 39 MB |

ของที่เก็บอยู่: **1,014 ไฟล์ = 102 MB** (JPEG 676 ใบ @111 KB · PNG 338 ใบ @88 KB)

**สิ่งที่ทำ:** `compressPhotoImage()` (WebP · 2000px · q0.85) ที่จุดอัปโหลดทั้ง 2 ใน `PMSetup.jsx`
(เฟรมหมุน + รูปอ้างอิงจุดตรวจ) และเพิ่มรูปกลุ่มนี้เข้าตัวบีบของเก่า

**⚠️ ต่างจากรูปผัง: รูปพวกนี้ถูกบีบมาแล้วรอบหนึ่ง** (JPEG คุณภาพต่ำ) ⇒ บีบ lossy ซ้ำ = เสียคุณภาพซ้ำซ้อน
จึง **ไม่ลดความละเอียดเพิ่ม** + quality สูง (0.85) — ขนาดที่ลดมาจากการเปลี่ยน**ฟอร์แมต** ไม่ใช่การทิ้งรายละเอียด

**⚠️ กับดักของกลุ่มนี้ (ไม่มีในรูปผัง):**
- **path เดียวถูกอ้างจาก 3 ตาราง** — `jig_images` · `jigs` · `jig_checkpoints`
  ⇒ ต้อง update ครบทั้ง 3 ก่อนลบไฟล์เก่า ไม่งั้นรูปหายจากจอใดจอหนึ่งแบบไม่รู้ตัว
- **มีเป็นพันไฟล์ ไม่ใช่ 20 ใบ** ⇒ ทำทีละ `RECOMPRESS_BATCH = 150` · คืน `remaining` ให้กดซ้ำ
- **กดซ้ำต้องปลอดภัย** ⇒ ไฟล์ที่เป็น `.webp` แล้วถูกข้าม**ก่อนโหลดลงมา** (ไม่เสีย egress ซ้ำ)

### 🔴 บทเรียนวิธีวัด (รอบที่ 2 ที่ผมพลาดเรื่องเดิม)

§6 เวอร์ชันก่อนเขียนว่า `child_lot_requests` = **55 MB/วัน** — **ผิด**
ผมเอา **ไบต์ดิบ** (39.8 KB) × จำนวนครั้ง ทั้งที่ของจริงถูก**บีบก่อนส่ง**

วัดใหม่ด้วย `pg_column_size` (บีบแล้ว) ของวันที่ 21/09 ครึ่งวัน:

| คิวรี | ครั้ง (ครึ่งวัน) | บีบแล้ว/ครั้ง | รวม |
|---|---:|---:|---:|
| `child_lot_requests select=*` | 852 | 8.3 KB | **6.9 MB** |
| `production_sessions select=*` + join | 526 | 6.6 KB | 3.4 MB |
| `downtime_logs` รายการเปิดค้าง | 2,265 | 0.9 KB | 2.0 MB |

⇒ **ทั้งวันก็แค่ ~14 / 7 / 4 MB** — ไม่ใช่ 55 MB

**กฎเพิ่ม:** `octet_length()` = ไบต์ดิบ **ห้ามเอาไปคูณจำนวนครั้งตรงๆ**
ต้องผ่าน `pg_column_size()` (หรืออย่างน้อยหารด้วยอัตราบีบ ~4×) ก่อนเสมอ
— ใช้ "ไบต์ดิบ" ได้เฉพาะตอน**เทียบ 2 ทางเลือกของคิวรีเดียวกัน** (full vs slim) ซึ่งอัตราบีบใกล้กัน

### สถานะจริงหลังรอบ 2

**ไม่มีคิวรีตัวไหนเหลือที่ใหญ่พอจะเป็นเป้าอีกแล้ว** — ตัวโตสุด ~14 MB/วัน
ก้อนที่เหลือคือ **long tail + overhead ต่อ request** (~69,000 req/วัน × หัว ~1.5 KB ≈ 100-130 MB/วัน)

⚠️ **ห้ามไปไล่ตัด `select('*')` ของ `production_sessions` ใน Daily Report เพื่อประหยัด ~4 MB/วัน** —
40 คอลัมน์นั้นป้อน `computeOEE` + จอหลักของทั้งโรงงาน · **risk/reward ไม่คุ้ม** (ต่างจาก `mtn_orders`
ที่เป็น 116 คอลัมน์ × 628 MB/วัน)
