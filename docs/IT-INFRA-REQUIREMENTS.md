**แปลว่ามีอุปกรณ์ระหว่างทางตอบแทน** — พร็อกซี / ไฟร์วอลล์ / SSL inspection / ผู้ให้บริการอินเทอร์เน็ต

## 4. 🔴 สิ่งที่ขอจากทีม IT (เรื่องเร่งด่วน — ชั้นเครือข่าย)

### 4.1 ปลายทางที่ต้องเปิดให้ออกได้ (allowlist) — TCP 443 ทั้งหมด

| โดเมน | ใช้ทำอะไร | ถ้าโดนบล็อก |
|---|---|---|
| `ewhdfqwfwofivojtsizn.supabase.co` | ฐานข้อมูลหลัก (ผู้ใช้/สิทธิ์) | **ล็อกอินไม่ได้เลย** |
| `eyhclzkifitbhbljgoav.supabase.co` | ฐานข้อมูลการผลิต | เปิดกะ/ลงยอดไม่ได้ |
| `*.supabase.co` (เผื่อ storage/auth ย่อย) | รูปภาพ/ไฟล์แนบ | รูปไม่ขึ้น |
| โดเมนของ Render (ที่ตั้งหน้าเว็บ) | ตัวหน้าเว็บ | เปิดแอปไม่ได้ |
| `fonts.googleapis.com` · `fonts.gstatic.com` | ฟอนต์ | ตัวหนังสือเพี้ยน (ไม่ถึงกับพัง) |

### 4.2 WebSocket ต้องผ่านได้ (`wss://`)
ระบบใช้ **Realtime** เพื่ออัปเดตจอหน้างานทันทีโดยไม่ต้องกดรีเฟรช
- ต้องอนุญาต **HTTP Upgrade → WebSocket** ไปยัง `*.supabase.co`
- ต้องไม่ตัดการเชื่อมต่อที่ **idle** (จอ TV เปิดค้าง 24 ชม. ต้องต่อค้างได้)
- ถ้าพร็อกซีตัด idle ให้บอกค่า timeout มา เราจะตั้ง heartbeat ให้พอดี

### 4.3 🔴 พร็อกซี/ไฟร์วอลล์ **ห้ามตอบ 5xx แทนปลายทาง**
นี่คือหัวใจของรอบที่ 3 — ขอให้ IT ตรวจว่ามีอุปกรณ์ตัวไหน
- ตอบ **502/503/504** แทนเมื่อปลายทางช้าหรือคิวเต็ม
- ทำ **SSL/TLS inspection** แล้วมีเพดานจำนวน session
- มี **rate limit ต่อ IP** (เราออกทาง IP เดียว ~800 คำขอ/นาทีตอนพีค — ดูเหมือน DoS ได้ง่าย)
- มี **connection limit / keep-alive** ต่ำเกินไป

ถ้ามีข้อใดข้อหนึ่ง ขอ **ยกเว้น (bypass) โดเมนในข้อ 4.1** ออกจากการตรวจ

### 4.4 แบนด์วิดท์และคุณภาพสาย
- โหลดไม่สูงมาก (คำขอส่วนใหญ่เป็น JSON ขนาดเล็ก) แต่ **จำนวนคำขอเยอะและถี่**
- สิ่งที่สำคัญกว่าแบนด์วิดท์คือ **ความเสถียร + ค่า latency ที่ไม่กระโดด** (ปลายทางสิงคโปร์ ปกติ ~30–60 ms)
- ขอทราบ: ความเร็ว/ผู้ให้บริการปัจจุบัน · มีสายสำรองไหม · ตัดสลับอัตโนมัติหรือเปล่า

### 4.5 DNS
- ขอให้ใช้ DNS ที่เชื่อถือได้ และ **ไม่ทำ DNS filtering กับ `*.supabase.co`**

### 4.6 🔴 ขอ log ที่ "ขอบเครือข่าย" ไว้สืบย้อน
ตอนนี้เวลามีปัญหา **เราพิสูจน์ไม่ได้ว่าใครตอบ error** เพราะฝั่งคลาวด์ไม่เห็นคำขอนั้นเลย
ขอให้ IT เปิด/เก็บ log ของพร็อกซีหรือไฟร์วอลล์สำหรับโดเมนในข้อ 4.1 (เวลา · status code · ปลายทาง)
เก็บย้อนหลังอย่างน้อย **7 วัน** — ครั้งหน้าจะชี้ได้ใน 5 นาทีแทนที่จะเดา

### 4.7 เครื่องลูกข่าย
- **จอ TV หน้างานเป็น webOS (Chromium 94)** — ระบบทดสอบให้รองรับรุ่นนี้อยู่แล้ว **ห้ามอัปเกรด/เปลี่ยนจนกว่าจะแจ้ง**
- PC/PDA: เบราว์เซอร์ Chromium รุ่นใหม่ ใช้ได้ปกติ

## 5. ถ้าจะย้ายมาโฮสต์ในบริษัท (เป้าหมายระยะยาว)

### 🔴 ข้อเท็จจริงที่ต้องเคลียร์ก่อนคุย
**"ย้ายมาโฮสต์เองแล้วจะไม่เจอปัญหาเน็ต" — ไม่จริงทั้งหมด** ต้องแยกเป็น 2 ชั้น:

| ย้ายอะไร | ช่วยเรื่องเน็ตไหม |
|---|---|
| **A. ย้ายแค่หน้าเว็บ (static)** | ❌ **ไม่ช่วยเลย** — เบราว์เซอร์ยังยิงตรงไป `supabase.co` อยู่ดี |
| **B. ย้ายฐานข้อมูลเข้ามาด้วย** | ✅ ช่วย (ทุกอย่างอยู่ใน LAN) แต่ **ความเสี่ยงย้ายมาอยู่ที่เราเต็มตัว** |

### 5.1 ทางเลือก A — ย้ายเฉพาะหน้าเว็บ
- เครื่อง/VM เล็กมาก: **2 vCPU · 4 GB RAM · 50 GB SSD** (แค่เสิร์ฟไฟล์ static + HTTPS)
- ได้ประโยชน์: ไม่ต้องพึ่ง Render · คุมรอบ deploy เอง · เปิดแอปเร็วขึ้นเล็กน้อย
- **ไม่ได้**: ความทนทานเรื่องเน็ต (ข้อ 4 ยังต้องทำอยู่ดี)

### 5.2 ทางเลือก B — ย้ายฐานข้อมูลเข้ามาด้วย (self-host)

**สเปคเครื่องที่ประเมินจากโหลดจริง + เผื่อ SCADA:**

| รายการ | ขั้นต่ำ | แนะนำ | เหตุผล |
|---|---|---|---|
| CPU | 8 vCPU | **16 vCPU** | พีค 13 คำขอ/วิ. + realtime + งานคำนวณกลางคืน |
| RAM | 16 GB | **32 GB** | PostgreSQL + PostgREST + Realtime + cache |
| ดิสก์ | 500 GB NVMe | **1 TB NVMe (RAID 1)** | DB วันนี้ 243 MB แต่ SCADA โต ×113–450 · ต้องเผื่อ WAL + backup |
| เครือข่าย | 1 Gbps LAN | 1 Gbps + สำรอง | |
| ไฟ | **UPS** | UPS + เครื่องปั่นไฟ | ไฟดับกลางเขียน = ฐานข้อมูลเสียหาย |
| สำรองข้อมูล | นอกเครื่อง ทุกวัน | **นอกอาคาร + ทดสอบกู้คืนจริงทุกเดือน** | |

**🔴 เงื่อนไขที่ต้องมี "ก่อน" ย้าย — ไม่ครบ ห้ามย้าย:**
1. **มีคนรับผิดชอบชัดเจน** (patch · ต่ออายุใบรับรอง · เฝ้าดิสก์/แรม · กู้คืน)
2. **ทดสอบกู้คืนจากไฟล์สำรองได้จริง** อย่างน้อย 1 ครั้ง ไม่ใช่แค่มีไฟล์สำรอง
3. **เข้าจากนอกโรงงานได้** (หัวหน้า/ผู้บริหารเปิดจากมือถือนอกสถานที่เป็นเรื่องปกติ) → VPN หรือ reverse proxy + TLS
4. **แผนรับเหตุ:** เครื่องล่มตอนตี 2 ใครกู้ · กี่ชั่วโมงถึงกลับมา

> ⚠️ ตอนนี้ **ทั้งโรงงานพึ่งระบบนี้เปิดกะ** — ระบบล่ม = เปิดกะไม่ได้
> การย้ายเข้ามาเอง **เพิ่มงานดูแลถาวร** แลกกับการตัดความเสี่ยงเรื่องเน็ต ต้องชั่งน้ำหนักร่วมกัน
