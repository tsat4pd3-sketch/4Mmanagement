## 2. สาเหตุราก — ระบบยัด **4 คำถาม** ลงใน **2 ช่อง**

| คำถามจริง | วันนี้เก็บที่ไหน | ปัญหา |
|---|---|---|
| ① **ใคร** | `employees` | ✅ ชัดแล้ว |
| ② **อยู่หน่วยไหน** | `org_nodes` + `profiles.section` | ⚠️ **เพดานคือ "ส่วนงาน"** |
| ③ **ทำฟังก์ชันอะไร** (ผลิต/คุณภาพ/ซ่อมบำรุง/วางแผน/วิศวกรรม) | **ไม่มีช่อง** — ซ่อนอยู่ใน*ชื่อ* `role` (`qa`,`mtn`,`planner_store`,`engineer`) | 🔴 ต้นเหตุเคส QA |
| ④ **ระดับชั้นไหน** (operator→leader→หัวหน้าส่วน→หัวหน้าแผนก→ผจก.) | ซ่อนอยู่ใน*ชื่อ* `role` เหมือนกัน (`leader`,`supervisor`,`manager`) | 🔴 ชนกับ ③ |

**③ กับ ④ ถูกบีบให้อยู่ช่องเดียวกัน** ⇒ เลือกได้อย่างเดียว
คนเป็น *หัวหน้าส่วนของฝ่ายคุณภาพ* ต้องเลือกว่าจะเป็น `supervisor` (ได้ระดับชั้น เสียฟังก์ชัน)
หรือ `qa` (ได้ฟังก์ชัน เสียระดับชั้น) — **เลือกทางไหนก็ผิดครึ่งหนึ่ง** นี่คือ "มั่ว" ที่ user เห็น

> 💡 **QA เป็นฟังก์ชันที่ตัดขวางทุกส่วนงาน (cross-cutting)** — เหมือน Maintenance และ Planning
> ระบบรู้เรื่องนี้อยู่แล้วบางส่วน (`FACTORY_WIDE_ROLES = ['qa']` ใน `sectionScope.js`)
> แต่ไปผูกกับ**ชื่อ role** แทนที่จะเป็น**ฟังก์ชันของคน** ⇒ พอเปลี่ยน role ก็หลุดทันที

## 3. เพดานที่ชนแน่ตอนขยายเป็นกลุ่มธุรกิจ

วัดจริง 30/10 — `org_nodes` มี **4 ชั้น** เท่านั้น:

```
section (10 ราก · ไม่มีแม่)  →  department (27)  →  line (27)  →  team (24)
```

🔴 **ไม่มีโหนด "โรงงาน" · "กลุ่มธุรกิจ" · "บริษัท" เลย** — โรงงานเป็นสิ่งที่ *อยู่ในใจ* ไม่ได้อยู่ในฐาน
⇒ เติมโรงงานที่ 2 เข้ามา ส่วนงานชื่อ `PD1` จะชนกันทันที และ `profiles.section = 'PD1'` จะไม่รู้ว่าโรงงานไหน

**ลำดับชั้นที่ต้องการจริงตามที่ user อธิบาย:**

```
บริษัท (Thai Summit Group)
└── กลุ่มธุรกิจ (เหล็ก · และกลุ่มอื่น)
    └── โรงงาน (TSAT Plant 4 · โรงงานอื่น)
        └── ส่วนงาน (PD1…PD4 · QA · Maintenance …)   ← เพดานปัจจุบันอยู่ตรงนี้
            └── แผนก → ไลน์ → ทีม
```

### ข่าวดี — ของที่ scale ได้อยู่แล้ว
- 🟢 **`org_nodes.parent_id` เป็น tree อยู่แล้ว** — เติมชั้นบนได้โดยไม่ต้องรื้อ (แค่ให้ section มี `parent_id`)
- 🟢 **Cost Center เป็นคีย์ระดับบริษัทอยู่แล้ว** (`214055654` = 9 หลัก · ของ SAP) —
  นี่คือแกนที่ข้ามโรงงานได้จริง และระบบมี `src/utils/ccScope.js` + `canWriteScope()` รองรับแล้ว
- 🟢 **กฎ "ลำดับชั้นมาจาก `parent_id` เท่านั้น เลขรหัสไม่ได้บอกชั้น"** ถูกเขียนไว้แล้วใน CLAUDE.md ✅
- 🟢 **`employees.position`** เก็บระดับชั้นจริงไว้แล้ว (`operator`/`technician`/`officer`/`engineer`/
  `section_head`/`dept_head`/`manager`) — **มีข้อมูลแล้ว แค่ยังไม่ถูกใช้ตัดสินสิทธิ์**

### ของที่ขาด
- 🔴 ชั้น **plant / business_group / company** ใน `org_nodes.kind`
- 🔴 ช่อง **"ฟังก์ชัน"** ของคน (production / quality / maintenance / planning / engineering)
- 🔴 ชั้นบนของ `section` — วันนี้ 10 ส่วนงานเป็นราก ⇒ ไม่มีอะไรบอกว่าอยู่โรงงานไหน
- ⚠️ ข้อมูลเพี้ยนที่เจอระหว่างทาง: `DIE Maintenance` เป็น `department` ที่**ไม่มีแม่** (ควรอยู่ใต้ส่วนงาน)

## 4. 🎯 แบบที่ user กำหนด — **"สิทธิ์ต้องมองจาก ใครอยู่ตรงไหนของผังองค์กร แล้วค่อยดูเลเวลของพนักงาน"**

> คำสั่ง user 2026-10-30 (แทนข้อเสนอเดิมของ session ที่แยก "ฟังก์ชัน" เป็นช่องใหม่ — **ไม่ต้องมีช่องใหม่**)

```
สิทธิ์ = f( โหนดที่คนนี้ผูกอยู่ , เลเวลของคนนี้ )
         └── employees.org_node_id      └── employees.position
```

**ชั้นที่ 1 — อยู่ตรงไหนของผัง** (`org_node_id`) ตอบ 2 อย่างพร้อมกัน **โดยไม่ต้องกรอกอะไรเพิ่ม**
- **ฟังก์ชัน** = สายที่โหนดเราอยู่ (ไล่ `parent_id` ขึ้นไป) — อยู่ใต้ `QA` ⇒ งานคุณภาพ · ใต้ `PD3` ⇒ งานผลิต
- **ขอบเขต** = กิ่งใต้โหนดของเรา

**ชั้นที่ 2 — เลเวล** (`position`) ตอบว่า *ทำอะไรได้ในกิ่งนั้น*
- `manager` / `section_head` / `dept_head` / `line_leader` = **หัว** ⇒ ขอบเขต = **ทั้งกิ่งใต้โหนดตัวเอง**
- `engineer` / `qc` / `technician` / `officer` / `operator` = **สมาชิก** ⇒ ขอบเขต = **โหนดตัวเอง**

🔑 **ไม่ต้องตั้ง `sections` · `scope_depth` · `resp_cost_centers` ด้วยมืออีก** — derive ทั้งหมด
(3 ช่องนี้กลายเป็น "ค่าทับพิเศษ" สำหรับเคสยกเว้น ไม่ใช่ทางหลัก)

### 🔁 แก้แบบให้ถูก — **user ท้วงถูก: "กว้างเกิน" คือกว้างใน "เรื่อง" ไม่ใช่ "พื้นที่"** (30/10)

⇒ ต้องมี **3 แกน ไม่ใช่ 2**:

```
ทำ X กับแถวนี้ได้ไหม
```

## 5. เคส QA วันนี้ — แก้ได้ทันทีโดยไม่ต้องรอสถาปัตยกรรมใหม่

ปัญหาเฉพาะหน้าคือ **5 บัญชี** ที่เป็นชุดสิทธิ์ `supervisor` ในส่วน QA
(พิชิต · อุบลรัตน์ · ศุภภิสรา · ศราวุธ · เฉลิมขวัญ) ⇒ ไม่มีใบผ่านข้ามหน่วย

> 🔴 **เป็น product decision — ห้ามแก้ให้เอง** (CLAUDE.md: *"คนต้องเป็นคนตัดสินว่าใครควรเห็นแค่ไหน"*)

**3 ทางที่เป็นไปได้ (ให้ user เคาะ) — ทางที่ 3 คือแบบ §4 ที่ user กำหนดแล้ว:**
1. **ย้าย 5 บัญชีไปชุดสิทธิ์ `qa`** — ได้ใบผ่านข้ามหน่วยทันที · เสี่ยงน้อยสุด ·
   แต่ *เสียความหมายของระดับชั้น* (หัวหน้าส่วนกับ QC กลายเป็นชุดเดียวกัน) = เลื่อนปัญหาออกไป
2. **ออกชุดสิทธิ์ใหม่ `qa_head`** (= `qa` + คีย์ของหัวหน้า) — ตรงความจริงกว่า
   แต่ **เพิ่ม role ที่ 16** = เดินต่อในทางที่ทำให้มั่วตั้งแต่แรก
3. **ทำขั้น 1–2 ของ §4** (ฟังก์ชัน × ระดับชั้น) — แก้ที่ราก ใช้ซ้ำได้กับ MTN/Planning และระดับกลุ่มธุรกิจ
   แต่กินเวลาและต้องพิสูจน์กับทะเบียนจริงก่อน merge

📌 ระหว่างยังไม่เคาะ **ห้ามแก้ role ของใครเงียบๆ**
