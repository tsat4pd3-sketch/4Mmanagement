## 0. ปรัชญา — 3 ประโยค

1. **โค้ดถูกอ่านและแก้บ่อยกว่าถูกเขียน** — เขียนให้คนที่มาทำต่อ (รวมถึงตัวเราอีก 3 เดือน) เข้าใจ *เจตนา* ไม่ใช่แค่ทำงานได้
2. **แก้ที่ "ต้นเหตุ" ไม่ใช่ที่ "อาการ"** — อาการเดียวกันโผล่จอที่ 2 เมื่อไหร่ แปลว่ารอบแรกแก้ผิดที่
3. **ทุกการแก้ต้องตอบได้ว่า "ถ้าพรุ่งนี้มีอีก 10 เคสแบบนี้ ระบบรับได้ไหม"** — ถ้าคำตอบคือ "ต้องมาแก้โค้ดอีก" แปลว่ายังไม่จบ

> **มาตรฐานของโปรเจคนี้:** ระบบนี้ไม่ใช่โปรเจคจบ — มีคนใช้จริงทุกกะทุกวัน มีหลาย session ทำงานขนานกัน
> และกำลังจะขยายไปหลายบริษัท **"แก้ให้จบเคสนี้พอ" คือการสร้างหนี้ที่คนอื่นต้องจ่าย**

## 2. แยก "ปัญหาข้อมูล" ออกจาก "ปัญหาโค้ด" ให้ขาด

**อาการหน้าจอผิด ≠ โค้ดผิดเสมอไป** — โปรเจคนี้เจอ "ปัญหาข้อมูล" บ่อยกว่าปัญหา logic

| เคสจริง | ดูเหมือน | ที่จริงคือ | สิ่งที่ทำ (ถูก) |
|---|---|---|---|
| ใบ Scrap พิมพ์ PART NO. เป็นหมายเลขเครื่อง | บั๊กการพิมพ์ | `dr_products.p_no` ถูกกรอกเป็นเลขเครื่อง (SP-72/74…) | **ไม่แก้ข้อมูลให้เงียบๆ** → ตรวจเจอแล้ว **เตือนบนจอ** + ปล่อยช่องว่างให้กรอกเอง + บอกว่าไปแก้ที่ไหน |
| PM Setup กับ PM ตรวจสอบ ลิสต์เครื่องไม่ตรงกัน | logic คนละชุด | เกณฑ์ 2 หน้าต่างกันโดยธรรมชาติ (มี checklist vs ลงทะเบียนแล้ว) | ไม่ยัดให้เท่ากัน แต่ **ทำให้เห็นส่วนต่าง** (บล็อกส้ม "มีจุดตรวจแล้วแต่ยังไม่ลงทะเบียน N เครื่อง" + ลิงก์ไปจัดการ) |
| ชิป "ปั๊ม" ไม่มีไลน์เลย | ฟิลเตอร์พัง | 13 ไลน์ยังไม่ตั้ง `line_type` | รายงานให้ user ตัดสินใจ **ไม่ไปเดา/เขียนข้อมูลแทน** |

**กฎ:**
- **ห้ามให้ระบบ "เดาแล้วเขียนข้อมูลแทนคน"** ในเรื่องที่เป็นการตัดสินใจของคน (เช่น เครื่องไหนต้องตรวจทุกกะ, ไลน์นี้เป็นประเภทอะไร)
- แต่ **ห้ามเงียบ** — ต้องมีจุดบนจอที่บอกว่า "ข้อมูลตรงนี้ยังไม่ครบ N รายการ · ไปตั้งที่หน้า X"
- ก่อนแก้โค้ด **ไปดูข้อมูลจริงก่อนเสมอ** (`select ... group by` เร็วกว่านั่งเดา 1 ชั่วโมง)

## 3. Single source of truth — กฎข้อที่สำคัญที่สุดของโปรเจคนี้

> **ถ้าค่า/สูตร/รายการเดียวกันถูกใช้มากกว่า 1 ที่ → ต้องมี "จุดเดียว" ที่เป็นเจ้าของ**

**เคสจริงที่เจ็บที่สุด:** สูตร OEE เคยกระจายอยู่ 4 ไฟล์ + เขียนซ้ำในหน้า → **แต่ละจอโชว์ตัวเลขคนละชุด** ผู้บริหารถามว่าอันไหนจริง ตอบไม่ได้
→ รวมเป็น `src/utils/oee.js` ไฟล์เดียว (A/P/Q/OEE/OOE/TEEP/เฉลี่ยถ่วงน้ำหนัก/CT/break policy/Lean) **และห้ามแตกไฟล์ util OEE เพิ่ม**

**ตัวอย่างที่ทำแล้วในโปรเจคนี้ — ใช้เป็นแบบ:**

| เรื่อง | จุดเดียวที่เป็นเจ้าของ | เคยพังแบบไหนตอนไม่มี |
|---|---|---|
| สูตร OEE/A/P/Q/ค่าเฉลี่ย | `src/utils/oee.js` | 4 จอตัวเลขไม่ตรงกัน |
| ชื่อ/สี/ไอคอน role | `src/utils/roleMeta.js` | label ซ้ำ 4 ไฟล์ แล้ว drift |
| ตำแหน่งงาน (position) | `src/utils/positions.js` | 3 หน้าคนละลิสต์ (อังกฤษ/ไทยปนกัน) |
| ขนาด marker บนผัง | `src/utils/markerScale.js` | ตอน setup กับตอนแสดงผลขนาดไม่เท่ากัน |
| กำลังคนมาตรฐาน | `src/utils/stdManpower.js` | 3 หน้าตอบ "ไลน์นี้กี่คน" ไม่ตรงกัน (14/28/ทิ้งไลน์แม่) |
| ทีมช่าง / ประเภทกระบวนการ | `mtn_teams` / `process_types` (ตาราง) | hardcode 4-5 หน้า เพิ่มทีมทีต้องไล่แก้ |
| เลขฟอร์ม/Rev เอกสาร | `doc_forms` + `utils/docForms.js` | เลขฟอร์ม hardcode กระจาย แก้ทีต้อง deploy |

**วิธีทำเวลาเจอโค้ดซ้ำ:**
1. ย้าย logic ไป `src/utils/<domain>.js` เป็น **pure function** (ทดสอบง่าย ไม่ผูก UI/DB)
2. แก้ **ทุกจุด** ที่เคยเขียนเองให้เรียก util (ห้ามทิ้งของเก่าไว้ครึ่งทาง — จะ drift อีก)
3. เขียนหมายเหตุในไฟล์ util ว่า "จุดใหม่ที่ทำเรื่องนี้ให้เรียกตัวนี้ ห้ามเขียนเอง"
4. บันทึกใน CLAUDE.md ว่าใครเป็นเจ้าของเรื่องนี้

## 4. Data-driven ก่อน Hardcode เสมอ

**คำถามตัดสิน: "รายการนี้มีโอกาสเพิ่ม/แก้โดยคนที่ไม่ใช่โปรแกรมเมอร์ไหม"** → ถ้าใช่ ต้องอยู่ในตาราง ไม่ใช่ array ในโค้ด

| ควรอยู่ใน DB (แก้เองได้) | อยู่ในโค้ดได้ (คงที่จริง) |
|---|---|
| ประเภท downtime/ของเสีย · ทีมช่าง · กระบวนการผลิต · หมวดอะไหล่ | สูตรคำนวณ (OEE, kanban) |
| สิทธิ์ role × permission · ห้อง Telegram · กฎแจ้งเตือน | โครงสร้าง workflow ที่มีกฎธุรกิจตายตัว (4M 7 ขั้น) |
| เลขฟอร์ม/Rev/ช่องลายเซ็น · เป้า OEE · ปฏิทิน/วันหยุด | ค่าคงที่ทางฟิสิกส์/มาตรฐาน (นาทีต่อกะ, เกณฑ์ ABC 80/95%) |

**ถึงจะ hardcode ก็ต้องรวมไว้จุดเดียว + ทำให้ "เพิ่มของใหม่ = เพิ่ม 1 บรรทัด" ไม่ใช่ก็อปโค้ดทั้งบล็อก:**
- `METRICS` ใน FactoryMap → เพิ่ม metric ใหม่ = เพิ่ม entry เดียว การ์ด/สี/ป้ายตามให้เอง
- `TABS` ใน DailyChecker → เพิ่มระบบเช็คใหม่ = เพิ่ม entry
- `ORG`/`ZONES`/`LTYPES` ใน GroupOverview → เพิ่มบริษัท/โซน/ประเภทไลน์ = เพิ่ม entry ที่เดียว การ์ด/อันดับ/แผนที่/ตารางตามเอง

**กับดักที่เจอจริง:** seed สิทธิ์ด้วย `enum_range(user_role)` = ล็อกรายชื่อ role ณ วันนั้น → role ที่เพิ่มทีหลัง **เข้าหน้าใหม่ไม่ได้แบบเงียบๆ**
→ เวลา seed อะไรที่อิง "ทุกค่าในอีนัม" ให้คิดเสมอว่าอีนัมจะโตอีก

## 5. ออกแบบให้ "ขยาย" ได้ ไม่ใช่แค่ "ใช้ได้"

**คิดล่วงหน้า 1 ก้าว — ไม่ใช่ 10 ก้าว** (over-engineer ก็เป็นหนี้อีกแบบ) เกณฑ์ที่ใช้จริง:

- **ก้าวถัดไปที่ "เห็นอยู่แล้ว" ต้องรองรับตั้งแต่แรก** เช่น ระบบเดิมทำมาเพื่อโรงเดียว แต่รู้ว่าจะมีหลายบริษัท → เวลาแตะโครงลำดับชั้น ให้เผื่อชั้นบนไว้ (`org_nodes` มี `parent_id` อยู่แล้ว = เพิ่ม `kind` ใหม่ได้ ไม่ต้องสร้างตารางใหม่)
- **ก้าวที่ยังไม่เห็น ไม่ต้องสร้างของรองรับ แต่ต้อง "ไม่ปิดประตู"** — เลี่ยงสมมติฐานที่ถอนยาก เช่น อย่าฝัง "1 โรงงาน" ลงใน primary key
- **เขียน "ยังไม่ทำ (เฟสถัดไป)" ไว้ในเอกสารเสมอ** — โปรเจคนี้ทำแล้วหลายที่ (Transport, PM Forecast, Traceability GAP, QA→SPC) คนที่มาต่อจะได้ไม่ต้องเดาว่าตั้งใจไม่ทำ หรือลืม

**ตัวอย่างการตัดสินใจที่ "เผื่ออนาคต" อย่างถูกต้อง (จากหน้า mockup หลายบริษัท):**
- ไม่สร้างตาราง `plants` ใหม่ → เสนอขยาย `org_nodes.kind` (โครงเดิมรองรับ)
- ตารางรายวัน (session/order/downtime/defect) **ไม่ต้องแก้เลย** เพราะสืบบริษัทผ่านไลน์ได้ → blast radius เล็กมาก
- ตัวเลขในหน้าใหม่ใช้ **สูตรกลางเดิม** → ค่าตรงกับหน้าที่มีอยู่โดยอัตโนมัติ ไม่ต้องมาไล่ปรับทีหลัง

## 6. เปลี่ยนแปลงแบบ "ถอยได้" (backward-compatible by default)

**กฎ migration ของโปรเจคนี้:**
1. **Additive ก่อนเสมอ** — เพิ่มคอลัมน์/ตาราง/แถว ไม่ลบ ไม่เปลี่ยนความหมายของคอลัมน์เดิม
2. **คอลัมน์ใหม่ต้องมี default หรือ nullable** + โค้ดต้องทำงานได้ทั้ง "apply แล้ว" และ "ยังไม่ apply"
3. **ลบของเก่าเป็นขั้นตอนแยก** ทำหลังยืนยันว่าไม่มีใครใช้แล้ว (โปรเจคนี้เก็บ `document_controls`, `mtn_mo_counter`, `model_path` ไว้เป็น vestigial โดยตั้งใจ)
4. **เขียน migration file ลง `supabase/migrations/` เสมอ** — ห้ามแก้ schema ผ่าน UI/MCP เฉยๆ แล้วไม่ทิ้งร่องรอย
5. **งานที่ย้อนยาก (drop column, เปลี่ยน RLS, migrate ข้อมูล)** → หยุดถาม user ก่อน + เขียน `docs/ROLLBACK_*.md`

> ### ⚠️ กับดักสำคัญ: "tolerant code" ที่เงียบเกินไป
> โปรเจคนี้เขียนโค้ดแบบ best-effort (try/catch, retry ตัดคอลัมน์ที่ไม่มี) เพื่อให้ยังไม่ apply migration แล้วไม่พัง — **ดีแล้ว**
> **แต่เคสจริง:** migration `line_type` ค้างไม่ได้ apply 2 สัปดาห์ ระหว่างนั้น **หน้า LineSetup เซฟช่องนี้ไม่ติดแบบเงียบๆ** แล้วขึ้น "บันทึกสำเร็จ"
> **กฎที่ได้:** tolerant ได้ แต่ต้อง **บอกผู้ใช้ว่าอะไรถูกตัดทิ้ง** ("ยังบันทึกช่อง X ไม่ได้ — ยังไม่ได้ apply migration") · เงียบ = โกหกผู้ใช้

## 7. คิดเผื่อ scale ตั้งแต่วันแรก (ข้อมูล / จอ / คน)

- **ข้อมูล:** Supabase ตัดที่ **1000 แถว/query** ถ้าไม่ `.range()` → ตารางที่โตได้ (role_permissions โตเกิน 1000 แล้ว) **ต้อง paginate** ไม่งั้นสิทธิ์ที่ seed ทีหลังหายเงียบ = fail-closed
- **จอ:** รายการเกินหลักร้อยแถว **ห้าม render แบน** → drill-down (สรุป → เจาะ) + จำกัดแถวแรก + ปุ่ม "แสดงอีก N" **ห้ามตัดข้อมูลเงียบ**
- **คน:** ฟีเจอร์ที่หลายแผนกใช้ → คิดเรื่อง **สิทธิ์ (permission) + ขอบเขตข้อมูล (scope)** ตั้งแต่ออกแบบ ไม่ใช่ patch ทีหลัง
  - หน้าใหม่ = seed `page:/route` + กรองข้อมูลตาม scope + **กรอง dropdown ด้วย** (เคยพลาด: ข้อมูลกรองแล้วแต่ dropdown ยังโชว์ไลน์ข้ามส่วนงาน)
- **เวลา:** ค่าที่ stamp ไว้แล้ว (OEE ตอนปิดกะ) **ห้ามคำนวณใหม่ย้อนหลังด้วย master ปัจจุบัน** — CT/นโยบายพักเปลี่ยนไปแล้ว จะได้คนละชุดกับที่หัวหน้าเซ็นไป
  ถ้าจำเป็นต้อง backfill: พิสูจน์ก่อนว่าแถวไหน stamp ด้วยสูตรเก่า (เทียบค่าที่คำนวณซ้ำได้) แล้วแตะเฉพาะแถวนั้น + idempotent

## 8. Blast radius & Rollback — คิดก่อนกด merge

**ทุกครั้งที่ merge เข้า main (= deploy จริง) ต้องมีครบ 3 อย่าง:**
1. **build ผ่าน** (`npm run build` — มีด่าน lint กฎ crash ในตัว **ห้าม bypass**)
2. **พิสูจน์ว่าไม่กระทบส่วนอื่น** — ไล่ทุกจุดที่พึ่งพาสิ่งที่แก้ (grep ทั้ง `src/`, เช็คทั้ง 2 Supabase project, เช็ค trigger/view/RLS)
3. **rollback พร้อม** — จด SHA ก่อน merge + วิธีย้อน (`git revert -m 1 <merge-sha>`) + ถ้ามี migration ระบุลำดับที่ปลอดภัย (revert โค้ดก่อน แล้วค่อยแตะ schema)

**สัญญาณว่า blast radius ใหญ่กว่าที่คิด (ให้หยุดแล้วออกแบบใหม่):**
- ต้องแก้ไฟล์เดียวกัน 5+ จุดด้วย pattern เดียวกัน → ควรเป็น util/helper
- ต้องแก้ >3 หน้าให้ "ตรงกัน" → ควรเป็น component/config กลาง
- ต้องแตะ RLS หรือ policy หลายตารางพร้อมกัน → **หยุด** (เคยทำพังทั้งฝั่ง DR มาแล้ว — client ฝั่งนั้นเป็น anon ไม่มี JWT)

## 9. เขียนโค้ดให้คนอ่านออกว่า "ทำไม" ไม่ใช่แค่ "ทำอะไร"

- **คอมเมนต์ต้องบอกเหตุผล/ข้อจำกัด/เคสที่เคยพัง** ไม่ใช่แปลโค้ดเป็นภาษาไทย
  - ❌ `// วนลูปไลน์` → ✅ `// นับซ้ำไม่ได้: แม่ตั้ง std ไว้แล้ว ลูกต้องเป็น 0 (เคสจริง LASER E50 มี 1 คน ทำ HYDROFORM กลายเป็น 28)`
- **หัวไฟล์ของ component/หน้าใหม่** เขียน 5-10 บรรทัดว่า: ทำอะไร · ใครใช้ · ข้อจำกัด · ของที่ห้ามทำ
- **ค่าคงที่ต้องมีที่มา** — `STRICT_WARN_SHARE_PCT = 5` ต้องบอกว่าทำไม 5
- **ตั้งชื่อให้ตรงความจริง** — ตาราง `jigs` จริงๆ คือ "ทะเบียนอุปกรณ์ที่มีแผน PM" (ชื่อหลอกตามาหลายรอบ) → ถ้าตั้งชื่อผิดไปแล้วแก้ไม่ได้ **ต้องเขียนกำกับไว้ในเอกสาร**

## 10. เอกสารคือส่วนหนึ่งของงาน ไม่ใช่ของแถม

**กฎถาวรของโปรเจคนี้: แก้อะไร → อัพเดทกฎในคอมมิทเดียวกัน**

| แก้อะไร | ต้องอัพเดทที่ |
|---|---|
| pattern ที่ใช้ร่วมหลายหน้า (marker/สี/modal/ตาราง) | `docs/UI-CONVENTIONS.md` + วันที่ |
| schema / ตาราง / Edge Function / workflow / กฎธุรกิจ | `CLAUDE.md` section ที่เกี่ยวข้อง |
| สิทธิ์/role | `docs/PERMISSIONS-DESIGN.md` |
| เจอกับดัก/บั๊กที่คนถัดไปน่าจะเจอซ้ำ | `CLAUDE.md` (ส่วนกับดัก) — **ข้อนี้สำคัญที่สุด** |
| หลักการทำงาน/วิธีตัดสินใจ | ไฟล์นี้ |

**"เอกสารที่ผิดแย่กว่าไม่มีเอกสาร"** — ถ้าเปลี่ยนพฤติกรรมระบบแล้วปล่อยเอกสารเก่าไว้ คนถัดไปจะเชื่อของเก่าแล้วทำพัง

**สิ่งที่ควรบันทึกทุกครั้งที่ตัดสินใจอะไรที่ "เลือกทางใดทางหนึ่ง" (mini-ADR):**
```
เรื่อง: <ตัดสินใจอะไร>            วันที่: YYYY-MM-DD
บริบท: <ปัญหา/ข้อจำกัดตอนนั้น>
ทางเลือกที่พิจารณา: A / B / C     เลือก: B
เหตุผล: <ทำไม B ชนะ>
ผลข้างเคียงที่ยอมรับ: <trade-off ที่รู้ตัว>
ถ้าจะเปลี่ยนใจภายหลัง ต้องแตะอะไรบ้าง: <จุดที่ผูกไว้>
```

## 11. Rollout เป็นเฟส — ไม่ปล่อยทีเดียวทั้งโรงงาน

pattern ที่ใช้จริงในโปรเจคนี้ และควรใช้ต่อ:

1. **เปิดวงแคบก่อน** — seed สิทธิ์ให้ role ที่จำเป็นก่อน (เช่นหน้าใหม่เปิดให้ admin/manager) แล้วค่อยขยายจาก `/permissions` โดยไม่ต้อง deploy
2. **ของใหม่ที่ยังไม่ชัวร์ ให้ "อยู่คู่ของเดิม" ก่อน** — เช่น "OEE จริง (strict)" แสดงคู่ OEE มาตรฐาน ไม่ไปแทนที่ · ค่าเดิมยังอยู่ให้เทียบ
3. **ป้ายบอกสถานะให้ชัด** — ของทดลอง/mockup ต้องมีป้าย 🧪 และบอกว่าอันไหนจริงอันไหนจำลอง (ห้ามให้ผู้บริหารเข้าใจผิด)
4. **มีทางถอยที่ไม่ต้อง deploy** — ปิดฟีเจอร์ด้วยสิทธิ์/config ได้ดีกว่าต้อง revert โค้ด
5. **วัดผลก่อนขยาย** — ดูข้อมูลจริงว่ามีคนใช้/ตัวเลขสมเหตุผลไหม ก่อนบังคับใช้ทั้งโรงงาน

## 12. Anti-pattern — "แก้ฉาบฉวย" หน้าตาเป็นแบบนี้

| ❌ ฉาบฉวย | ทำไมถึงเป็นหนี้ | ✅ ทำแบบนี้แทน |
|---|---|---|
| ก็อปสูตร/logic ไปวางในหน้าใหม่ | อีก 3 เดือนสองที่คำนวณไม่ตรงกัน หาไม่เจอว่าอันไหนถูก | ย้ายไป util กลาง แล้วให้ทั้งสองที่เรียก |
| `if (ชื่อไลน์ === 'LASER-345')` | ไลน์ที่ 2 ที่มีพฤติกรรมเดียวกันต้องมาแก้โค้ดอีก | ทำเป็น**คุณสมบัติของไลน์** (`parallel_stations`) ตั้งค่าเองได้ |
| เพิ่ม role ใหม่เพราะ "ตำแหน่งต่างกัน" | role ระเบิดเป็นสิบตัว สิทธิ์เหมือนกันหมด | role = ชุดสิทธิ์ · ตำแหน่งเก็บที่ `position` · ต้องการ tier เพิ่มใช้ flag (`is_dept_admin`) |
| `catch {}` เงียบๆ | ข้อมูลหาย/ไม่บันทึกโดยไม่มีใครรู้ | ต้อง log/toast/แถบเตือน — **ห้ามล้มเหลวเงียบ** |
| แก้ข้อมูลใน DB ให้ตรงกับที่หน้าจอคาดหวัง | ต้นเหตุยังอยู่ เดี๋ยวข้อมูลเพี้ยนอีก | แก้ที่ต้นทาง (ฟอร์ม/validation) + ทำให้ผู้ใช้เห็นและแก้เองได้ |
| ตัดรายการที่ไม่เข้าเงื่อนไขทิ้งเงียบๆ | ผู้ใช้เห็นตัวเลขน้อยกว่าจริง แล้วไม่เชื่อระบบ | โชว์ "ซ่อน N รายการเพราะ…" + ทางไปแก้ |
| hardcode เลขฟอร์ม/ชื่อทีม/ประเภท ลงในหน้า | คนที่ต้องแก้คือ doc control/หัวหน้า ไม่ใช่โปรแกรมเมอร์ | เข้า master table + หน้าตั้งค่า |
| แก้ CSS เฉพาะหน้าให้ดูดีบนจอตัวเอง | จอ TV/มือถือพัง แล้วคนอื่นมาแก้ทับกันไปมา | ทำตาม UI-CONVENTIONS (ฟอนต์ขั้นต่ำ, grid, modal, marker) |
| "เดี๋ยวค่อยกลับมาทำให้ดี" โดยไม่จด | ไม่มีใครกลับมา | จดใน CLAUDE.md ว่า "ยังไม่ทำ + ผลกระทบ + เงื่อนไขที่ต้องทำ" |

## 13. เมื่อไหร่ที่ "แก้เร็ว" ยอมรับได้ (และต้องทำอะไรตามหลัง)

**ยอมรับได้เมื่อ:** ไลน์หยุดผลิต / ข้อมูลกำลังเสียหาย / หน้าจอที่ใช้ทุกกะพัง — **หยุดเลือดก่อน ถูกต้อง**

แต่ hotfix ต้องมี 3 อย่างเสมอ:
1. **คอมเมนต์กำกับว่าเป็นการแก้ชั่วคราว** + เหตุผล + สิ่งที่ควรทำจริง
2. **บันทึกเป็นหนี้ที่มองเห็น** ใน CLAUDE.md (ส่วน "ยังเหลือ/ยังไม่ทำ")
3. **ตามด้วยการแก้ต้นเหตุ** ในงานถัดไป ไม่ปล่อยข้ามเดือน

> ถ้า hotfix อยู่ในระบบเกิน 1 เดือนโดยไม่มีใครแตะ = มันกลายเป็นสถาปัตยกรรมไปแล้ว (โดยไม่ได้ตั้งใจ)

## 14. Checklist ก่อน commit / ก่อน merge

**ก่อน commit**
- [ ] อ่าน CLAUDE.md + UI-CONVENTIONS.md ส่วนที่เกี่ยวข้องแล้ว (และทำตาม convention เดิม)
- [ ] ไม่มี logic/ค่า ที่ซ้ำกับที่มีอยู่แล้ว (grep แล้ว)
- [ ] ค่า/รายการที่คนอาจอยากแก้เอง อยู่ใน master/config ไม่ใช่ hardcode
- [ ] error/ข้อมูลไม่ครบ **แสดงบนจอ** ไม่เงียบ
- [ ] query ที่อาจโตเกิน 1000 แถว paginate แล้ว
- [ ] หน้าใหม่: seed permission + กรอง scope + กรอง dropdown ครบ
- [ ] แตะ schema → มี migration file + additive + โค้ดทนทั้งก่อน/หลัง apply
- [ ] เอกสารอัพเดทในคอมมิทเดียวกัน (CLAUDE.md / UI-CONVENTIONS / ไฟล์นี้)
- [ ] คอมเมนต์บอก "ทำไม" ในจุดที่ไม่ชัดเจน

**ก่อน merge เข้า main (= deploy จริง)**
- [ ] `npm run build` ผ่าน (ไม่ bypass lint)
- [ ] ไล่ blast radius แล้ว — ระบุได้ว่ากระทบหน้าไหน/ตารางไหนบ้าง และพิสูจน์ว่าพฤติกรรมเดิมไม่เปลี่ยน
- [ ] จด SHA ก่อน merge + วิธี rollback (+ ลำดับ revert ถ้ามี migration)
- [ ] ถ้าเป็น product decision ที่ตีความได้หลายแบบ / ย้อนยาก → **ถาม user ก่อน**
- [ ] งานใหญ่: รัน `/qc-audit` ก่อน merge

## 15. สรุปครึ่งหน้า (ถ้าจำได้ข้อเดียว ให้จำอันนี้)

> **แก้ทุกครั้ง ให้ถามว่า "นี่คือเคสเดียว หรือเป็นเคสแรก"**
>
> - ถ้าเป็น**เคสเดียวจริงๆ** → แก้ตรงจุด + คอมเมนต์เหตุผล
> - ถ้าเป็น**เคสแรกของอีกหลายเคส** → ทำเป็น master/util/config ตั้งแต่ตอนนี้ เพราะตอนนี้ถูกที่สุด (มีเคสเดียวให้ย้าย)
>
> และไม่ว่าทางไหน: **อย่าให้ระบบเงียบ · อย่าให้เอกสารล้าสมัย · อย่า merge โดยไม่รู้ว่าจะถอยยังไง**
